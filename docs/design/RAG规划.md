# RAG 参考文档

> 文档状态：规划稿 / 设计参考  
> 适用项目：Story-Weaver  
> 文档目的：基于现有代码结构，规划「日摘要标签 + 首次事件登记 + 回忆检索」的轻量 RAG 方案  
> 当前约束：**只做方案与边界规划，不进入代码实现**

---

## 0. 结论摘要

现有架构已经具备实现轻量记忆检索的基础，不需要推翻历史装配，也不需要马上引入向量数据库。

推荐的最小改造路径是：

1. 保留现有 `timeline_nodes.day_summary` 正文与摘要生成流程；
2. 为日摘要增加独立的普通标签数据；
3. 增加「首次事件候选 → 校验 → 登记」的独立记录；
4. 在生成回复前做轻量回忆意图识别；
5. 只在当前分支父链上的旧日摘要中检索少量相关记忆；
6. 将检索结果补充到现有【前情提要】附近，并纳入现有上下文预算。

第一版目标是跑通三个核心能力：普通标签、首次事件登记、回忆检索。暂时不扩展为复杂事件图谱、通用 RAG 框架或向量检索系统。

---

## 1. 背景与目标

### 1.1 现有基础

当前项目已经具备以下基础：

- 日摘要存放在 `timeline_nodes.day_summary`；
- 摘要生成一次后默认固化，手动 `force=true` 才覆盖；
- 历史装配按当前节点的父链取最近 3 个 day 节点；
- 更早的 day 节点以日摘要形式进入 system 的【前情提要】；
- 已有上下文预算、动态每日条数、摘要裁剪与降级机制；
- 时间线节点已有 `parent_id` 与 `branch_id`，主线用 `branch_id IS NULL` 表示；
- 每个故事使用独立 `story.db`，迁移由 `apply_all_story_migrations` 统一执行。

### 1.2 本方案目标

在**不改变现有近三天原文装配骨架**的前提下，让模型在用户提起旧事时，能够额外看到少量相关的远期摘要记忆。

重点不是「把所有历史都塞进上下文」，而是：

- 平时不增加明显成本；
- 用户明确回忆时，才检索少量旧日记忆；
- 检索结果可解释、可控、可回退；
- 优先复用现有摘要与预算机制。

### 1.3 非目标

本方案第一阶段明确不做：

- 向量数据库 / embedding 服务；
- 自动事件图谱；
- 通用 RAG 框架；
- 跨故事记忆；
- 自动改写旧摘要正文；
- 第一版新增完整前端管理界面；
- 对现有时间线、分支、摘要体系做大规模重构。

## 2. 现有代码基线

### 2.1 摘要生成

相关位置：`src-tauri/src/timeline.rs`

现有事实：

- 日摘要字段为 `timeline_nodes.day_summary`；
- `DAY_SUMMARY_PROMPT` 要求只写事实：谁做了什么、关系或认知变化、未回收伏笔；
- 提示词要求第三人称、200 字以内；
- `generate_day_summary` 读取该节点的全部消息，剥掉导演指令标记后拼接转录；
- 转录截断到约 24000 字符；
- 使用与正文相同的模型配置和 API Key；
- 非流式请求，`max_tokens=1500`，`temperature=0.3`；
- 第一次尝试显式关闭思考，空正文时再重试一次；
- 结果写入前硬截 600 字；
- 节点已有摘要时默认直接返回，只有 `force=true` 才覆盖。

触发链路：

- 切换节点时调用 `backfill_day_summaries`，补齐当前节点之前、有剧情、无摘要、非倒叙的节点；
- 回复完成后先补历史摘要，再调用 `maybe_auto_day_summary`；
- 当天 AI 回复达到 10 条后，自动生成并持续刷新当天摘要；
- 界面支持手动生成/覆盖当天摘要。

阶段摘要：

- `story_summaries` 表和 `save_phase_summary` / `list_phase_summaries` 接口已存在；
- 目前没有自动生成，也没有接入前端；
- 本方案第一阶段不依赖阶段摘要。

### 2.2 数据库结构

相关位置：`src-tauri/src/story_db.rs`

整体是两层结构：

- `library.db`：全局配置、故事索引、立绘等；
- `projects/{story_id}/story.db`：每个故事一个独立 SQLite 库。

`story.db` 中与本方案相关的表：

- `timeline_nodes`：时间线树，包含 `parent_id`、`branch_id`、`node_type`、`is_flashback`、`day_summary`；
- `messages`：消息按 `node_id` 归属，包含 `role`、`content`、`mode`、`branch_id`；
- `story_summaries`：阶段摘要，包含 `kind`、`day_from`、`day_to`、`content`、`source_days`、`branch_id`；
- `branches`：分支定义，包含 `fork_node_id`、来源分支、颜色、备注等；
- `characters` / `relations` / `world_settings`：按分支隔离的设定数据；
- `debug_requests`：请求快照，记录 system、历史、预算参数、实际每日条数等。

结构约定：

- 主线：`branch_id IS NULL`；
- 分支：`branch_id` 为具体 UUID；
- 时间线父子关系靠 `parent_id`；
- 没有硬外键，主要靠应用层维护引用关系；
- 迁移函数是幂等的，老库通过 `ALTER TABLE` 补列、`CREATE TABLE IF NOT EXISTS` 补表。

---

### 2.3 历史装配

相关位置：`src-tauri/src/generate_stream.rs`

实际生成入口是流式命令，主要流程如下：

1. 构造稳定 system：
   - 基础写作规则与输出排版；
   - 数据字典；
   - 世界观；
   - 角色；
   - 方向和关系；
   - 世界观/角色/关系按当前分支过滤。

2. 取最近历史原文：
   - `KEEP_DAYS = 3`；
   - 按当前节点的父链取最近 3 个 day 节点；
   - 父链异常时退回按 `sort_order` 取；
   - 每天条数由上下文窗口和 token 预算动态倒推，`context.n_recent` 只作为上限。

3. 拼【前情提要】：
   - 更早的 day 节点读取 `day_summary`；
   - 只取父链上的旧日摘要；
   - 没有摘要时显示「（这一天还没有摘要）」；
   - 摘要区超预算时从最旧的一条开始丢弃。

4. 拼尾部上下文块：
   - 当前模式、篇幅、关系数值与状态、聚焦、约束、时空提示、导演指令；
   - 不落库，每轮现拼；
   - 和本次用户输入合并成同一条 `user` 消息。

5. 最终消息顺序：
   - system（含【前情提要】）；
   - 近三天原文（每天首条带【第 N 天】标记）；
   - 当前 user（尾部块 + 用户输入）。

另有 `src-tauri/src/generate.rs` 的非流式备用逻辑。它仍是较简单的固定 `n_recent` 装配，没有动态预算和完整分支过滤；目前未发现它被注册为 Tauri 命令，实际入口是 `generate_story_reply_stream`。本方案以流式通道为主，非流式通道只作为后续一致性检查项。

### 2.4 已发现但本次不重构的问题

以下问题与本方案相邻，但不应在 RAG MVP 中顺手重构：

1. `backfill_day_summaries` 的选择器按全表 `sort_order` 找「当前节点之前」的节点，没有按父链/分支过滤，分支故事中可能处理到其他分支的节点。
2. 插曲/倒叙节点在父链可用时，会进入「最近 KEEP_DAYS 个 day 节点」的分支，与代码注释所说的「只带当前节点」不一致；其自身消息可能没有进入上下文。
3. `generate.rs` 非流式通道与流式通道的预算、分支行为不完全一致。
4. 当天摘要达到阈值后会被自动刷新，和「摘要一次生成后固化」的直观理解存在差异。

上述问题应在 P0 阶段单独记录、评估优先级，不与 RAG 主链路混在一起改。

## 3. MVP 范围

### 3.1 本阶段要做

- 日摘要正文保持原样；
- 为日摘要生成普通标签；
- 生成首次事件候选；
- 首次事件独立登记、去重、可追溯；
- 轻量回忆意图识别；
- 在当前分支可见父链内检索旧日摘要；
- 将少量相关旧日记忆接入现有【前情提要】；
- 检索结果纳入现有 token 预算；
- 保持无回忆请求时的现有行为基本不变。

### 3.2 本阶段不做

- 向量化检索；
- 复杂实体关系图；
- 全量历史重排；
- 自动生成阶段摘要；
- 前端标签管理页；
- 跨故事共享记忆；
- 以 RAG 结果替代近三天原文。

## 4. 总体数据流

```text
用户消息
  -> 日摘要生成（保留正文）
  -> 产出普通标签 + 首次事件候选
  -> 保存标签 / 校验并登记首次事件
  -> 用户发起新的生成请求
  -> 轻量回忆意图识别
  -> 提取线索（标签、事件、关键词、日期）
  -> 在当前分支可见父链的旧日摘要中检索
  -> 取 Top-K 并裁剪
  -> 注入【前情提要】附近
  -> 正常历史装配与模型生成
```

关键原则：**回忆意图识别不等于一定检索旧历史**。如果近三天原文已经足够回答，应优先使用现有近三天原文。

## 5. 数据模型规划

### 5.1 设计原则

1. 不把标签直接拼进 `day_summary` 正文，避免影响现有摘要显示与覆盖逻辑；
2. 普通标签允许跨天重复；
3. 同一节点内的同一标签不重复存；
4. 首次事件登记独立于摘要正文，覆盖摘要时不删除已有登记；
5. 所有新数据都必须能按分支可见范围过滤；
6. 优先选择可索引、可去重、迁移成本低的方案。

### 5.2 普通标签存储方案对比

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| `timeline_nodes` 加 JSON 列 | 改动小，读写跟随节点 | 索引和标签检索不方便，去重与统计麻烦 | 可选，但不作为首选 |
| 独立 `day_summary_tags` 表 | 易索引、易去重、易按标签反查 | 多一张表、多一次写入 | **建议优先评估** |
| 每个标签一个独立列 | 查询直接 | 标签集合不稳定，迁移和扩展差 | 不推荐 |

初步建议：普通标签使用独立表，最终以 P0 代码核对和迁移测试为准。

### 5.3 普通标签表建议字段

表名示意：`day_summary_tags`

| 字段 | 含义 | 说明 |
|---|---|---|
| `id` | 主键 | INTEGER PRIMARY KEY |
| `node_id` | 来源时间线节点 | 关联 `timeline_nodes.id` |
| `tag` | 标签显示文本 | 例如「牵手」「院子」「害羞」 |
| `normalized_tag` | 归一化标签 | 用于去重和检索 |
| `tag_kind` | 标签类型 | MVP 可只使用 `normal` |
| `branch_id` | 分支 | 主线为 NULL，分支为 UUID |
| `source` | 来源 | 例如 `summary_model` / `manual` |
| `created_at` | 创建时间 | 本地时间 |

建议索引：

- 唯一约束：`(node_id, normalized_tag)`；
- 普通索引：`normalized_tag`；
- 普通索引：`branch_id`；
- 如后续需要按天范围查询，可再加 `node_id` 与时间线排序的联合查询辅助。

### 5.4 首次事件表建议字段

表名示意：`first_events`

| 字段 | 含义 | 说明 |
|---|---|---|
| `id` | 主键 | INTEGER PRIMARY KEY |
| `event_key` | 归一化事件键 | 例如 `first_hand_hold` |
| `event_label` | 事件显示名 | 例如「首次牵手」 |
| `story_day` | 故事内第几天 | 来自来源节点，不是现实日期 |
| `node_id` | 来源节点 | 事件首次被确认的剧情节点 |
| `branch_id` | 分支作用域 | 主线为 NULL，分支为 UUID |
| `evidence` | 证据 | 必须能指向摘要或原文中的事实 |
| `confidence` | 置信度 | 可选，MVP 可只做阈值过滤 |
| `status` | 状态 | `candidate` / `registered` / `rejected` |
| `source_summary_rev` | 来源摘要版本标识 | 可选，用于追溯覆盖前后的变化 |
| `created_at` | 创建时间 | 本地时间 |
| `updated_at` | 更新时间 | 本地时间 |

关键约束：

- 首次事件不能只靠普通标签去重；
- 登记记录必须保存事件类型、故事日期和来源节点；
- 覆盖摘要时不删除已登记事件；
- 同一可见分支作用域内，同一 `event_key` 不应重复登记；
- 事件登记的唯一性范围需要单独确认（见第 15 节）。

### 5.5 日期语义

现有结构中的日期相关字段：

- `timeline_nodes.date_label`：故事内日期文本，例如「第 5 天」；
- `timeline_nodes.sort_order`：时间线排序；
- `stories.time_origin`：故事时间起点；
- 现有结构没有单独的现实日历日期列。

因此检索时必须区分三种查询：

1. **故事内日期**：例如「第 5 天发生了什么」；
2. **现实日历日期**：例如「4 月 23 号发生了什么」，需要由时间起点和故事日推导；
3. **关系/事件阶段**：例如「我们刚认识的时候」「第一次牵手之后」。

第一版可以只完整支持故事内日期与事件/标签线索；现实日历日期的解析作为独立能力评估，不能和故事日混成一个搜索条件。

## 6. 摘要生成改造规划

### 6.1 输入

在现有摘要转录之外，向模型额外提供：

- 允许使用的普通标签列表；
- 当前尚未登记的首次事件类型列表；
- 输出格式要求。

动态标签列表的目的不是限制模型发现新事实，而是减少标签漂移和重复表达。

### 6.2 输出

建议摘要生成返回结构化结果，示意：

```json
{
  "summary": "两人在院子里散步，男主主动牵起女主的手，女主感到害羞。",
  "tags": ["院子", "散步", "牵手", "害羞"],
  "first_event_candidates": [
    {
      "event_key": "first_hand_hold",
      "event_label": "首次牵手",
      "evidence": "男主主动牵起女主的手",
      "confidence": 0.9
    }
  ]
}
```

要求：

- `summary` 仍然作为 `day_summary` 正文保存；
- `tags` 只保存为独立标签；
- `first_event_candidates` 只作为候选，不等于已登记；
- 解析失败时必须回退，不能因此丢掉摘要正文。

### 6.3 一次调用还是两次调用

可选方案：

- **方案 A：一次调用同时返回正文、标签、首次事件候选**  
  成本低，但需要模型稳定输出 JSON，解析失败要有回退。
- **方案 B：先生成正文，再单独抽取标签与事件**  
  对现有摘要正文逻辑影响小，但增加一次请求和成本。

初步建议优先评估方案 A；如果实际模型输出稳定性不足，再降级为方案 B。P0 阶段需要结合现有模型和提示词稳定性决定。

### 6.4 事务边界

摘要保存与标签保存应在同一数据库事务中完成，保证不会出现「正文更新了但标签还是旧的」状态。

首次事件登记建议作为独立步骤或独立事务处理，原因：

- 首次事件不是摘要正文的附属数据；
- 摘要可能被 `force` 覆盖；
- 事件登记需要独立去重和证据校验。

推荐顺序：

1. 生成结构化结果；
2. 开启事务：更新 `day_summary` + 替换该节点普通标签；
3. 提交；
4. 独立执行首次事件候选校验与登记；
5. 任一步失败都不能影响原始摘要正文可用性。

### 6.5 覆盖与刷新规则

- 普通摘要：已有值默认跳过，`force=true` 才覆盖；
- 普通标签：随摘要覆盖而刷新，但只影响该节点的标签集合；
- 首次事件：独立保存，摘要覆盖时不删除、不回改来源日期；
- 如果第 4 天的摘要后来才包含「首次牵手」，事件应登记为第 4 天，而不是发现它的第 6 天；
- 如果新摘要不再包含某事件候选，已有登记不自动撤销，除非未来明确引入人工纠错机制。

## 7. 首次事件登记规划

### 7.1 候选与登记的区别

- 候选：模型从某天摘要中提出「这可能是一个首次事件」；
- 登记：通过规则校验后，写入独立事件记录。

第一版不应把「模型第一次发现」直接等同于「故事中第一次发生」。

### 7.2 建议登记规则

1. 事件键必须稳定、可归一化；
2. 证据必须能在摘要或原始消息中找到对应事实；
3. 来源节点与故事日必须明确；
4. 登记前检查当前可见作用域内是否已有同一事件；
5. 已存在则跳过或合并，不重复插入；
6. 摘要后续被覆盖时，不删除已有事件登记；
7. 分支隔离：不能把其他分支的事件当成当前分支的记忆。

### 7.3 分支作用域（待确认）

建议第一版按「当前分支父链可见范围」理解首次事件：

- 主线事件对主线可见；
- 分支能看到其祖先链共享的历史事件；
- 兄弟分支之间不共享各自独有的事件；
- 同一 `event_key` 是否允许在不同分支分别登记，需要在 P0 明确。

这是数据模型里最需要先定案的语义之一，不能用简单的「全故事唯一」草率替代。

## 8. 回忆意图识别与检索

### 8.1 第一版优先轻量规则

第一版不急于引入分类模型，先用规则判断：

强线索示例：

- 「第一次」「首次」「以前」「那次」「当时」「还记得吗」「记不记得」；
- 「我们……过」「之前你……」「那天晚上……」；
- 明确的故事日：「第 5 天」「那天」。

辅助线索：

- 普通标签词；
- 角色名、地点、物品；
- 首次事件类型；
- 关系阶段词。

规则的目标是**提高召回率**，不是追求完全准确。误触发时最多多带一条摘要；漏触发才会让用户觉得「AI 忘了」。

### 8.2 意图识别不等于一定检索

示例：

> 宝宝，我们第一次牵手的时候你害羞了哎！你还记得吗，哈哈。

应识别为回忆请求，并检索「首次牵手」对应的旧摘要。

> 之前你为什么要去院子啊？

也是回忆请求；但如果近三天原文已经包含「去院子」的原因，应优先使用近三天原文，不强制额外检索旧摘要。

建议规则：

- 先从用户输入提取线索；
- 如果所有关键线索都能在近三天原文中找到，跳过旧摘要检索；
- 如果有线索不在近三天原文中，或出现明确「第一次/那次/当时」等强线索，则进入旧摘要检索；
- 无法判断时宁可多带一条低风险摘要，不要直接忽略。

### 8.3 检索候选范围

只允许：

- 当前节点的父链可见节点；
- `node_type` 为 day 的历史节点；
- 早于当前近三天窗口的节点；
- 与当前分支语义一致的节点。

不允许：

- 全表按 `sort_order` 扫描；
- 兄弟分支的独有节点；
- 其他故事的节点；
- 当前节点自身和近三天已带原文的节点。

### 8.4 检索信号与排序

建议排序优先级：

1. 首次事件精确命中；
2. 明确的故事日匹配；
3. 标签重合数量；
4. 摘要正文关键词命中；
5. 时间接近度作为低权重 tie-breaker。

第一版可以使用 SQLite 普通查询 + `LIKE` + 标签表索引完成；如果后续中文全文检索效果不足，再评估 FTS5，而不是一上来引入向量库。

### 8.5 Top-K 与预算

建议第一版：

- 最多返回 2～3 条旧日摘要；
- 每条只带日期、摘要正文、可选的首次事件说明；
- 不返回旧原文，除非未来明确需要；
- 额外检索预算设置上限，例如不超过输入预算的 10%，并设绝对上限；
- 预算不足时先降 Top-K，再丢弃低分候选。

具体数值需要在 P0 阶段结合当前 1M 窗口配置、实际摘要长度和用户使用习惯定。

## 9. 接入现有【前情提要】

### 9.1 建议格式

保留现有【前情提要】不变，在其后增加一个独立小区块，示意：

```text
【前情提要】（更早的剧情摘要，用于延续前文；具体细节以历史对话为准）
- 第 1 天：……
- 第 2 天：……

【相关旧日记忆】（根据本次提问检索到的远期摘要）
- 第 5 天（首次牵手）：两人在院子里散步，男主主动牵起女主的手……
```

这样做的原因：

- 不改变现有摘要的语义和显示方式；
- 回忆检索结果来源不同，单独标注更可解释；
- 后续调试时可以清楚看到「哪些是常规前情，哪些是本次检索补充」。

### 9.2 插入位置

在 `generate_stream.rs` 中，建议插入点位于：

- 现有 `recap_lines` / `fit_recap` 完成之后；
- 最终 `system` 与 `recap_extra` 拼装之前或紧邻位置；
- 必须重新计算 `recap_tokens` / `recall_tokens` 和最终历史预算。

不能把检索块当成「固定成本」直接追加，否则会破坏现有 token 预算和降级逻辑。

### 9.3 预算优先级

建议优先级从高到低：

1. 近三天原文；
2. 首次事件精确命中的旧日记忆；
3. 现有【前情提要】；
4. 普通标签/正文命中的补充记忆。

当总预算超限时：

- 先减少普通检索候选；
- 再减少现有摘要中最旧的条目；
- 不应为了保留检索结果而牺牲近三天原文；
- 关闭记忆上下文时，近三天原文、现有摘要和检索结果都不带。

### 9.4 调试与可观测性

建议在 `debug_requests` 的请求快照中增加（或后续扩展）以下信息：

- 是否识别为回忆请求；
- 提取出的线索；
- 检索到的节点与分数；
- 实际注入的回忆条数；
- 回忆块 token 估算；
- 是否因为预算被裁剪。

第一版可以先不新增前端展示，但后端调试数据应能回答「为什么带入了这条记忆」。

## 10. 上下文装配顺序（改造后）

```text
system 基础段（稳定前缀）
  + 现有【前情提要】
  + 【相关旧日记忆】（可选）
  -> 近三天原文（父链、动态 N、每天标记）
  -> 当前 user（尾部上下文块 + 用户输入）
```

关键约束：

- 近三天原文仍是主体；
- 旧日记忆只是补充；
- 检索块必须参与预算；
- 无回忆请求时，装配结果应尽量与现状一致；
- `memory=false` 时不带任何历史或检索内容。

## 11. 分支与日期语义

### 11.1 分支隔离

所有新功能必须沿用现有分支语义：

- 主线：`branch_id IS NULL`；
- 分支：具体 UUID；
- 可见范围：当前分支自身节点 + 父链共享历史；
- 不能把兄弟分支独有的节点、标签、首次事件带入当前上下文。

新增的标签表和首次事件表都需要包含 `branch_id` 或可推导的分支作用域，并在查询时使用父链过滤，而不是全表扫描。

### 11.2 日期分离

检索接口和内部数据结构应能区分：

- `story_day`：故事内第几天；
- `calendar_date`：现实日历日期（若未来支持）；
- `phase`：关系/剧情阶段。

第一版推荐只把 `story_day` 作为一等检索条件；现实日期与阶段检索作为后续扩展，避免把不同语义混成一个模糊搜索。

## 13. 测试与验收

### 13.1 数据与迁移

- 老 `story.db` 打开后自动补表/补列；
- 迁移可重复执行；
- 现有 `day_summary` 数据不丢失；
- 分支列为 NULL 的历史数据仍归主线；
- 新表索引存在且查询可用。

### 13.2 摘要与标签

- 正常摘要正文不受标签字段影响；
- 标签按节点保存，允许跨天重复；
- 同一节点同一标签不重复；
- `force=true` 覆盖摘要后标签正确刷新；
- 结构化输出解析失败时，摘要正文仍能保存；
- 模型未返回标签时不影响主流程。

### 13.3 首次事件

- 候选不会自动等于已登记；
- 同一可见作用域内重复候选不会重复登记；
- 摘要覆盖后已登记事件仍存在；
- 第 4 天摘要后来才补出的事件，登记日期仍为第 4 天；
- 兄弟分支事件互不污染；
- 主线事件可被后代分支作为共享历史看到。

### 13.4 回忆检索

- 回忆请求能触发候选检索；
- 非回忆请求不额外检索；
- 近三天原文已覆盖答案时可以跳过旧摘要；
- 只检索父链上的旧日节点；
- 不检索兄弟分支独有节点；
- 首次事件命中优先于普通标签命中；
- Top-K 与 token 上限生效；
- 预算不足时按优先级裁剪；
- `memory=false` 时不带检索内容。

### 13.5 回归

- 无回忆请求时输出结构与现状基本一致；
- 现有【前情提要】逻辑不被破坏；
- 近三天原文、动态 N、降级策略保持可用；
- 请求快照仍能正常记录。

**漏了裸标识符 `memory`**，于是得出"全仓库没有"的错误结论。

**事实**：

| 位置 | 内容 |

`memory=false` 时不检索、不注入（与原文第 9.3 / 10 / 13.4 节的表述一致）。

> 教训：做"某功能是否存在"的核查时，**不能用带引号的字面量去搜标识符** ——
> 会漏掉所有没有引号的正常代码位置。这类核查应当同时搜 `"x"`、`'x'`、`x`、`_x`、`x_`。
