### 2.2 明确不做（不是欠账，别再提）

| 事项 | 决定 | 理由 |
|---|---|---|
| **代码签名** | 不做 | 作者是学生、软件不赚钱、无证书（OV 一年几百到几千元 + 资质审核）。改交付"可验证性"：源码公开 + SHA256SUMS + [安全自证四件套](../user/security/README.md) |
| **自动更新** | 不做 | 避免"静默更新"这类风险；升级靠手动下载新版本 |
| **多用户 / 权限系统** | 不做 | 单机单人，数据目录权限 = 你的账户权限 |
| **加密数据库** | 不做 | 有意选择：无密码、方便备份/迁移/直接查库。需要加密就套 BitLocker/VeraCrypt，而不是做"半吊子加密" |
| **上帝视角扩写模式** | 不做 | 2026-10-20 用户明确放弃（"太麻烦"）。现有「旁白 / 对话」两态已够用；`messages.mode` 里的 `director` 值是历史遗留，不会再被写入 |
| **裸文本 = 元指令** | 不做 | 同上。元指令已由 `#标签` 承担；裸文本就是普通剧情，不再改造输入语法 |
| **蝴蝶效应预览** | 不做 | 同上。原设计是"改历史后对比新旧分支让用户选"，实现成本高；现有「设定版本 + 回滚」已能兜住误改 |

## 三、仍然有效的设计决策

| # | 决策 | 结论 |
|---|---|---|
| D1 | 跨天历史策略 | 近三天用原文 + 更早用摘要；摘要走 C 路线（分层），先落 B 层（日摘要），再叠阶段摘要 |
| D2 | 时间流逝的表现 | 日历/时间线用**灰色区间条**表现"无事件"，**不生成空节点**；用户点区间才插入事件 |
| D3 | "近三天"的口径 | **按节点数**（当前节点 + 前 2 个 day 节点），不按自然日 |
| D4 | 摘要的三条铁律 | ①生成一次就固化，绝不每轮重算 ②只追加不回改 ③摘要属稳定前缀，进 system 的【前情提要】段 |
| D5 | 评估模型评什么 | 评 **AI 回复质量**：输出排版 / 角色贴合 / 接续前文 / 剧情推进，四维 1–5 分，每维必须有证据引文，总分由软件算 |
| D6 | 检查的两层分工 | 本地规则只查纯结构；语法/歧义/数值矛盾交给 AI。AI 只报三类，不得评价文笔与创意 |
| D7 | 分支的适用范围 | **只做手动分叉**，不自动分叉；主要面向"主线 + 第一层分支"，嵌套在数据层可用但界面表达有限 |
| D8 | AI 输出的执行边界 | AI 只输出文本/JSON 补丁，**不接入 tool calling**；补丁经白名单校验 + 二次确认 + 快照后才落库 |

### 2026-10-21 修：回顾检测不到新加的物品（两个 bug + 一处权重设计问题）

用户实测：世界观里加了物品「rtx显卡」（**别名**「显卡」），第 4 天的日摘要里确实有「显卡」，
但「🔍 回顾试算」检测不到。

**真实数据摆在这里**：

```
world_settings: key='rtx显卡', category='物品', meta_json={"aliases":"显卡"}
timeline_nodes: 第 4 天 day_summary 含「显卡」✅
```

| # | Bug | 后果 |
|---|---|---|
| ① | `recall::explain`（试算用的那份）**自己复制了一份词典查询，且 category 列表没有 '物品'** | 试算面板里物品完全不存在 |
| ② | 两份词典都只取 `key`，**不解析 `meta_json.aliases`** | 用户输「显卡」（别名）永远匹配不上 |
| ③ | `entity` 权重 12 < `min_score` 20 | 就算命中也 `picked=false` —— "检测得到却带不出来" |

**修法**：

1. 把词典构建合并成**唯一实现** `push_world_terms(pool, branch, &mut lexicon)`，
   `search` 与 `explain` 都调它 —— 根治"改一处漏一处"（这正是 ① 的成因）；
2. 加 `split_aliases(meta_json)` 解析别名（中英文逗号 / 顿号 / 分号；**单字别名丢弃**，
   因为单字误命中率太高），名称与别名一起进词典；
3. `entity` 权重 12 → **20**（与标签词同档）。理由：用户点名一个专有名词、
   且它真的出现在那天摘要里，是**最强信号**，不该比"日常标签词"还低。

**真实数据验证**（`cargo test --lib diag_explain_alias -- --ignored`，只读副本）：

```
=== explain("显卡") ===
第 4 天    score=   22 picked=true  理由=含「显卡」
第 2 天    score=    0 picked=false
第 3 天    score=    0 picked=false
第 5 天    score=    0 picked=false 理由=这天没有日摘要 —— 自动检索看不到它（手动选择不受限）
```

**测试**：`split_aliases_handles_separators` / `split_aliases_skips_empty_and_single_char` /
`single_entity_hit_reaches_min_score`（回归锁：实体单命中必须过门槛）。

**教训**：同一段逻辑复制两份，早晚会漂移。词典构建、提示词渲染这类"两处都要用"的东西，
必须抽成一个函数，否则一定出现"界面上有、试算里没有"。

**根因**：`DayStrip` 的过滤写成了 `branchId === null || branchId === 当前分支` ——
**把「主线」当成了「共享历史」的同义词**。共享历史只是「分叉点及之前」那一段；
分叉之后主线自己往下写的天，属于**另一条时间线**。

**修法**：改用 `lib/branchView.ts::branchPathIds`（本分支自己的节点 ∪ 从分叉点沿父链上溯的那串），
和时间维其它地方同一套口径。

**真机核对**（dev 数据 `projects/4`，5 条分支）：「从6分支」= 主 1~6 + 分支 7、8、9、10；
「从7分支」= 主 1~7 + 分支 8~11；嵌套分支同样只带自己的父链。不再出现 16/17。

**验证**：前端 **137** 项（`dayStrip` 4 → 5）· `tsc` 0 错 · `vite build` 通过。

### 2026-10-26 「新建分支」的分叉节点下拉：按分支分组（**v3.8.0**）

**症状**（用户截图）：下拉里是一张平铺清单 ——「第 7 天」「第 7 天（分支内）」「第 8 天（分支内）」…
存在多条分支时，好几个「第 N 天（分支内）」长得一模一样，选的时候根本不知道是哪条线上的那天。

**根因**：选项标签只印了 `date_label` + 死板的「（分支内）」，**没有带分支身份**；
而且所有分支的天按节点插入顺序交错排列。

**修法**：新增纯函数 `lib/branchView.ts::forkPickerGroups` —— 主线一组、每条分支一组（组名 = 分支名），
组内按 `sort_order` 排；无节点的组不出现；分支记录已不在的节点归「未知分支」不丢。
下拉改用 `<optgroup>` 渲染，选项标签回归干净的「第 N 天」（插曲带 🎭）。

**真机核对**（dev 数据 `projects/4`）：主线 1~17 一组；「从6分支」7~10；「从7分支」8~11；
两条嵌套分支各自一组 —— 一眼能看出「这条分支从哪天开始」。

**验证**：前端 **140** 项（`branchView` 6 → 9）· `tsc` 0 错 · `vite build` 通过。

### 2026-10-26 分叉节点下拉改成自绘：固定向下展开 + 紧凑盒子（**v3.8.0**）

**为什么不用原生 `<select>`**：弹窗靠页面下方，原生下拉会被系统判成「下方空间不够」而**向上弹**，
刚填的分支名被挡住（用户要求固定向下展开）；原生控件的盒子高度跟系统行高走（约 34px），也压不下去。

**做法**：新组件 `views/ForkNodePicker.tsx` —— 触发盒 **28px**、列表最高 **220px** 可滚、
组名 + 分支色点、打开时把选中项滚进可视区、Esc / 点外面关闭、点某项即选中并收起。
业务状态仍在 `branchDialog.forkNodeId`，组件只负责"选一个 id"。

**验证**：`tsc` 0 错 · 前端 140 项 · `vite build` 通过（组件不在单测范围，交互靠手测）。

### 2026-10-26 故事卡片的「前史」撑破卡片（**v3.8.0**）

**症状**：给故事补写很长的前史后，卡片上那一行会**一直往右长**，冲出卡片、压到列表容器外面，
而 `text-overflow: ellipsis` 看着像是写了却没生效。

**根因**：典型的 flex 陷阱 —— 卡片是 `display:flex`，左栏是 flex 子项但**没写 `min-width: 0`**，
flex 子项的默认 `min-width: auto` 等于内容最小宽度；配合 `white-space: nowrap`，
它就"撑到内容那么宽"，`ellipsis` 永远没有收缩空间。

**修法**：左栏 `flex: 1; minWidth: 0`；前史本身做成**限宽的单行小框**（虚线/实线边框 + `ellipsis` + `title` 悬停看全文）；
标题行、元信息行同样单行省略；卡片加 `overflow: hidden` 兜底。

**验证**：`tsc` 0 错 · 前端 140 项 · `vite build` 通过（纯样式，无单测）。

### 2026-10-26 「新建故事」的前史输入框：宽度自适应 + 加高 60px（**v3.8.0**）

**症状**：新建故事表单里，前史输入框又窄又矮 —— 标签「前史（可选）」和它挤在同一行，
框只有默认 `cols≈20` 那么宽，写两行就得滚。

**根因**：`<textarea>` 既没写宽度也没写 `display`，保持 inline-block 默认宽度（`cols` 属性决定），
于是和前面的 `<label>` 一起排在一行里；它又不在上面的 120px/1fr 网格里，没有"整行"可言。

**修法**：标签 `display: block` + 上间距 12/下间距 6；文本域 `display: block; width: 100%; box-sizing: border-box`，
高度 `minHeight: 122`（原来是 `rows={3}`，约 61px，+60px），`resize: vertical` 保留手动拉伸。

**验证**：`tsc` 0 错 · `vite build` 通过（纯样式）。

### 2026-10-26 关键记忆：正文改「本轮对话」，并修掉它从来没进过提示词（**v3.8.0**）

**两个问题（用户实测）**：
  ① 记忆正文从上一轮 AI 的半句话开始（截图：`…”（杯子搁回桌上…）[用户] 我爱你 [AI] …`），
     看不出是谁对谁说了什么；
  ② 界面提示「已记下关键记忆：表白」，但 Prompt 预览里**根本没有【关键记忆】段**。

**根因**：
  ① 采集时把**整段**（该节点最多 6 条消息）喂给 `excerpt`，取「命中词 ±80 字」的窗口；
  ② `build_tail_block` 的实参 `memory_block` 与 `focus_examples` **传反了** —— 两个都是 `&str`，编译期不报错。
     于是【关键记忆】拿到空串（永不出现），【示例对话】拿到记忆正文。

**修法**：
  ① `evolution::memory_round` 只取「最后一条用户消息 + 它之后的 AI 回复」（每条截 400 字），
     `capture_first_events` 直接把这一轮原样落盘（不再取窗口）；删掉已无调用的 `excerpt`；
  ② 实参换回 `focus_examples, memory_block` 的正确顺序。

**验证**：Rust **341** 项（321 + 20 ignored；`evolution` 31 → **36**、`generate_stream` 37 → **38**、`memory` 7 → **8**）·
新增测试：取轮 5 条、正文整轮 1 条、尾部块串位 1 条。

**没做的**：已经写坏的那条记忆**不会自动重写**（旧文件里还是 ±80 字窗口的正文），
用户可在「关键记忆」面板里编辑正文，或删掉后等下一次同类事件重记。

### 2026-10-26 关键记忆改「态度打分 + 累计一张卡」（**v3.8.0**）

**起因**：用户看完记忆卡后问「AI 拒绝了，这需要记吗？被拒多次不该每条都写吧」。
讨论后的方案（用户拍板）：

| 决策 | 内容 |
|---|---|
| 判定方式 | **只给这一轮 AI 的回复打分**，不再用 4 个拒绝词做布尔判断 |
| 打分规则 | 强/中/弱三档拒绝为正、接受为负；**负向优先**（「我不喜欢你」不会被判成接受）；**标点算短语的一部分**（「别。」才是拒绝，「别忘了带伞」不算）；`|分| ≥ 2` 才算有判定，否则「未定」 |
| 多次表白 | **同一张卡累计**：`attempts` 次数一直加，`stance` 记被拒/被接受，`reasons` 只留前 3（权重×次数） |
| 后来接受 | **同一张卡改判**（不新开一条），已接受的卡不会被后来的拒绝翻回去 |
| 正文 | 只留**最近一次**的用户消息 + AI 回复；更早的交给「🔍 回顾」 |
| 范围 | 只对「表白」这样做；承诺 / 牺牲 / 背叛仍按"每种只记第一次" |

**文件格式**：front matter 增加 `attempts` / `refusals` / `stance` / `score` / `reasons`（JSON 一行），
正文第一段就是给提示词用的摘要（`render_block` 不用改）。

**验证**：Rust **348** 项（328 + 20 ignored；`memory` 8 → **15**）·
新增 `memory/attitude.rs` 打分器 + 5 条打分测试 + 2 条累计/改判测试。

**第二轮（同日，用户实测打脸第一版）**：三段真实拒绝回复（「别说了。」「这种话，我不接。」／「说多了，就不算数了。」／
「我哪句话是同意。」「你一个人在说。」）第一版全判成「未定」。修法：
  ① **只扫台词**（`「」`/`“”`），旁白里的「她没应声」不再影响判定；
  ② **短台词兜底**：≤24 字且含「不/没/别」算一条弱拒绝（词表补不全的正解）；
  ③ 词表补「别说了 / 我不接 / 不算数 / 我哪句话是同意 / 你一个人」等"只能是拒绝"的说法；
  ④ 「短句否定」只参与打分，不作为给模型的理由。

**第三轮（同日，用户继续实测）**：`「你认错人了。」「这种话，别在我这儿放。」` 仍被判「未定」，
而且**旧卡写着「态度未判定」时模型会越演越软**（"软接受"）。修法：
  ① 新增「否认前提」档（认错人 / 误会 / 想多了 / 开玩笑）；
  ② 注入时对**旧卡**用正文重算态度（只改措辞，不改文件）；
  ③ 有被拒表白时，块尾补一句「被拒绝 ≠ 关系确立」—— 这是"软接受"的直接解药；
  ④ 表白卡在提示词里单独拼一行（天数 · 表白：被拒绝（共 N 次）；对方理由：…），不再拿正文摘要凑。

**已知遗留**：`analyze.rs` 的 `ACCEPTANCE` 里仍混着「我们在一起吧」（影响关系提案，不影响记忆）；
**关系强度没接进打分**（capture 在关系加载之前跑）—— 目前靠台词本身判断，必要时下一版把"强度 0"作为先验。
**编辑过的消息不会重跑分析**：用户改了 AI 回复，记忆卡不会跟着变（要更新得删卡重记）。

**第四轮（同日，换路线：不再猜自然语言）**：又出现「你这算什么。」「刚还念数字呢。」这类说法。
用户拍板改成**协议**：
  ① 本轮用户输入命中表白/承诺时（`evolution::stance_marker_kind`），尾部块末尾注入一段
     「请在**最后一行**原样输出 `〔态度:接受〕` 或 `〔态度:拒绝〕`」——**只给两个例子照抄，不讲 JSON**；
  ② 记忆判定优先级改为 **标记 > 台词打分 > 未定**；
  ③ 标记在剧情区 / 编辑框 / 导出里剥掉（`parse.ts` / `memory::strip_marker`），**存库保留**（记忆要读）。
     注意剧情气泡有**两条渲染分支**（纯文本 / `parseScriptBlocks`），第一版只剥了一条，气泡里漏出来过；
     另外协议判定时往往"没有可引用的理由"，摘要里不许留空壳「对方理由：」，首次被拒的 `refusals` 也要算 1；
  ④ 「承诺」先走同一条协议，为后面"承诺有没有兑现"留口子（加标记种类即可，不改结构）。

**验证**：Rust **362** 项（342 + 20 ignored；`memory` 22 → **27**）· 前端 **143** 项（`parse` 40 → 43）。

**补充（同日）**：协议判定没有"词级理由"可写，卡片里出现过「（累计被拒 0 次）。对方理由：」这种空壳 ——
  ① 首次被拒的 `refusals` 补成 1；② 没有理由时**改用「她的原话」**（AI 回复里前 1–2 句台词，截 60 字），
  比词表更可信；③ 三者优先级：词级理由 → 她的原话 → 只报次数。
**发布**：**v3.8.0 已发布（2026-10-26）** —— MSI **9,211,904 字节**（8.79 MB）/ 便携 zip **7,828,777 字节**（7.47 MB），
哈希见 [releases/v3.8.0.md](../user/releases/v3.8.0.md)（`SHA256SUMS-3.8.0.txt` 199 字节，两份产物的 sha256 已逐字符核对）。
构建方式：`npm run tauri build`（带 `custom-protocol`，产物即打包版）。

### 2026-10-27 导演代价：开挂要结账（未升版本号）

**一句话**：导演指令从"免费的强制推进"变成**记账的开挂** —— 用一次，AI 要在回复最后一行交代"她凭什么松口"，
软件按类型自己算分；账记在 `director_costs`（带 `branch_id`，分支隔离），攒到 60 分就锁住导演指令，
账本里逐条「撤销 / 赦免」。

| 项 | 内容 |
|---|---|
| **协议行** | `〔导演代价〕类型：理由` —— 只认**最后一行、整行、理由 ≤ 32 字**，全角/半角冒号都收；**表外类型 = 0 分**（不记账，只把协议行从正文里删掉）|
| **分值表** | `director.rs::COST_KINDS`：交换 5 / 条件 10 / 时限 15 / 压力 20 / 心软 25 / 白给 30（单次上限 = 30）。**提示词里只有类型与口径，没有数字**：模型不碰数字、也不给 JSON |
| **一轮只结一次账** | 模板收据与关键词兜底各至多一条，**取更重的那一笔**（`settle`）；0 分不入账 |
| **注入** | 尾部块在【导演指令】之后补【导演代价】段，**只在用了导演指令的那一轮出现**（平时每轮都要求 = 协议行写进所有回复）|
| **新表 + 隔离** | `director_costs`（node_id / message_id / character_id / kind / reason / score / source / excused / branch_id），story.db 15 → **16** 张；累计按「分支 + AI 扮演者」各算各的 |
| **闸门第二条件** | `directorGate` 多收 `cost: { total, limit }`：累计 ≥ 60 就锁（原因里带数字），与"强度 = 0"并列；**阈值只在后端**（`LIMIT`），前端不抄一份 |
| **账本 UI** | 输入台「📒 导演账本 32/60」：最近 30 条（天 / 类型 / 理由 / 分值），每行「赦免」（留痕不计分）与「撤销」（删掉）；关键词推断那条标「（推断）」。账本按钮**不跟着闸门锁** —— 锁住时恰恰要靠它解锁 |
| **不人工确认** | 这是**角色对这件事的真实看法**，不是可以拒绝的提案：不弹确认框、不进「演进提案」队列，与「后台静默演进」是两条线 |
| **剥标记** | 存库前就剥（气泡 / 历史 / 导出 / 记忆都不带），前端 `parse.ts::stripCostMarker` 再兜一次（只认最后一行）；`export.rs` 也兜一次（老库/手改数据）|

**验证**：Rust **380** 项（**360** 常规 + 20 ignored；新模块 `director` **17**，`generate_stream` 39 → **40**）· 前端 **157** 项（`directorGate` 11 → **17**，
新增 `tests/directorCost.test.cjs` **8**）· `tsc --noEmit` 0 错 · `npm run build` ✅。

**没做的 / 已知边界**：代价**不随时间衰减**（只靠人工「撤销 / 赦免」调）；关键词兜底故意保守（同类型要命中 ≥ 2 个词），
宁可漏记；换 AI 扮演者就是另一本账（换角色不加锁，这是"她对你的看法"而不是全局债务）。
