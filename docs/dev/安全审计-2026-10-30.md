## 二、静态发现

### F-01 立绘下载：URL 由服务端给、鉴权头跟着走（中 · 已实测）

```rust
// src-tauri/src/generator_cloud.rs:466
async fn download(url: &str, cfg: &CloudConfig) -> Result<Vec<u8>, String> {
    let mut rb = reqwest::Client::new().get(url).timeout(...);
    for (k, v) in headers(cfg) {          // ← 含 Authorization: Bearer <你的 key>
        ...
    }
```

调用点：`:338`（OpenAI 兼容形态取 `data[].url`）与 `:425`（自定义形态取 `response_path`）。
`url` 完全来自**服务端响应体**，没有 scheme / host 白名单。

| 攻击者 | 能做什么 |
|---|---|
| 恶意/被换掉的绘图 API | 返回 `url = http://127.0.0.1:<port>/...`、`http://192.168.x.x/...`、`http://169.254.169.254/...`；后端**从你机器上**发起 GET → 端口探测 / 打内网服务 / 读云元数据 |
| 网络中间人（base_url 是 `http://` 时） | 篡改响应里的 url 指向自己的主机 → `Authorization: Bearer <key>` **直接送到对方** |

应用允许 `model.base_url` / `portrait.cloud_url` 填 `http://`（没有强制 HTTPS），中间人模型下这是现成入口。

**修复建议**
1. 只接受与 `cfg.base_url` **同 scheme+host+port** 的图片 URL（本地 SD 场景同源，不破坏现状）；
2. 非同源时**不带** `Authorization`（不少 CDN 本来就不需要）；
3. 至少拒绝私网 / loopback / 链路本地地址（除非 base_url 本身就在本机）。

### F-02 下载大小检查在"读完"之后（中低 · 已实测）

`resp.bytes()` 先把整个响应读进内存，然后才 `if bytes.len() > MAX_DOWNLOAD`（32MB）。
`MAX_DOWNLOAD` 只是事后拒绝，不是事前限制。

**修复**：先看 `Content-Length` 快速拒绝；再用 `resp.chunk()` 流式累计，超限即 `break`。

### F-03 审批队列落地不核对 before（低）

`apply_group_inner`（`evolution/proposal.rs:238-315`）读出当前 relation 值 → 把 pending 提案的 `new_value`
直接拼进去 → 一条 UPDATE。**没有**把提案里存的 `old_value` 与当前值比对。
对照 `check::apply_check_patch`（`check/patch.rs:503-509`）是有 `values_equal` 核对的 —— 两条"AI 改库"路径口径不一致。

影响：提案排队期间库被改过，确认后会**覆盖中间改动**；审计里记的 `before` 是"应用时重拼的当前值"，不是 AI 当时声称的旧值 → 审计失真。

**修复**：逐条用 `old_value` 与当前值比对，不一致整组拒绝并提示"提案已过期，请重新分析"。

### F-04 CSP 的 `script-src 'unsafe-inline'`（低 · 纵深）

`connect-src` 只有 `'self' ipc: http://ipc.localhost`，`object-src 'none'`/`base-uri 'self'`/`frame-ancestors 'none'` 都在。
但 `script-src 'self' 'unsafe-inline'` 意味着：万一将来引入 markdown→HTML 渲染或第三方组件注入，
内联 `<script>` 会直接执行，CSP 兜不住。当前前置条件不成立（见第二节 grep 全 0），所以是纵深问题不是漏洞。

### F-05 命令面对 main 窗口全量开放（信息）

`generate_handler!` 注册 **155** 个命令，`capabilities/default.json` 只有 `core:default` + `dialog:default`。
Tauri 的 ACL 管的是插件权限，自注册命令默认对 main 窗口全开放 —— "前端任意一次脚本执行" = "能调删库/清数据/写文件/改配置的全部能力"。
这与红线 3 是同一个前提：**只要前端没有注入点，它只是放大器，不是入口**。

### F-06 `assetProtocol` 复核（信息）

`scope: ["**"]` + `img-src`/`media-src` 放行 `asset:`。复核 `SECURITY.md §3.2` 逐条判断成立：
AI 输出是 React 文本节点、无 `innerHTML`，构造不出 `asset://`；`connect-src` 无外域，图片也发不出去（canvas 跨源污染）。
**补充一点**：`media-src` 也放行 `asset:`，音视频文件同样会被加载（同样不能外发）。
风险等级维持"低"，等 C 方案（`portrait://`）。

### F-07 WebView 创建失败 = 裸 panic，不弹对话框（低 · 动态发现）

实测（release `app.exe`）：

```
thread 'main' panicked at tauri-2.12.4/src/app.rs:1444:
Failed to setup app: runtime error: failed to create webview:
WebView2 error: WindowsError(0x800700AA, "请求的资源在使用中")
```

- `lib.rs` 的 `fatal_startup()` 只兜了**数据库初始化**；webview 建不出来时是 Tauri 自己的 panic，
  `install_panic_hook` 只把 `PANIC:` 写进 `startup-trace.log`，**用户看到的是"窗口一闪即没"**。
- `0x800700AA` 是 `ERROR_BUSY`：同 bundle id 的 WebView2 profile 被占用。dev 构建有独立目录（`#[cfg(debug_assertions)]`），
  **两个 release 实例没有** → 第二个直接被第一个打死。
- 触发时当时没有 `app.exe` 存活，可能有残留 `msedgewebview2` 持有 profile，**根因未完全定位**；
  换成独立 `WEBVIEW2_USER_DATA_FOLDER` 后又变成 `0x8000FFFF`（本会话无法创建 webview，原因同样未定位）。

**修复建议**：把 webview 创建失败也接进 `fatal_startup()` 那条"弹框 + 写日志 + 优雅退出"的路径；
或注册 single-instance 插件，第二个实例直接把焦点还给第一个。

## 三、动态验证（真实代码路径 + 真实网络栈）

做法：临时 `#[cfg(test)]` 探针模块（已删除，仓库无残留），起本地假服务端，直接调
`generator_cloud::generate_openai` —— 与界面点"生成"走**同一条**代码路径，只是由测试驱动。
运行：`cargo test --lib security_probe -- --test-threads=1 --nocapture` → **2 passed**。

### 3.1 F-01 实测：SSRF + Key 外带

- 假模型服务返回：`{"data":[{"url":"http://127.0.0.1:<目标端口>/admin/internal"}]}`
- 配置：`base_url=http://127.0.0.1:<api>/v1`，`api_key=sk-test-LEAKME-0123456789`，`auth_style=bearer`

**观测**：目标机收到 `GET /admin/internal`，请求头里 `Authorization: Bearer sk-test-LEAKME-0123456789`。
即：**服务端给什么 URL 就打什么，鉴权头原样带过去**。生成调用本身返回 `Ok`（内网响应被当成图片字节落盘），
说明它连"这看起来不像图片"都不校验。

### 3.2 F-02 实测：40MB 全量读入后才拒绝

- 目标机声明 `Content-Length: 40MB` 并完整写出；`MAX_DOWNLOAD = 32MB`
- **观测**：服务端**写满 40MB**（写满才说明客户端一直在读，不是 socket 缓冲糊弄过去的），之后客户端才返回"图片过大"。

## 七、修复记录（2026-10-30）

修的是 F-01 / F-02，改动集中在 `src-tauri/src/generator_cloud.rs`，**不碰数据模型、不加配置键**。

### F-01 图片下载来源准入

新增 `classify_download_url()`（纯函数，可单测）：

1. 只允许 `http` / `https`；
2. 与用户配置**同源**（`base_url` 或自定义请求地址）→ `SameOrigin`：放行，**带**鉴权头；
3. 其它地址 → 只允许 `https` + 公网 → `PublicHttps`：放行，**不带任何凭证**；
4. 本机/内网/链路本地（`127.*`、`10.*`、`172.16-31.*`、`192.168.*`、`169.254.*`、`localhost`、`[::1]`）
   一律拒绝 —— **同源除外**，所以本地 SD（`http://127.0.0.1:7860`）不受影响。

### F-02 流式限长

- 先看 `Content-Length`：超过 `MAX_DOWNLOAD`（32MB）**立即拒绝，不开始下载**；
- 没有长度（chunked）时用 `resp.chunk()` 逐块累计，超限即中止。

### 回归测试（`cargo test --lib generator_cloud` → 27 passed）

| 测试 | 锁住什么 |
|---|---|
| `download_policy_rejects_private_and_downgrade_targets` | 内网/降级/非 http(s) 全拒；同源（含 `127.0.0.1:7860`）放行 |
| `download_same_origin_still_sends_auth` | 同源仍带鉴权头，别把正常用法定死 |
| `download_refuses_cross_origin_loopback_before_request` | 跨源回环在**发请求之前**就拒 |
| `download_rejects_declared_huge_body` | 声明 40MB → 按 Content-Length 立即拒 |
| `download_stops_chunked_stream_at_limit` | chunked 写到约 32MB 客户端中止，服务端写不完 40MB |

全量 `cargo test --lib`：**450 passed, 0 failed, 20 ignored**。

**已知取舍**：若某个服务的图床在**另一个域名**且**要求鉴权**，现在会 401（跨源不带凭证）。
正确解法是给它加显式白名单配置键（`portrait.cloud_download_hosts`），而不是把凭证放开 —— 本期没做。

## 八、修复记录 · 第二批（F-03 / F-07）

### F-03 审批队列落地前核对 before（口径：**拒绝**）

- 新增 `ensure_group_fresh()`：把一组 pending 提案的 `old_value` 与库中现值逐条比对，
  任一条对不上 → **整组拒绝**，错误文案写明「当前值 / 提案里写的是什么」。
- 单组确认（`confirm_proposal_group` → `apply_group`）：落地前现场核对。
- 批量落地（`confirm_proposals_batch`）：**先对着基线把每一组各核对一次**，再打快照、再改数据。
  否则"组 1 把 50 改成 60"会让"组 2 的旧值仍是 50"被自己误判成过期 —— 第一版就是这么踩的，
  被 `batch_confirm_applies_all_but_takes_one_snapshot` 当场逮住。
- 核对通过后才落地，所以审计里记的 `before` 就是真实旧值，不再失真。

测试：`stale_proposal_is_rejected_instead_of_overwriting`（先改成 70 再确认 → 报"已过期"、
数据不动、状态仍 `pending`）、`fresh_proposal_still_applies`（正常路径不被误拦）。

### F-07 建窗口失败走 `fatal_startup`，不再裸 panic

根因：Tauri 在调 setup 钩子**之前**就按配置建窗口（`tauri/app.rs` 的 `setup()`），
建失败时直接 `panic!("Failed to setup app: {e}")` —— 那一刻 dialog 插件还没注册，用户什么都看不到。

改法：

1. `tauri.conf.json` 主窗口加 `"create": false`（官方支持的手动建窗方式）；
2. `lib.rs` 在 setup 里（dialog 插件注册之后、**数据库初始化之前**）自己建：
   `WebviewWindowBuilder::from_config(app.handle(), &cfg).build()`；
3. 失败 → `fatal_startup(...)`：写崩溃日志 + 弹原生对话框 + `exit(1)`。

放在 DB 初始化之前是**有意的**：第二个实例要在这里就失败退出，
不能让它先把临时快照之类的数据动一遍再死。

**实测（release，连开两个实例）**：

- 窗口标题变成「织梦机 · 启动失败」，不再是"一闪即没"；
- stderr **没有** `panicked at` / `Failed to setup app`；
- `startup-error.log` 写入：
  `无法创建主窗口（多半是另一个实例正开着，占用了 WebView2 配置目录）… 0x800700AA 请求的资源在使用中`；
- 测试实例与临时数据目录已清理，无残留进程。

> 注：本机测的时候**单实例也**报了 `0x800700AA` —— 说明还有别的进程占着
> `%LOCALAPPDATA%\com.guchenxi.story-weaver\EBWebView`。这正好是这条修复要兜的场景：
> 以前是静默死，现在会明确告诉用户"多半是另一个实例开着"。
