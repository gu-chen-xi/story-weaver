## 一、用户输入规则

> ⚠ **2026-10-20 更正**：本节是早期设计。实装只有**旁白 / 对话**两态；
> 「上帝扩写」模式**已明确放弃、不再实现**（用户决定）。下面的「裸文本 = 作者指令」
> 同样未采用——元指令改由 `#标签` 承担，裸文本就是普通剧情。

### 1. 双模式输入（早期设计，未采用）

- 🎭 沉浸扮演：用户以角色身份与 AI 对话、推进剧情 ← **实装为「对话」模式**
- 🎬 上帝扩写：用户以作者身份给出大纲 / 转折点，AI 扩写 ← **已放弃**

### 2. 括号语法

| 写法 | 含义 | 示例 |
|------|------|------|
| （动作） | 角色动作描写 | （推开酒馆的门） |
| "台词" | 角色对话内容 | "你终于来了" |
| 裸文本（无括号） | 作者指令 | 让A揭露B的身份 |

### 3. 实现状态（Tauri 2 现状，2026-10-08 核对）

> 早期批次 1~7 在 Electron 原型（renderer/index.html）实现，2026-09 迁移至 Tauri 2 后由 `src\App.tsx` / `src-tauri\src\*.rs` 重新落地。
> **注意**：下列"未实现"项是按代码实测标注的，早期文档曾把它们写成已实现（实际不存在 `parseInput` / `hasUnclosed` / 解析结果条）。

**已实现：**

- [x] 旁白 / 对话两态模式切换（`navMode`），对话模式含「我扮演 / AI 扮演」下拉；默认 我扮演=男主、AI 扮演=女主，无对应定位则为「自由」；**进入每个故事都会按该故事角色表校验一次**（跨故事带入或已删除的角色会被自动纠正并提示）
- [x] 输入内容**原样**发给模型，用户消息与 AI 回复分别入库；`#标签` 会被剥离并写入节点标签，`@角色` 只作本次聚焦注入提示词
- [x] **导演指令（2026-10-08 新增，2026-10-25 改口径）**：仅沉浸对话模式；输入台 `🎬 导演指令` 收集若干条，**一次性**附加到下一条消息（发完自动清空）；消息内联 `〔导演指令〕…` 标记，气泡上方单独显示指令条、正文不含标记；注入系统段 `【导演指令】`（**必须达成 / 必须付代价 / 不得白给 / 写出转变过程 / 不替用户角色做决定**），且该标记在历史与状态提取中会被剥离
- [x] **导演指令的软件闸门（2026-10-25）**：AI 扮演的角色 → 用户扮演的角色 关系强度 **= 0（彻底决裂）** 时，`🎬 导演指令` 直接锁住（按钮变 🔒、点了提示原因、已排队的指令也不随本次发送）。判定在前端纯函数 `src/lib/directorGate.ts`，**不交给 AI 判断**——"能不能做"属于软件层，"怎么做"才进提示词。没有关系记录时放行（数据稀疏不该让功能不可用）
- [x] **演进分析的两条边界（2026-10-27）**：① 只看**这一轮**（最后一条用户消息 + 它之后的回复），不拼更早的轮次；② **用过导演指令的那一轮只记事件、不生成数值提案**（开挂逼出来的"答应"不是她的真实态度，代价另记在导演账本里）。词表里不许放两字词（「我也」曾把「可我也撑不住再吵一次」判成接受，见 E-AI-15）
- [x] **导演代价（2026-10-27 新增）**：用了导演指令的那一轮，尾部块在【导演指令】之后注入【导演代价】，要求 AI 在回复**最后一行**整行写 `〔导演代价〕类型：理由`（类型限 交换/条件/时限/压力/心软/白给；理由 ≤32 字；**不出现分值、不出现 JSON**）。分数由软件按 `director.rs::COST_KINDS`（5/10/15/20/25/30）算，**模型不碰数字**。一轮只结一次账（模板收据与关键词兜底取更重，见 §一之补 5）；协议行存库前剥掉（气泡/历史/导出/记忆都不带），账记在 `director_costs` 表（带 `branch_id`）。累计到 60 分锁住导演指令（闸门第二条件），账本里可逐条「撤销 / 赦免」
- [x] 输出排版：`[角色名]“台词”` 强标记 / （圆括号）动作 / `*……*` 心声 → 对话区剧本渲染（旁白淡灰 / 台词橙色角色标签 / 动作斜体灰 / 心声暖玫瑰斜体带左竖线）
- [x] 篇幅档位（简单 / 详细）、剧情约束（chips，注入【剧情约束·绝对红线】）、敏感词过滤、记忆上下文开关

**未实现（待办或已取消）：**

- [ ] 括号语法解析器（`parseInput`）与「解析结果条 + 草稿确认面板」：**当前没有**，（）/引号只是让 AI 理解的书写习惯，软件不做本地解析
- [ ] 空输入 / 括号未闭合的发送校验（`hasUnclosed`）：**当前没有**（仅敏感词命中时会拦截）
- [x] **指令与剧情冲突时的优先级规则（2026-10-25 部分落地）**：软件层用「强度 = 0 不给发」兜住极端情况（见上一节）；提示词层把口径从「必须执行」改成「必须达成 + 必须付代价」（强度 1-20 要经由条件/交换/时限/外部压力之一换取，且不许「嘴上拒绝、身体先软」）

## 一之补：提示词结构（2026-10-10 重排，为前缀缓存服务）

每次发送给模型的请求按「稳定前缀 → 历史 → 易变尾部」排列，越靠前的内容跨轮越不容易变：

```
[system]    稳定前缀（跨轮不变，缓存主要吃这段）
  基础指令 + 输出排版 → 数据字典（强度档位 / 关系态势 / **角色三维**）→ **前史（v3.3，可空）** → 世界观 → 角色 → 方向和关系
[messages]  历史对话（user / assistant 保持角色区分，每次只追加）
[user]      本次用户消息 = 上下文更新块 + 分隔线 + 用户输入（同一格）
```

> ⚠ **两层视角要分清**：上面是**接口结构**（请求 JSON 里的 `role` / `content`），软件与缓存按这个结构走；
> 而**模型实际读到的**是这些消息被**展平成的一段连续文本** —— 模型看不到 `role` / `content` 字段名。
> 所以：**涉及结构的判断/验证由软件侧（数据库、界面）做；模型侧只能做文本层面的判断**（见「一之补 2」）。

**「上下文更新」块的合并形态**（块在前、用户输入在后，同一条 user 消息，用分隔线区分）：

```
【上下文更新】（软件自动附带的本轮运行参数，不是剧情内容、也不是用户角色的台词；…本块与后面的
用户输入属于同一条消息：分隔线以上由软件生成，分隔线以下才是用户输入）
【当前模式】沉浸对话：用户以“宸熙”的身份与你说话，你扮演“夏婉琴”回应。…
【篇幅要求·简单描写】…
【数值与当下】（本节的数值为当前真值，以本节为准；历史中的旧数值/旧状态作废）
  角色属性（只作状态与倾向的参考，靠动作/语气间接表现，不要报数字）：
  - 夏婉琴：体力 偏低(30) · 理智 正常(55) · 存在感 偏低(25)｜当下「刚被拒绝，强撑着」
  关系强度与状态：
  - A → B：强度 83（羁绊）…
- 宸熙 → 夏婉琴：强度 83（羁绊）｜状态：稳定（冲突止于拌嘴）

——— 以下为用户输入 ———
（宸熙攥紧了拳头）我不管，今天你必须给我答案。
```

- **关系拆两段**：方向和关系（稳定，进 system，形如 `A 是 B 的「X」（方向：单向，说明：…）`）；数值与当下（易变，进尾部块，形如 `A → B：强度 83（羁绊）｜状态：稳定（冲突止于拌嘴）`）
- **数据字典**：「三种读法」（强度档位 + 关系态势 + **角色三维**）合并成一段，紧跟输出排版，各自只出现一次
- **角色三维（v3.5 起；v3.2 时是四维）**：数值只作倾向参考，用「档位(数字)」双写（`体力 偏低(30)`）避免模型演血条；
  焦点角色优先注入，自由模式最多列 8 个（每个约 25 token，防挤占历史预算）；
  数据字典里明确要求"靠动作/语气间接表现，不直接报数字"。
- **`stat_screen` 的中文名已统一为「存在感」**（2026-10-22）：数据字典、检查补丁字段说明、
  导演监视器属性条、角色页表单统一用同一个词。此前监视器显示「戏份」、数据字典写「存在感」，
  同一个值两套叫法会让 AI 在"该改哪个字段"上犯嘀咕；数据库列名仍叫 `stat_screen`（不动，避免无谓迁移）。
- 重排原因：把易变内容压到历史之后，避免「当前模式 / 导演指令 / 关系数值」变化时击穿前面的全部缓存
- 非流式通道（`generate.rs`，备用）与流式通道（`generate_stream.rs`）的段落顺序保持一致

- **世界书（v3.4，触发式注入）**：`world_settings.category = "世界书"`，`meta_json` 里存
  `triggers`（逗号分隔）/ `always`（"1"=常驻）/ `priority`（0-100）。

  | | 进哪 | 触发 |
  |---|---|---|
  | 地点 / 势力 / 术语 / **物品** | system 的【世界观】（**全量**）| 不需要，永远在场 |
  | **世界书** | **尾部块**的【世界书】（命中才进）| 触发词命中本次输入或最近 3 条消息 |

  * 为什么分两套：前者"少而稳"，后者"多而散"（人物前史、器物来历、某地习俗）——
    全塞进 system 会吃掉历史预算，也会推高固定区。
  * 放尾部块的另一个原因：命中随消息变化，进 system 会**击穿前缀缓存**。
  * 预算：总字数上限 1200，按 `priority` 降序取；被挤掉的条数会在块里注明
    「另有 N 条命中，因篇幅未注入」—— 否则用户会以为设定没生效。
  * 常驻（`always=1`）的条目无视触发词，每轮都注入 —— 相当于"用世界书的机制做全量注入"。

- **角色卡 v2（v3.4）**：`characters` 新增 5 个作者字段。分工按**前缀缓存**划：
  - **system（稳定）**：`过去 / 动机 / 目的 / 行为准则` 拼进【角色】段的同一条里，每项截断 400 字；
  - **尾部块（易变）**：【示例对话】放**一个**角色的 `dialogue_examples`（截断 800 字）。
    选谁（四级，用户 2026-10-21 定）：① 输入里 `@角色名` 提到的 → ② 否则 AI 扮演的角色
    → ③ 否则**导演监视器「当前角色卡」的焦点角色** → ④ 都不满足就**不给示例**（示例可以为空）。
    每个候选都必须确实写了示例才入选。
    **这个回落是修 bug 加的**：焦点角色来自 `@`，不 @ 就没有焦点，
    最初"只给焦点角色"等于"绝大多数时候都不给"，写进库的示例永远用不上。
    并写死"只用于模仿语气、不要照抄、不要接续"——否则模型会把示例当剧情续写；
  - 空字段整项不出现；老故事升级后提示词零变化。
  - **AI 不能改这 5 个字段**：`check.rs` 的补丁白名单没收录它们（作者设定不该被 AI 改写）。
- **前史 / 序章（v3.3）**：`stories.prologue`（故事级，不随分支走）。非空时在 `【世界观】（含 地点 / 势力 / 势力关系 / 术语 / **物品**，全量一行一条）` **之前**插入
  `【前史】…（属于已确立的背景，不是本轮剧情；与后文设定冲突时以前史为准）`。
  空串整段不出现 —— 所以老故事升级后提示词零变化。放稳定前缀是因为它几乎不变，可吃前缀缓存。

### v3.5 的提示词改动（2026-10-23）

**① 情绪不再是数值**

角色属性从四维变三维：`体力 / 理智 / 存在感`。`stat_emotion` 留在库里但**不再进提示词**，
改由角色卡的「当前状态」文字表达，形如 `｜当下「刚被拒绝，强撑着」`。

新增【情绪表演】段，写死三者分工：

> **情绪只定方向；强度定藏露；理智定语量。三者冲突时以强度优先** ——
> 疏离档下，任何情绪都不外放给对象看。

**② 术语定死**（消灭"状态"一词三义）

| 指什么 | 叫法 |
|---|---|
| 关系层面 `稳定/紧张/破裂` | **关系态势** |
| 角色此刻那一行文字 | **当下** |
| 从当下 + 强度 + 理智读出来的方向 | 情绪（**不是字段**） |

尾部块标题也同步改名：`【数值与状态】` → **`【数值与当下】`**。

**③ 心声与台词的关系从"必须相反"改成六种**

| 类型 | 例 |
|---|---|
| 反向（口是心非） | *有事。但我不会说给他听。* |
| 旁支（跑题） | *他袖口上沾了灰。* |
| 自欺（找台阶） | *我只是懒得争，不是在意。* |
| 掐断（说到一半停） | *我本来想说——算了。* |
| 钝（只有身体感） | *耳朵在响。* |
| 算计（盘算利害） | *现在翻脸，吃亏的是我。* |

保留两条边界：疏离/戒备/拒绝越界时，心声必须**与台词同向**；心声不许写成剧情总结或人物点评。

**④ 关系配合度**（把强度翻译成合作意愿）

- 低强度默认拒绝：可拒绝、回避、拖延、谈条件；亲密接触一律先拒；主动配合必须有明确理由
- 硬触发清单：上一轮有肢体伤害且未道歉 / 强度 < 20 且对方提亲密接触 / 台词与身体冲突 → **必须明确拒绝**
- 拒绝之后就停住：不加缓和句、不加"但是"、不加半推半就的动作

**⑤ 数据字典英文化**

关系强度/态势/角色属性的说明改成**英文脚手架**（中文枚举值保留），因为英文指令更容易被模型读成规则；
末尾显式写死「输出必须是简体中文」。

**⑥ 关键记忆注入**（v3.5）

尾部块新增 `【关键记忆】`，位置在 **【世界书】之后、【示例对话】之前**
（先补"她背后的世界"，再提"你们之间发生过什么"，最后才教"她怎么说话"）：

```
【关键记忆】本故事里已经发生、不可重来的事（不要重演第一次；可作为回忆、心结或情绪的来处）
- 第 4 天 · 表白：……
```

数据来自 `<数据根>/library/default/projects/<故事>/memories/*.md`，按分支过滤，空白则整段不出现。

**⑦ 日摘要改成「每满 10 条刷新一次」**

同一轮数不重复跑（`summary.rs:109`）。以前是"超过 10 条后每加一条都重算"，白烧 token 且破坏前缀缓存。

## 一之补 2：「上下文更新」块的机制说明（2026-10-10）

> 这一节写给"看到历史里出现块字样就以为系统在累积"的情况 —— 无论人还是模型，都容易误判。

### 机制（确定的事实）

| 问题 | 答案 |
|---|---|
| 块存在哪 | **只存在于本轮请求里**。每轮调用时现场拼装（`build_tail_block`），随请求发走即丢弃 |
| 会不会写进数据库 | **不会**。`messages` 表里只有：用户输入的原文（含 `〔导演指令〕` 标记）、AI 回复 |
| 会不会出现在下一轮的历史里 | **不会**。历史从 `messages` 表读取，表里没有块 |
| 每轮会不会累积 | **不会**。请求里永远只有一份块（并入本次用户消息），条数固定 |
| 历史条数会不会随轮次增长 | **不会**。上限 N 条（默认 10，`context.n_recent`），超出时从最旧开始裁 |
| 块会不会落进调试快照 | 会（`debug_requests.tail_block`），**只给界面看**，不参与 AI 上下文 |

### 常见误判与正确验证方法

**误判**：模型有时会说"我看到历史里有 N 个块，每轮 +1"。这通常是它在数**自己历轮回复里的引用** —— 当它在 meta 模式下讨论这个块时，回复里会带上 `【上下文更新】` 这几个字；下一次它读历史，读到的就是自己的这段引用。**只含词、不含块正文**。

**⚠ 关键事实：模型侧看不到 `role` / `content` 字段。** 消息在送到模型之前会被**展平成一段连续文本**（服务端行为），所以模型无法执行"查历史里有没有 role=user 的消息"这种验证 —— 它只能看文本。因此验证要分两层做：

**① 权威验证（在软件侧 / 数据库侧做，这一层才算数）**

查该故事库的 `debug_requests` 最近一条快照，看 `history_json` 里有没有 user 消息同时含「【当前模式】」和「【数值与当下】」：

```sql
-- 在 story.db 上执行；返回 0 表示机制正常
SELECT id, created_at FROM debug_requests
WHERE id = (SELECT MAX(id) FROM debug_requests)
  AND history_json LIKE '%【当前模式】%'
  AND history_json LIKE '%【数值与当下】%';
```

- 有结果 → 机制坏了（块真的进了历史）
- 无结果 → 机制正常，模型看到的"块字样"只是它自己的引用

界面上的对应入口见下一段（请求日志 / 生成参数都会把块与历史分开显示）。

**② 模型侧验证（只能看文本，用它够得着的方式）**

让模型只看**文本特征**，不要让它去数"块"：

- 块正文**只会出现在整段上下文的最末尾那一格**（并入本次用户消息），且紧跟一条 `——— 以下为用户输入 ———` 分隔线；
- 历史对话正文里**不会**出现「【当前模式】」「【篇幅要求·」「【数值与当下】」这三行同时成组出现；
- 若模型想自查，只能回答："我能看到的文本里，`——— 以下为用户输入 ———` 出现几次？在这条分隔线**之前**是否出现过「【数值与当下】」？"——出现 1 次分隔线、且它之前没有再出现块正文，即为正常。

**界面上的验证入口**：「设置 › 请求日志」点开某条快照 —— 「💬 历史消息」显示时已剔除块并标注；块单独显示在「🔄 上下文更新（尾部块）」一节（并注明"每轮现拼，并入本次用户消息（分隔线以上），不落库、不进下一轮历史"）。「生成参数 › Prompt 预览 / Token 预算 / JSON」三页签同样分区显示（JSON 里为 `tail_block` 字段）。

### 给模型的建议口径（可直接粘贴到对话里）

```
不要再数"看到几个块"，你数不准 —— 你看到的是被展平的文本，而且你会把自己历轮回复里引用的
"【上下文更新】"字样也当成块来数。机制是：块每轮现拼、只在本轮请求里出现一次，并入我这条消息
（分隔线以上），不写进历史、不落库；历史只有对话正文，条数上限 N 条。
你只需回答两个文本层面的问题：① `——— 以下为用户输入 ———` 这条分隔线，你能看到几次？
② 在这条分隔线之前，有没有出现过「【当前模式】」和「【数值与当下】」同时成组出现的段落？
分隔线只有 1 次、且它之前没有块正文 = 机制正常。权威验证由我在软件侧查数据库完成，不用你做。
```

> 备注（2026-10-10 补）：早期版本的这条口径要求模型"查 role=user 的消息"，**是错的** ——
> 模型侧拿不到 role/content 字段，只会得到展平后的文本。已改为上述"只看文本特征"的口径。

## 一之补 3：跨天记忆与日摘要（2026-10-10）

> 背景：历史曾经**只取当前这一天**（切到第 5 天，前 4 天 AI 完全看不到）。跨天记忆的目标是：
> **近三天用原文，更早的日子用日摘要**，同时不破坏「稳定前缀 + 易变尾部」的缓存原则。

### 三条硬规则（不可违反）

| 规则 | 含义 | 为什么 |
|---|---|---|
| ① **生成一次即固化** | 某天的日摘要一旦生成就写进库，之后每次装配直接读它，**绝不每轮重算** | 每轮重算 → 前缀每轮都变 → 缓存全灭 |
| ② **翻篇后固化** | 过去的天由 `backfill` 补一次即固化；正在写的这天可随写随刷（到量后） | 避免每个请求都重算摘要（省一次调用） |
| ③ **放 system 的【前情提要】段** | 摘要与更早的天统一放这里，不进 messages | 位置固定、便于预览与调试（**不再要求逐字节不变**） |

### 日摘要是什么

- **落库位置**：`timeline_nodes.day_summary`（摘要属于"这一天"，不属于某条消息）
- **内容要求**：只写事实 —— 谁做了什么、去了哪里、关系或认知发生了什么变化、留下什么未回收的伏笔或约定；
  **不写感想、不写评价、不写台词原文、不写文采描写**；第三人称、过去时、200 字以内、一段话
- **何时生成**（两类触发，2026-10-11 定）：
  1. **过去的天**：切换节点 / 回复完成时，幂等地补齐"当前节点之前、有剧情、还没有摘要"的天；
  2. **正在写的这天**：回复完成后检查**当天 AI 回复条数**，达到阈值（默认 **10 条**）即自动生成/刷新当天摘要；
     **未到阈值绝不生成**（否则每轮都变，前缀缓存会被打散）。
- **不参与的节点**：倒叙 / 回忆节点；以及"还没有任何剧情"的天
- **能否覆盖**：只有用户手动点「📝 生成日摘要」并二次确认才覆盖；否则永远跳过已有值

### 分层（C 路线，先做 B 层）

```
日摘要（B 层，已实现）     ── 每天一条，进【前情提要】
阶段摘要（C 层，接口已留）  ── story_summaries 表 + 读写函数；等日摘要积累到一定天数再"若干天滚一段"
```

### 与验证相关的提醒

日摘要属于**软件侧数据**：模型看不到"哪段是摘要、哪段是原文"的字段边界，只能读到展平后的文本。
所以"摘要有没有进上下文、进得对不对"一律**在软件侧验证**（时间线的 📝 标记、当前这天的摘要卡片、
「生成参数 › Prompt 预览」里的【前情提要】段），不要让模型去猜。

---

### 跨天装配规则（B 子项落地，2026-10-11）

```
[system]  基础指令 + 输出排版 / 数据字典 / 前史 / 世界观 / 角色 / 方向和关系
          + 【前情提要】（更早的天，每天一条日摘要）
[messages]  近 3 个天数节点的原文（各自若干条，按预算动态分配）
[user]      上下文更新（尾部块）+ 本次输入
```

- **天数标记（2026-10-11 新增）**：每天**实际保留的首条消息**正文前加一行 `【第 N 天】` ——
  模型据此知道哪几句属于哪一天；只在首条加、不新增消息、不破坏 user/assistant 交替
  （若某天被截取到只剩后几条，标记会跟着"实际保留的首条"走）
- **保留天数**：`KEEP_DAYS = 3`（当前节点 + 前 2 个天数节点）；**插曲 / 倒叙不算天数**，不参与计数
- **每天条数（N 由预算倒推，不写死）**：`min(倒推 N, 用户每日上限 n_recent, 当天实际条数)`，且**每天至少 1 条**
  - `倒推 N = (历史可用预算 ÷ 保留天数) ÷ 单条消息平均 token`
  - `历史可用预算 = 窗口 × 安全系数 − 输出预留 − 固定区(实测) − 摘要区(实测) − 尾部块 − 本次输入(预估)`
  - **固定区与摘要区都取实测值**：固定区 = 实际注入的 system（基础指令/输出排版/数据字典/世界观/角色/方向和关系）；
    摘要区 = 【前情提要】里已生成的日摘要（**会随天数增长**）。写死常数会在加角色 / 天数变多时算错
  - 安全系数默认 **0.8**（用户保留：留 20% 防止软件异常导致爆上下文）
  - 界面「生成参数 › Token 预算」的「📐 每日 N 值」卡片**双口径并排**演示：「默认档 32k」与「当前设置」，各给出 **N 值理论上限**（预算能装多少条）与**封顶后的实际取值**（受每日上限约束）
- **两级降级**：① 先逐条降 N（下限 1）② 仍超预算则从**最老的一天**开始整天移出原文区，改用它的日摘要
- **开关联动**：关闭「记忆上下文」时**不带历史、也不带摘要**（否则关不掉）
- **设计取舍（用户 2026-10-11 决定）**：**不再以"前缀缓存"为设计约束** —— 摘要每轮从库里现读现拼，
  优先"简单、好算、好调"；因此不再要求摘要段"逐字节不变"

### 检查功能的提示词约定（第二批 ②，2026-10-11）

**分工**：本地规则只查纯结构问题；**语法 / 歧义 / 关系数值与类型矛盾交给 AI**。

**AI 检查提示词硬性约束**：
- 只报三类：① 语法（读不通、缺字、断句错）② 歧义（指代不清、可两解、同段自相矛盾）③ 与数据字典标尺矛盾
- **不得找茬、不得评价文笔与创意、不得提扩充建议、不得报个人口味问题**
- 每条必须给出**最小修改**（只改到能读懂、不歧义）
- **注入【数据字典】**（强度档位 + 状态含义）作为统一标尺，保证与生成时同一把尺子
- 强制 JSON 输出（`response_format: json_object`）并**显式关闭思考模式**（思考会吃光 max_tokens 导致正文为空）

**「继续对话」的上下文约定**：不保留多轮上下文，每轮只带「板块当前内容 + **上一轮建议** + 用户输入」，
因此要求 AI **每轮输出"更新后的完整建议集"（不是增量）**。

**一键替换的安全边界**：AI 只输出 JSON 补丁（不使用 API 层 tool calling）；
软件先做**白名单校验**（板块 / 字段 / 条目类型，禁止 id、created_at 等内部字段）→ **二次确认**（含改动前后对照）
→ 打快照 → 执行；JSON 不合法则降级为只读报告，不执行任何修改。

**补丁的四条硬性约定（2026-10-11 验收后加固）**：
1. **一板一字段集**：`field` 只能用当前板块自己的字段名（角色板块不得出现 `scale` / `attitude` 等世界字段）；
2. **`before` 必填**：原样复制 AI 看到的当前值，软件执行前会与库中现值**核对**，不一致即**拒绝该条**（防基于错误理解改动）；
3. **`value` 必须是完整值**（不是 diff、不是半个词）：关系数值须写 `0~100` 的整数，不得写「单向」这类文字；
4. **`direction` 不可改**：关系方向不交给 AI；方向存疑只在 `problems` 里说明（若只想报告，`patch` 留空）。

**提示词组织方式（2026-10-11 三轮加固）**：`check_system_prompt` 采用**一板一套**的独立模板 ——
角色板块模板里只出现角色/关系字段名，世界板块模板里只出现世界字段名（早期把两套字段拼在一个示例里，
模型会直接照抄世界字段写进角色补丁）。

**字段的判定依据（2026-10-11 六轮加固）**：模型**不知道**某段文字在数据库的哪个字段里（给它的内容是拼接后的 JSON）。
因此软件按「AI 声明的当前值」与各字段真实值比对来**反查字段**（相等优先 → 互为包含 → 取更长；对不上不猜）。
提示词据此放宽：**字段名写不准没关系，条目名与"改好后的完整文本"必须准**。

**板块与类型的判定依据（2026-10-11 五轮加固）**：不依赖模型对 `board` / `target_kind` 的判断；
软件用**数据库反查 `target_name`** —— 能匹配角色名 → 角色补丁；含箭头 → 关系补丁；能匹配世界条目 key → 世界条目补丁。
模型把角色标成 `world_entry` 也能纠正回来。

**字段名与板块的归一化（2026-10-11 四轮加固）**：模型经常把"要改的那个值"写成泛化词（`value` / `内容` / `值`），
或把角色关系标成世界板块。软件按**上下文**纠正：名字带箭头 = 关系 → 泛化词落地为 `strength`、板块改判为 `characters`；
角色语境 → `profile`；世界语境 → `value`。中文别名（`数值`/`强度`/`关系数值`/`人物小传`/`说话方式`…）同样归一为真实列名。
**只对泛化词兜底**：`scale` 这类"明确属于别的板块"的字段仍然拒绝，不猜。

**SQL 类型安全**：`strength` 在库里是 INTEGER 列 —— 读取按整数、写入按整数，比较时用数值感知（容忍 `80` / `80.0` / 空白），
避免 `mismatched types ... TEXT is not compatible with SQL type INTEGER`。

**软件侧容错（2026-10-11 二轮加固）**：模型若串用了别的板块的条目类型（如角色板块写 `faction_relation`），软件会按「板块 + 名称是否带箭头 + 字段是否属于关系」**归一化**纠正后继续执行，而不是拒绝整批；但 `before` 与库中现值不符时**整批不执行**（避免改一半失败），并提示重新检查。

> **回复质量评估已整套删除（2026-10-27）**：用户判断"多余"，插件、后端、`reply_evaluations` 表、`evaluate.auto`
> 配置一并移除，后面重新规划。这里不再描述它的提示词口径。

### 演进引擎的信号与自动触发（第三批，2026-10-11）

**自动触发**：回复完成后自动跑一次 `analyze_evolution`（**纯本地规则引擎，不调 API**），
只是"把剧情里读到的关系变化产成提案"，不替用户做决定；开关 = 设置 › API「自动演进分析」（默认开）。

**信号表（本地规则，全部为明确的剧情动作，避免误判）**

| 信号 | 触发词示例 | 处理 |
|---|---|---|
| 表白 | 我喜欢你 / 做我女朋友 / 向你表白 | 与「接受」同现 → 关系跃迁（**需人工确认**）；单独出现 → 只记事件 |
| 接受 | 我也喜欢你 / 我愿意 / 我答应你 | 同上 |
| 拒绝 | 我不喜欢你 / 我们还是朋友吧 | 表白被拒 → 强度 −15（自动应用） |
| 关心 | 关心 / 递伞 / 照顾 / 扶住 / 心疼 | 强度 +5（自动应用） |
| 冲突 | 争吵 / 冷战 / 推开 / 摔门 | 强度 −10（自动应用） |
| **承诺**（新） | 我保证 / 我发誓 / 说到做到 / 我永远 | **只记事件**，不改数值 |
| **守护**（新） | 挡在她身前 / 替她挨 / 挺身而出 | 强度 **+10**（自动应用） |
| **伤害**（新） | 恶语 / 冷暴力 / 失信 / 背叛 | 强度 **−20** + 状态「稳定 → 紧张」（自动应用） |

高风险的「关系跃迁」只产提案、必须人工确认；低风险的「关心 / 冲突 / 守护 / 伤害」自动应用并留审计日志。
所有改动前都会打快照，可回滚。

## 一之补 4：表态标记（2026-10-26）

**解决什么**：关键记忆要判断"AI 这一轮是接受还是拒绝"，靠猜措辞永远补不完词表
（实测：「别说了」「我不接」「你认错人了」「你这算什么」…每轮都不一样）。改成**协议**：

| 项 | 规则 |
|---|---|
| 触发 | **只在**本轮用户输入命中「表白」或「承诺」关键词时注入（`evolution::stance_marker_kind`）|
| 位置 | 尾部块**末尾**（紧贴用户输入之前），不在 system 里 |
| 内容 | 只给两个例子照抄，不解释 JSON、不给字段表：<br>`接受时输出：〔态度:接受〕`<br>`拒绝或回避时输出：〔态度:拒绝〕`<br>并要求写在**最后一行**，说明"只给软件记录用、不会被展示、不影响正文写法" |
| 与导演代价共存 | 同轮同时触发时**两行都写**：态度行在上、代价行在最后；解析只认"末尾协议区"，谁在前都能抓到（见 §一之补 5） |
| 判定口径 | 这一行只回答**角色自己的真实态度**：导演指令要她配合时正文照演，但这一行照实写 —— 被迫答应、只让一步、心里不认，都写「拒绝」（2026-10-27 实测：模型把"照指令配合"写成了「接受」）|
| 判定 | 记忆卡：**标记 > 台词打分 > 未定**；标记缺失自动回落 |
| 展示 | 剧情区、编辑框、导出文件、**发给模型的历史**里**都剥掉**（`parse.ts::stripStanceMarker` / `memory::strip_marker`），但**存库保留**（否则记忆拿不到）。**按形状剥**：表外值（「冷淡」「敷衍」）一样删 —— 2026-10-27 实测它留在历史里，模型每轮照着补 |
| 只能选两行 | 提示词明写"不要自创别的词"：模型写过 `〔态度:冷淡〕`，解析当它没写（退回台词打分），但界面上不许露（见 E-AI-17）|
| 预留 | 「承诺」先走同一条协议，为后面"承诺有没有兑现"留口子（加新标记种类即可，不改提示词结构）|

> 为什么不给 JSON：模型不知道我们的字段命名，给模板照抄比给 schema 稳。

## 一之补 5：导演代价（2026-10-27）

**解决什么**：导演指令是"强制剧情这样走"的特权，可它原来**没有账** —— 用户能无限次硬推"她答应了"，
关系数值、记忆、状态卡纹丝不动，开挂零成本。这一版把"她凭什么松口"变成**软件记账**，并且只让模型交**类型**：

| 项 | 规则 |
|---|---|
| 触发 | **只在**本轮用了导演指令时注入（尾部块【导演指令】之后紧跟【导演代价】）；没用指令的轮次不要求写 |
| 位置 | 回复末尾单独一行；若同轮也要写态度标记，两行都写（态度行在上、这一行在最后）。解析只认"末尾协议区"，**不要求它必须是最后一行** |
| 内容 | 模板给**一行照抄的例子**：`〔导演代价〕条件：她要求他先交出钥匙`（不要写「类型：」「理由：」这种字段名 —— 2026-10-27 实测模型会照字面抄，导致类型读不出来、整笔账丢掉）；类型只能取 交换 / 条件 / 时限 / 压力 / 心软 / 白给；理由 ≤ **32 字**（超了当没写）；全角/半角冒号都收 |
| 分值 | `director.rs::COST_KINDS`：5 / 10 / 15 / 20 / 25 / 30；**提示词里不出现任何数字**（模型只选类型）|
| 结账 | 一轮**只结一笔**：模板收据 + 关键词兜底（同类型命中 ≥2 个词才算）各至多一条，**取更重**的那笔；表外类型 = 0 分不入账 |
| 去向 | `director_costs` 表（分支隔离，按「分支 + AI 扮演者」累计）；累计到 `LIMIT`=60 就锁住导演指令。同时**自动扣关系强度**：白给 −10 / 心软 −5（其余 0，夹到 0），并弹「已自动下降 N」|
| 展示 | 协议行**存库前就剥**（气泡 / 历史 / 导出 / 记忆都不带）；前端 `parse.ts::stripCostMarker` 只动**末尾协议区**（跳过空行/协议行，遇正文即停），正文中间的同名文本不动 |
| 人工确认 | **没有**。这是角色的真实看法，不是可拒绝的提案；账本里只能事后「撤销 / 赦免」 |

> 为什么不给 JSON、不给分值：模型既不知道我们的字段名，也不该决定"这次扣多少"。给模板照抄 + 软件算分，
> 是 10-26 表态标记那条协议的同一个结论（见 [E-AI-12](错误合集.md)）。

> 为什么"取更重"而不是"收据优先"：模型自报轻了（写「交换」，正文却是"她心一软就答应了"）时，
> 按重的算才守得住"开挂有代价"；反过来自报重了也没什么可亏的。

### 赦免请求的提示词（2026-10-27）

「赦免」不是软件一键免掉，而是发一条**元对话**问过她：

| 项 | 规则 |
|---|---|
| system | 复用主生成那套（角色卡 / 关系 / 世界观），末尾追加一句「这是元对话、不要续写场景、只写态度 + 最后一行协议标记」 |
| user | 七段：谁请求赦免 / **当时**他对你用的导演指令（写明「当时的情况，不是现在」）/ 代价类型与理由 + 她当时的台词 / 当天历史（同节点、截 12 段）/ 回复模板 / 「同意=原谅」+ 用户的补充 / 要求她填「理由是」与「想对你说（可以不说）」 |
| 回复 | 认**整行**的 〔赦免:同意〕 / 〔赦免:不同意〕：优先在末尾协议区，找不到再全文按整行找（模型常把标记写在最前面再补理由）；混在句子里的不算。没标记时按正文「不同意 / 不原谅」兜底（先剥掉所有〔…〕段，避免标记自证） |
| 不进历史 | 请求与回答都**不写进** messages；只存 pardon_requests，界面上是 AI 回复下面的盒子 |
| 次数 | 同一笔账 3 次（盒子挂当天最后一条消息，次数按账算）；同一个故事日 5 次；3 次都没同意 → 软件再扣 5 点关系（不靠模型） |
## 二、AI 输出规则

### 1. 输出排版格式（当前生效；2026-10-08 已同步心声 / 导演指令 / 心理描写新规）

> **2026-10-28**：这一段与「基础指令」的**正文改成英文**（标题与示例句仍中文：标题是预览的切段锚点，
> 示例句要能照抄）。英文正文里显式要求「剧情正文用简体中文」，防止指令语言把输出带跑。
> 契约测试同步改成按英文标签断言（`prompt_rules_tests.rs`）。

AI 输出按【台词 / 动作 / 心声 / 旁白】分块，软件对话区按剧本样式渲染：

```
秦坦站在原地没有动。他原本准备好的那些话，那些“我可以等”“我不在乎”之类的台词，一句都说不出口。
[陆言]“我心里有别人了。你再这样，对你不公平。”
（陆言说完转身就走）
（手指却在门把上顿了顿）
*他怎么能这样……我分明没允许。可是为什么，我一点都不讨厌。*
```

- **台词（硬性要求）**：必须用双引号“”包住台词内容，并在台词前紧挨着写一个中括号，里面放**说话人的角色名**，格式：`[角色名]“台词内容”`。每条台词单独一行，**台词与动作不要写在同一行**。标记里写主名，正式回复的台词里可以用别名表示亲昵或其他意思。
  - 示例：`[母亲]“你回吧。”`
  - 软件识别：行首 `[角色名]` + 引号 → 渲染为橙色角色标签 + 台词
- **动作 / 神态（非台词）**：用中文括号（）包裹，独占一行。示例：`（他攥紧了拳头）` → 渲染为斜体淡色。**连续动作时一个动作一个括号、各自换行**，不要挤在同一行
- **心理描写（只用沉浸式心声一类，2026-10-08 起）**：第一人称、现在时，写角色脑中真实冒出来的念头、自我说服、犹豫、口是心非；**整行用星号包裹**，示例：`*他怎么能这样……我分明没允许。*` → 渲染为暖玫瑰色斜体 + 左侧竖线（软件会剥掉星号，星号不要写在行中间）。心声须单独成行，不与动作、台词、旁白同行，不用中括号或引号
  - 硬性要求：角色口是心非时（尤其傲娇型），心声必须写出与台词相反或矛盾的真实想法，角色自己未必肯承认
- **旁白 / 场景**：只写场景、时间、气氛、外部事件，**不进入任何人的内心**；正常成段书写，**不要用中括号或引号标记** → 渲染为淡灰旁白段
- 除"台词必须带 `[角色名]` 标记"外，其余内容保持自然文学发挥，不得输出 JSON / 死板格式

> 说明：本格式为"软性排版约定 + 强标记台词 + 心声标记"，旁白段落中自然出现的引号不会被误判为台词——只有行首以 `[角色名]` 开头的才识别为台词；只有**整行**被 `*…*` 包裹的才识别为心声（行内星号不触发）。
