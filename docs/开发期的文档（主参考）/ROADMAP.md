## 四、待细化的核心设计：摘要机制（D1 的延伸）

**目标**：让"更早的日子"以低成本进上下文，同时**不破坏前缀缓存**（上一轮刚建立的「稳定前缀 + 易变尾部」原则不能自己破坏）。

### 可选路线（三选一，待定）

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地规则摘要**（现成） | 每条消息已有 `abs` 一句话摘要，按天拼接 | 零成本、零延迟 | 机械、丢因果，只适合当"目录" |
| **B. AI 逐日摘要** | 每天剧情结束后，用一次小请求生成"这一天发生了什么"（≤N 字） | 质量好、可读 | 每天一次额外调用 |
| **C. 分层摘要**（A+B） | 每天一条日摘要（B）+ 若干天滚成"阶段摘要" | 可容纳整部长篇 | 实现最复杂 |

### 必须遵守的三条规则（无论选哪条）

1. **生成一次就固化**：摘要生成后写库，**绝不每轮重算** —— 否则前缀每轮都变，缓存全灭。
2. **只追加、不回改**：新的一天完成 → 追加一条日摘要；阶段摘要只"追加新覆盖的天"，不改写旧文字。这样历史段仍然满足"只追加"的缓存特性。
3. **存放位置**：摘要属于**稳定前缀**（进 system 的【前情提要】段，`【】` 段落便于「生成参数」预览分区），近期三天仍是 messages 里的原文（role 结构保留）。

### 建议的数据落点

- 日摘要：`timeline_nodes` 加一列（如 `day_summary`）或在 `messages` 的 `abs` 基础上聚合 —— 需要定
- 阶段摘要：新表（如 `story_summaries`，按覆盖的天数区间存）—— 需要定

### 6.2 子项 B：跨天历史装配（核心）—— ✅ 已实现（2026-10-11，待用户验收）

#### 6.2.1 动态 N 值公式（已拍板，替换原"固定 10 条"）

**核心思想**：把"每天 10 条"降级为**理想目标**，实际每天取多少条由**模型窗口 + token 预算**动态分配得出。

**用户 2026-10-11 修订：不要把 N 写死，N 必须由「历史可用预算」倒推。**

```
① 历史可用预算
   = 窗口 × 安全系数(默认 0.8；用户决定保留 —— 各项占用虽已显式扣除，仍留 20% 防止软件异常导致爆上下文)
     − 回复预留（max_tokens 4000 + 安全余量 800）
     − 固定区（实测：基础指令 + 输出排版 + 数据字典 + 世界观 + 角色 + 方向和关系）
     − 摘要区（实测：【前情提要】已生成的日摘要 —— 会随天数增长，不能当固定成本）
     − 尾部块（上下文更新块）
     − 本次输入（预估）

② 每日基准预算 = 历史可用预算 ÷ 保留天数（KEEP_DAYS = 3）

③ 实际 N = 每日基准预算 ÷ 单条消息平均 token
   （单条均 token 由近三天真实消息长度算出；N 再受「每日上限 n_recent」与「当天实际条数」约束）

④ 阶梯式降级（最终落地）
   第一阶梯 封顶    ：N = min(倒推 N, 用户每日上限（默认 10）, 当天实际条数)
   第二阶梯 强制降级：三天总量超预算时，从最老的一天开始把该天踢出原文区、转【前情提要】摘要块
   第三阶梯 继续降 N：仍超预算 → N 逐条递减（下限 1，保证当天仍有上下文）
   第四阶梯 兜底    ：摘要区本身放不下 → 从最旧的摘要开始丢弃（保证最近的记忆一定在）并提示
```

**说明**：固定区与摘要区都取「本次实际要发出去的内容」的 token 估算，而不是写死的常数 ——
写死会在加角色 / 加世界观 / 天数变多时算错（N 偏大 → 实际超窗）。

**踢出顺序（已拍板）**：`算出 N → 封顶 → 三天总量超预算则 Day-3 转摘要 → 仍超则继续降 N → 极端情况 N=0 只带摘要 + 本次输入`。
**每一步都要重新校验**：摘要区本身也占预算（摘要区 = 稳定前缀的一部分，随天数增长，因此也要纳入 ① 的"系统段占用"里一起算）。

| 序号 | 改动 | 涉及 |

```json
{
  "has_issue": true,
  "problems": [
    { "where": "夏婉琴", "field": "人物小传", "kind": "歧义",

  "patch": [
    { "board": "characters", "target_kind": "character", "target_name": "夏婉琴",

  ]
}
```

| 环节 | 规则 |
|---|---|
| 执行范围 | **只执行 patch 列出的字段**（局部覆盖，绝不整表重写） |

| 可回滚 | 执行前自动打快照（复用演进模块的 `make_snapshot`） |
| 降级 | AI 返回的 JSON 不合法 → 只显示只读报告，**不执行任何修改** |

### 8.7 验收阶段发现并修掉的三个问题（2026-10-11）

用户实际点击「一键替换」时失败（`no such column: scale`）并发现建议不可执行，根因与修法：

| 问题 | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① 补丁串板块 | 角色板块的补丁里出现世界字段（`scale` / `attitude`），报 `no such column: scale` | 提示词把两个板块的字段混在一个示例里，AI 照抄 | 每个板块**独立的**示例与枚举；显式写明「不要用其它板块的字段名」 |
| ② 前端字段名串 | 角色关系补丁显示成「规模 / 对主角态度」 | 前端 `fieldLabel` 把角色/关系/世界字段**混在一张表**里 | 拆成 `CHAR_FIELDS` / `REL_FIELDS` / `WORLD_FIELDS`，按 `target_kind` 取 |
| ③ 关系数值改不动 | AI 对 `strength` 给出 `value:"单向"` 这类"半个值"；且它想把**双向**关系改成单向 | 提示词没说清 `value` 必须是完整值、也没禁止改方向 | ① 硬性规则写明 `value` 必须是完整值（强度须为 0~100 整数）② **`direction` 从可改字段中移除**（方向不交给 AI）③ 新增 `before` 字段：AI 必须原样复制它看到的当前值 |

**新增防伪校验**：执行补丁前，软件读取库中现值与 AI 给的 `before` 比对 —— 不一致则**拒绝该条**并说明原因
（避免 AI 基于错误理解改动数据）。实测修复后三个补丁均为 `board=characters / kind=relation / ΣA→B / before 正确 / value 为完整整数`。

### 8.12 六轮加固（2026-10-11）：以角色名定位，字段由软件反查

用户提出关键判断（并拍板）：

> 「既然我们需要的是 AI 的判断内容本身，那就**只取 AI 的判断内容 + 必需的角色名**，
> 然后由**软件**根据角色名去改对应内容 —— 先看角色名，再看角色管理里的那几个字段。」

这条判断完全正确，而且指出了前几轮一直没解决的**根本矛盾**：

| 矛盾 | 说明 |
|---|---|
| 模型**不知道**"这段文字在数据库的哪个字段里" | 给它的板块内容是各字段拼成的 JSON，它只看到内容：`"女主，身材瘦小纤细，身高154cm"` 到底属于 `one_liner` 还是 `profile`，它无从判断 |
| 于是它随口猜字段名 | 猜成 `profile` → 与库中现值对不上 → 被 before 核对拒绝。实测报错即为：「夏婉琴」的 `profile` 当前值是「」，但 AI 以为它是「女主，身材瘦小纤细，身高154cm」（**那段其实在 `one_liner` 里**） |

**修法（本轮实现）**：

| 机制 | 内容 |
|---|---|
| **`resolve_field`（按内容反查字段）** | 拿 AI 声明的 `before` 去比对该条目**各个可改字段的真实值**：完全相等优先；否则取"互为包含"的字段；多个命中取**更长更具体**的那个；都对不上则不猜（保留原字段，交给 before 核对报错） |
| 校验顺序 | ① 按库反查板块/类型（8.11）→ ② 归一化字段名 → ③ **按当前值反查真实字段** → ④ before 核对 → ⑤ 执行 |
| 提示词放宽 | 明确告诉 AI："字段名写不准没关系，软件会按你对条目的判断定位正确字段；只要**条目名准确**、`value` 是**改好后的完整文本**" |
| 结果可追溯 | 执行结果里带上"实际的板块 / 类型 / 字段"（可能已被软件改判）；二次确认框在字段名不可识别时标注"（字段名由软件按内容自动定位）" |

**新增测试** `field_is_resolved_from_current_value`：造 `one_liner` 有值、`profile` 为空的角色，
AI 声称改 `profile` 但给的当前值来自 `one_liner` → 应改判为 `one_liner`，执行后**只有 `one_liner` 被改、`profile` 仍为空**；
before 与任何字段都对不上时**不改判**。共 **35 项单测**全过。

## 一、依赖链（为什么是这个顺序）

```
① 时间线扩展：节点关系由「线性顺序」改为「树」（parent_id）
        ↓  同一套数据结构
② 快照与回滚增强：按分支隔离的状态快照，可对比、可回滚
        ↓
③ 分支系统（软件原生，只做手动）：节点可分叉，各分支状态互不干扰，可切换回去
        ↓
④ 树状图管理平行故事：①的树长成分叉形态，可视化 + 跳转
```

**关键判断**：`①` 不只是"顺手做个可视化"。**"一个节点可以有多条后继"正是树的数据结构**，
所以 ① 直接按树来做（用 `parent_id`，线性顺序退化为"只有一个子节点"的特例），
到 ③ 时只需加"分叉 + 状态隔离"，**不必再改一遍数据模型**。这是本批最重要的一条技术决策。

## 二、① 时间线扩展：可展开树状图

| 项 | 内容 |
|---|---|
| **数据模型** | `timeline_nodes` 增加 `parent_id`（幂等补列）。现有线性链按 `sort_order` 顺序回填 `parent_id`，老库无感迁移；`sort_order` 保留用于同层排序与向后兼容 |
| **纯函数 + 单测** | `build_tree(nodes)`（线性 → 树）、`flatten_tree(tree)`（树 → 带层级的列表）、`path_to_root(node)`、`branches_of(node)` —— 全部纯函数，配单测（这是分支系统的地基） |
| **UI：树状图** | 时间线页新增「树状」视图：可展开/收起、显示层级缩进与连线、点击节点跳转；**保留现有线性视图**（默认仍是线性，树视图为可切换） |

## 四、③ 分支系统（软件原生，**只做手动**）

用户定的形态：**按节点来分支；分支之后仍是原来的运行逻辑；两个分支互不干扰各自的独立状态、
角色关系与后续时间线；而且可切换回去。**

| 项 | 内容 |
|---|---|
| **分叉方式** | 在任意节点上「从此处分叉」→ 新建一个子节点作为新分支起点（`parent_id` 指向该节点） |
| **状态隔离** | 每分支独立维护：角色卡与关系数值 / 状态、世界观与术语、演进提案、快照链。实现上沿用 ② 的"快照归属分支" |
| **切换** | 顶部或时间线树可切换"当前所在分支"；切换后对话区/角色管理/世界观/演进提案都跟着切 |
| **不干扰** | 分支 B 的生成**不得**读到分支 A 的后续内容（跨天装配按"路径"取，见 ①） |
| **明确不做** | **不做自动分支**（那属于插件，见第六节）；不做分支合并（先不做，避免数据冲突语义复杂） |
| **验收** | ① 同一节点分出 A/B 后，各写剧情互不影响（可用真实库验证）；② 切回 A 后看到的角色状态与离开时一致；③ 不分支的故事零变化 |

## 八、⑥ RAG：历史回顾与检索（方案已与用户讨论，采用"本地判定优先"）

用户的原始设想：**在提示词里加一句"当用户想回顾某段历史时请回复某某某"，软件接关键字，
把用户输入与找到的历史传回去再输出一次。**

**讨论结论**：流程保留，但**"关键字"不交给 AI 输出** —— 让模型在小说正文里插暗号不可靠
（检查功能六轮加固已证明该模型的结构化输出不稳；暗号会被揉进句子、可能改写或漏掉）。
改为**软件本地判定**：

| 层 | 做法 |
|---|---|
| **第一层：本地规则判定意图** | 输入命中"还记得 / 之前 / 那次 / 第一次 / 上次 / 回顾 / 第 X 天 / 当时"等模式 → 判定为回顾意图（纯规则、可单测、零成本） |
| **第二层：本地检索** | 用输入里的角色名 / 关键词 / 天数去检索：该分支**路径上**的日摘要 + 阶段摘要 + 原文片段，按相关度取 1~2 天摘要 + 3~5 条原文（**预算受控**，不整段塞） |
| **第三层：再跑一次生成** | 组装【历史回顾材料】+ 用户原话，再走一次正常生成；结果照常入时间线，但**标记为"回顾轮"**（不计入日摘要的天数累计） |
| **兜底** | 输入台加「🔍 回顾」按钮：用户自己指哪段就检索哪段（最可靠，不依赖意图识别） |
| **可选增强** | 允许 AI 用**方括号独立行**（如 `【回顾：第 5 天】`）提议回顾 —— 方括号比裸暗号可靠得多（模型已习惯 `[角色名]` 语法）；软件扫到则用它做检索锚点 |
| **验收** | ① 命中规则时能检索出正确片段并组装；② 回顾轮不污染日摘要与天数；③ 不命中时行为与现在完全一致；④ 检索为纯本地函数，可单测 |

### 10.9 第五批 ① 时间线树：数据模型 + 树状视图（2026-10-12 完成）

| 项 | 落地 |
|---|---|
| **数据模型** | `timeline_nodes` 增 `parent_id`（幂等补列）；老库按 `(sort_order, id)` 回填；**每次打开库跑一次幂等补链**（`ensure_parent_links`）—— 关键：新建节点 `parent_id` 为 NULL，只在"首次补列"时回填会让新节点永远没父节点、树碎成孤点 |
| **纯函数** | `children_index` / `path_to_root`（= `ancestor_ids`）/ `flatten_tree` / `branches_of` / `is_fork`，全部无副作用、可单测；另有 `load_tree_nodes` 读树 |
| **跨天装配改为按父链** | `keep_nodes`（近 KEEP_DAYS 天）与 recap（更早的天）都改为"**当前节点的父链上的天数节点**"，不再用"全表位置"。数据异常时**退回原位置算法**，保证不因迁移问题改变生成内容 |
| **界面（形态 A′）** | 并入现有时间线条：有子节点的节点左侧出现 `▸/▾` 展开钮（**默认全部收起**）；展开后子节点带缩进显示；分叉点的节点边框用强调色；`dayNodesSorted()` 同步过滤，日历轨道与"共 N 天"不会与时间线条对不上 |
| **不改的地方** | 保留线性视图作为默认；不新增页面、不新增下拉框 |

**风险与守住的方式（本批最重要的一条）**：跨天装配改按父链，**不分支的故事行为必须与改动前逐项一致**。
用等价性单测钉住：`linear_story_path_equals_positional` 对每个节点分别算"父链法"与"位置法"，
比较 近 KEEP 天 与 recap 两部分结果必须相同（含插曲混排的真实形态）。
另加 `forked_story_path_excludes_other_branch` 证明分支后两条线互不可见。

**实施中发现并修掉的问题**
1. 新建节点无父节点（见上，改为幂等补链）
2. **坐标系混用**：recap 项的排序键一度改成"链上相对下标"，而下游算降级天数时用的是"全表下标"（`earliest_kept`）→ 会算错哪些天的摘要进【前情提要】；已统一为全表下标
3. `earliest_kept` 一度被放进 `if` 分支内部导致作用域错误，已提到分支外

**真机验证**：对真实库（story 7，9 个节点、sort_order 有跳号 5→9→12→15）跑迁移，
父链完整串起（`1→2→3→6→7→12→15→21→29`），`path_to_root` 长度 = 节点数。

**用户实测后修正（同日）**：第一版按"**有子节点就显示 ▸**"实现，结果线性故事里**每个节点都长出一个 ▸**
（线性链上每个节点恰好有 1 个子节点），满屏折叠按钮、还带缩进，横向空间被挤占 —— 纯噪音。
改为按"**这棵树有没有分叉**"（存在任何节点子节点数 > 1）判定：**没有分叉时树控件一律不显示**
（不显示 ▸、不缩进、不留占位、圆角保持原样、日历也不过过滤），外观与改动前完全一致。
**教训：树控件的触发条件应当是"分叉"，而不是"有子节点"** —— 线性链上"有子节点"是常态。
### 10.10 第五批 ② 快照增强（第一项：回滚前的差异预览，2026-10-12 完成）

用户选择"先做 ② 再做 ③"，本轮先做其中最要紧的一项 —— **回滚不再盲操作**。

| 项 | 落地 |
|---|---|
| **问题** | 回滚是**破坏性操作**（现存角色 / 关系 / 世界观被整表替换），原实现只有一句 `confirm("确定回滚吗")`，用户根本不知道会失去什么 |
| **新增命令** | `preview_snapshot(storyId, version) -> SnapshotDiff` |
| **差异结构** | `SnapshotDiff { characters, relations, world_settings }`，每项为 `ItemChange { kind: added/removed/modified, label, fields }`，`modified` 带字段级 `before → after` |
| **纯函数** | `diff_items(before, after, fields, label_of, match_on)` —— 不碰数据库，可单测 |
| **比对字段** | 角色 15 项（**刻意不含 version** —— 内部计数，对用户无意义）、关系 6 项、世界观 4 项 |
| **界面** | 点「回滚到此版本」→ 先弹**差异预览**（分角色卡 / 关系 / 世界观三区，`新增 → 修改 → 删除` 着色，字段显示"当前 → 回滚后"）→ 确认按钮写明"（N 处变更）"；**0 差异时按钮禁用**并提示"完全一致，回滚不会产生任何变化" |

**实施中真机测出并修掉的两个 bug**（都是"看起来像整批设定被换掉"的假象）

1. **快照生成端漏了 `world_settings.id`**：`SELECT key, value, ...` 没选 id → 预览的按 id 对齐全部落空，
   7 条世界观**全被报成"将删除"**。已补 id（并同步调整索引，否则列会读错位）。
   注意：**历史快照的 payload 里仍没有 id**（无法追溯），所以世界观对齐改为按 `key`。
2. **对齐键两边不一致**：当前库的世界观条目有 id、老快照没有 → 一边按 `i:5`、一边按 `k:背景介绍`，
   配不上 → 同一条目**同时出现在"新增"与"删除"里**（新增 7 + 删除 7）。
   根治：对齐键**由调用方显式指定**（`match_on`），不允许函数"聪明地自己挑"。
   角色/关系按 `id`，世界观按 `key`。加 2 项单测锁住这个坑。

**真机验证**（真实库 story 7，15 个快照）
- 修复前：`V15：新增 7 · 修改 4 · 删除 7`（其中 14 处是假象）
- 修复后：`V15：新增 0 · 修改 4 · 删除 0` —— 剩下的 4 处**全是真实差异**
  （用户编辑过角色卡：`说话方式`、`当前状态`、`小传` 各改了内容），正是这个功能要展示的东西

**② 还剩的项**（后续做）：快照归属分支（`branch_id`/`node_id`，为 ③ 的状态隔离铺路）、快照清理策略（保留最近 N 个 + 手动标记保留）。

### 10.12 回滚安全垫：会话内临时版本（2026-10-12 完成，用户定"退出即失效"）

**背景**：回滚是破坏性的（整表替换设定）。用户确认要加"回滚前先自动备份"，但要求
**做成临时的 —— 一旦退出程序就失效**，避免版本列表被自动备份越堆越长。

| 项 | 落地 |
|---|---|
| **表结构** | `setting_snapshots` 加 `temporary`（默认 0）+ `note`（说明文案）两列，幂等迁移；**老库已有版本一律视为永久**（默认 0，不会被清理误删） |
| **回滚前自动备份** | `rollback_snapshot` 入口先调 `make_rollback_backup` 存一个临时版本，note 写明"回滚到 V{n} 前的自动备份（临时，退出程序即清除）"；**备份失败不阻断回滚**（否则"备份不了就永远回滚不了"），但会把情况写进返回文案 |
| **"退出即失效"的实现** | 程序**启动时**遍历 `library/*/projects/*/story.db` 调用 `purge_all_temporary_snapshots`，删掉上一次运行遗留的临时版本（`temporary = 1`）；失败只记日志，绝不阻断启动 |
| **版本号序列** | 临时版本与永久版本**共用同一条 version 序列**（否则回滚时会撞号） |
| **界面** | 列表里临时版本带「⏳ 临时」徽标（橙色边框 + 加粗版本号）+ note 说明；标题行新增「🧹 清理临时版本」按钮；说明文字写明"点错回滚可以用它退回来，但要在关掉软件之前退" |

**测试**（`temporary_snapshot_tests` 4 项，临时文件库）
1. `purge_removes_only_temporary` —— 清理只删临时版本，**永久版本必须原样保留**（最要紧的一条）
2. `migration_marks_existing_snapshots_permanent` —— 老库补列后已有版本视为永久；迁移可重复执行
3. `temporary_versions_share_the_same_sequence` —— 临时版本也占版本号
4. 另在 `rollback_sql_tests` 里覆盖"缺失 id 不许退回 0"

**用户可见的完整流程**
```
点「回滚到此版本」→ 差异预览（会改什么/删什么）
   → 确认回滚 → 自动存一份临时版本（⏳ 临时）→ 整表替换
   → 提示"已回滚…已自动备份当前状态为临时版本 V16（退出程序即清除）"
   → 若发现点错了：在列表里找到那条 ⏳ 临时，再回滚回它
   → 关掉软件后再打开：临时版本已被自动清除，只剩永久版本
```
### 10.13 直接编辑设定也有退路（2026-10-12 完成，第五批 ② B 项）

**问题**：设定版本**只有"应用提案"时才会产生**。直接在角色管理 / 世界观 / 关系里手改，
既不留版本也留不下备份 —— 手滑改错就没有退路（这一点在写 §10.11 的界面说明时才暴露出来）。

| 项 | 落地 |
|---|---|
| **触发时机** | **首次直接编辑设定之前**自动存一个临时版本。覆盖 10 处写入点：角色（存/删）、关系（存/删）、世界观设定（存/删）、势力关系（存/删） |
| **只存一次** | 用 `backupTakenRef` 记住"本次会话已备份"→ 连续改十几个字段只留 1 个版本，不会把列表刷满；**切换故事时重置**（新故事要重新备份） |
| **失败不阻断** | 备份存不上也要让用户能改设定（与回滚前的自动备份同一原则） |

**设计取舍（写在代码注释里）**
- 为什么不是"每次保存都存"：那会为每个字段改动产生一个版本，列表被冲垮，真正的历史版本反而找不到


**实施中踩到并修掉的一个隐蔽 bug（值得记）**

复制语句最初写成：

```sql
INSERT INTO characters (…, branch_id)
SELECT …, ?1 FROM characters       -- ?1 = 新分支 id
WHERE branch_id = ?                -- 匿名 ? 被 SQLite 当成 ?1！
```

**SQLite 里匿名 `?` 等价于 `?1`**，于是 WHERE 也绑上了"新分支 id"——而此时新分支还没有行
→ **静默复制出 0 行**（不报错、不抛异常，纯粹数据丢失）。

- 为什么差点溜过去：**主线场景的 WHERE 是 `branch_id IS NULL`（没有占位符）**，所以
  `create_branch_copies_world_state` 当时是**通过的**；只有"源分支非 NULL"（嵌套）时才暴露。
- 修法：`branch_clause` 增加**参数编号**（`?N`），复制语句固定 `?1` = 新分支 id、`?2` = 源分支 id，
  两个参数总是都绑，避免条件绑定带来的错位。
- 补测试 `nested_copy_copies_full_world_state`：**嵌套时也逐表断言行数**，专门为这个坑守门。

**测试（7 项）**：创建/列表/详情、**复制世界状态（逐表断言 + 临时版本不复制 + id 必须是新的）**、
主线不被触碰、**嵌套分支从源分支复制**、**嵌套时逐表行数正确**、错误处理、颜色轮替。

**顺带修掉的测试卫生问题**：测试原本会在用户的 `library/default/projects/` 里留下临时故事目录
（实测留下 7 个）。现在每个测试结束时关池并删目录，跑完 `library/` 只剩真实故事。

**验收**：114 项单测通过（107 + 新增 7）；`cargo build` / `tsc` 通过。

### 10.23 用户实测反馈修的三处（分支计数口径）（2026-10-16）

用户实测后反馈："测试 3：在分支里发消息不会出现在主线里"失败 ——
分支第 11 天建"测试A"、加第 12 天、说话，切回主线后第 12 天还在且能发消息。
并给出口径：**分支按天算不按消息算，分叉点那天算共享历史，之后才算分支起点**。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 切回主线后时间维仍有分支的"第 12 天"，且能发消息 | `loadTimelineAndMessages` 未指定节点时取 `nodes[nodes.length - 1]`（**全局最后一个**），那节点属于分支 | 默认节点只在**当前分支自己的节点**里选最后一个 |
| 2 | 主线里能点到其它分支的节点（可切换/可删除） | 时间维返回全树（树形展示需要），但没区分"能不能操作" | 其它分支节点 **🔒 + 变淡 + 只读**，点了提示"请先切到 X" |
| 3 | 从第 3 天分叉的分支里点「下一天」建成"**第 1 天**" | 天数基准只数了**分支自己的节点**（分叉点属于主线，没算进共享历史） | 基准改为 **本分支自己的节点 ∪ 父链上的共享历史**（新增 `branch_path_ids` 辅助） |

**顺带修的两处同类问题**
- `create_node_at_day`（"这段里插入事件"）的天数比较同样改为"本分支 ∪ 父链"
- `create_next_day_node` **原来根本不设 `parent_id`** —— 靠启动时 `ensure_parent_links` 按**全局顺序**补救，
  分支下会把新节点挂到别的分支上。现在**显式设父**（分支无自己节点时 = 分叉点）
- `create_next_day_node` 拆出 `_in` 核心版（接 pool + 分支），测试可直连真实函数而不用复刻 SQL

**新增测试 `new_day_is_scoped_to_its_own_branch`**（直连真实函数）：
分叉点为第 3 天时，分支的「下一天」= 第 4 天（父 = 分叉点）、再加 = 第 5 天（父 = 分支自己的上一天）；
主线各自数天数不受影响；**分支节点的父不得是主线的同一天节点**。

**口径已写入实施方案 §十二**（含"走过的弯路"表，避免重犯）。

### 10.24 分叉点被删除导致的"半坏"数据（用户第三轮实测）（2026-10-16）

用户反馈：分支里新建的节点显示"第 1 天"，且提示"属于主线"。

**查真实数据库找到根因**：`第三轮测试分支A` 的 `fork_node_id = 55`，但**节点 55 在
`timeline_nodes` 里已不存在**（被 `delete_timeline_node` 删掉了）。后果：

1. 分支找不到"共享历史的起点"→ `branch_path_ids` 只剩分支自己的节点 → 天数从 0 开始数 → 建出"第 1 天"
2. 新建节点的 `parent_id` 指向不存在的 55 → **父节点悬空**
3. 数据变成"半坏"状态，但**全程不报错**（最难查的一类问题）

| 修法 | 内容 |

### 10.37 主生成链路：超时 + 取消 + 部分内容标记（2026-10-16）

依据《织梦机-现状说明（困境与未解决项）》**第二节第 2 条**（原文列为"最值得先看"之一）。

**原文三条问题**

> - 主生成链路没有超时、没有重试、没有取消……请求可以永远不返回 —— 界面永远停在「正在生成」
> - 流式传输中途断开时，已收到的半截正文会被当成完整回复存进数据库，你拿到被截断的回复且没有任何提示
> - 网络请求失败这条分支直接返回错误、不发出任何事件 → 前端监听器永久泄漏

| 修法 | 内容 |
|---|---|
| **连接/首字节超时** | `GEN_CONNECT_TIMEOUT_SECS = 90`：`connect_timeout` + 用 `tokio::time::timeout` 包住 `send()`。上游连不上时**立刻报错**，不再永远转圈 |
| **流式空闲超时** | `GEN_STREAM_IDLE_TIMEOUT_SECS = 60`：每读一个 chunk 包一次 timeout。**上游半开（连接在但不推数据）时从"永远不返回"变成"明确报错"** |
| **取消** | 新增 `gen_cancel.rs`（进程级注册表，只存一个 `AtomicBool`）+ 命令 `cancel_generation(requestId)`；流式循环每收到一个 chunk 检查一次；前端「⏹ 停止」按钮 |
| **部分内容不冒充完整** | 取消 / 读失败 / 空闲超时时：**已收到的部分存下来并追加标记**"（⚠ 本段生成未完成：原因。以上为已生成的部分）"，并发 `chat-cancelled` / `chat-error`（带 `partial`） |
| **失败路径发事件** | `send()` 失败那条分支补发 `chat-error`（原来直接 return → 前端监听器永不注销 → 重复正文） |
| **发送守卫** | 生成中再次点提交会被拦下（原来连点两次会并发两条流） |

**前端配套**：`requestId`（UUID，随命令传下去）+ 统一收尾函数（注销 4 个监听器 + 清 `genRequestId`）+ 生成中把「➤ 提交」换成「⏹ 停止」+ 有部分内容时**重读节点**让标记显示出来。

**测试**

- `gen_cancel` 4 项：登记/取消/结束的往返、同 id 共享标志、未知 id 不算错、结束后不留残留
- `generate_stream::stream_guards` 4 项**防护栏测试**：超时常量存在且真被使用、循环里有取消检查与空闲超时、
  三个事件都在、失败分支发了事件、部分内容带标记。
  *（真实流式链路要上游服务，跑不了单测；这几条守着"最容易改回去"的写法，
  用 `include_str!` 读自己 —— 文中所有 needle 都用拼接构造，避免断言匹配到自己的源码。）*

**验收**：141 项单测通过（137 + 新增 4）；`tsc` / `vite build` 通过。

### 10.42 启动 panic（exit code 101）：日志插件写不进去（2026-10-16）

用户报告"打不开"，报错 `process didn't exit successfully: app.exe (exit code: 101)`。

**真凶**（直接跑 exe 拿到）：

```
Failed to setup app: error encountered during setup hook:
failed to initialize plugin `log`: 拒绝访问。 (os error 5)
```

`tauri_plugin_log` 的**默认目标是 `%LOCALAPPDATA%\<bundle id>\logs`**，
在用户机器上那条路径**拒绝访问** → 插件初始化失败 → setup 报错 → **panic，界面都出不来**。
而且它发生在 `fatal_startup` 之前 —— 连我们的错误对话框都来不及弹。

| 修法 | 内容 |
|---|---|
| **日志目录显式指定 + 多级兜底** | `paths::logs_root()` 改为"**先探测可写性**，逐级退让"：`<数据根>/logs` → `<数据根>/library/logs` → 系统临时目录 → **exe 同级 `logs`** → cwd 下 `logs`。判定方式是**真的写一个探针文件**（不能只看 `create_dir_all` 返回值 —— 实测某些环境"已存在目录可写、新建目录被拒"） |
| **日志插件改为可选** | 启用失败只 `eprintln` 提示 + 打印各候选的可写状态，**不再让应用起不来** |
| **数据库失败改优雅退出** | 原来是 `return Err` → Tauri 再 panic 一次；现在弹对话框说明原因 + 写崩溃日志 + `exit(1)` |

### 10.44 页面显示"localhost 拒绝连接"：缺 `custom-protocol` 特性（2026-10-16）

窗口能出来了（§10.43 修好），但页面显示 **"嗯… 无法访问此页面 / localhost 拒绝连接"**。

**根因**：`src-tauri/Cargo.toml` 里**没有 `[features]` 段、也没有 `custom-protocol`**。

Tauri 判定"打包版还是开发版"看的是**特性，不是 debug/release**：

```rust
// tauri/build.rs
let custom_protocol = has_feature("custom-protocol");
let dev = !custom_protocol;                  // 没开 → 认定是 dev

// tauri-codegen/src/context.rs:178
} else if dev && config.build.dev_url.is_some() {
    // 于是把前端地址写成 devUrl → http://localhost:5173
```

**所以 `cargo build --release` 出来的 exe 依然会去连 `localhost:5173`** ——
没有 vite 服务时页面就报"拒绝连接"。这解释了为什么**三种启动方式全部打不开**。

**修法**：`src-tauri/Cargo.toml` 补上

```toml
[features]
default = []
custom-protocol = ["tauri/custom-protocol"]
```

构建命令随之变为（**`--features custom-protocol` 不能省**）：

```powershell
npm run build
cd src-tauri
cargo build --release --features custom-protocol
```

（`npm run tauri build` 会自动带上这个特性。）

#### 验证方法（决定性）

起一个监听 `127.0.0.1:5173` 的探针，再启动应用：

```
=== 5173 收到的连接：0 次 ===
✅ 应用没有访问 5173 —— 用的是内嵌前端

PID=25396 class='Tauri Window' 标题='织梦机' 尺寸=(1295, 837)   ✅ 主窗口正常
```

exe 里也能看到 `<!doctype html>`（前端确实内嵌了）。

**教训**：Tauri 的"dev 模式"由 `custom-protocol` 特性决定；
**直接用 `cargo build --release` 而不带该特性，会得到一个"看似打包、实则仍要 dev 服务器"的 exe**。

### 10.48 立绘列表 N+1 查询（《现状说明》5.4）（2026-10-17）

**原文**：立绘列表 3N+1 查询，素材多了会卡。

#### 实际比"3N+1"更严重

`portrait_list` 是「查一次列表 → 每行调 `row_to_item_bound`」，而那个函数每行：

| 每行做的事 | 查询数 |
|---|---|
| 查故事标题 | 1 |
| **新建一个 story.db 连接池** + 查角色名 | 1 + 1 次建池 |
| 查版本历史 | 1 |

N 张素材、M 张绑定了角色时，总开销 = **`1 + 3N 条查询 + M 次新建连接池`**。
**连接池创建远贵于单条查询** —— 这才是真正的大头。

#### 修法

| 数据 | 原来 | 现在 |
|---|---|---|
| 版本历史 | 每张 1 条 | **1 条** `WHERE portrait_id IN (...)`，按 portrait_id 分组 |
| 故事标题 | 每张 1 条 | **1 条** `WHERE id IN (...)` |
| 角色名 | 每张 1 条 + **每张新建连接池** | **每个不同故事 1 条** + 每个故事 **1 次**建池 |

顺带：SQLite 绑定参数上限 999，所以按 500 一批分块（素材上万也不会炸）。

#### 测试（新增 4 项）

| 测试 | 作用 |
|---|---|
| `batch_list_matches_rowbyrow_oracle` | **核心**：批量版必须与"逐行版（旧实现，留作 oracle）"**完全相同** —— 内容、顺序、绑定名、版本列表逐字段比对。覆盖 6 种情况（有绑定/无绑定/只有 story 没 character/多版本/无版本/故事不存在） |
| `batch_is_much_faster_than_rowbyrow` | 60 张素材（40 张绑定）实测：**逐行 36.5 ms → 批量 3.0 ms（12.4 倍）**；硬断言"不许比逐行慢" |
| `batch_list_handles_empty_table` | 空表不越界 |
| `list_path_must_not_call_per_row_loader` | **结构守卫**：用 `include_str!` 读源码，断言 list 路径里**不许再出现** `row_to_item_bound`。这类"批量改回逐行"的退化**不会让任何测试失败**（结果一样，只是变慢），只能靠守卫拦 |

#### 一个测试自身踩的坑

`ensure_table` 里有条**迁移**：把"没有任何版本记录的素材"补上 version 1
（`change_desc` = 导入图片素材 / 创建占位素材）。所以"无版本素材"读出来是 **1 条**不是 0 条 ——
我第一版断言写成 `is_empty()` 挂了，已改为 `len() == 1` 并注明原因。

#### 真实数据验证

用改造后的两条批量 SQL 直接对真实 `library.db` 执行：

```

② 版本历史：一条 IN 查询拿到 3 条（原先要 3 条查询）
③ 故事标题：一条 IN 查询，1 个故事 → [(7, '初次相见')]
④ 角色名：需要查 1 个故事（原先要查 3 次 + 开同样多次连接）
```

### 10.49 `open_story_pool` 统一 + 连接池缓存（2026-10-17）

**起因**：§10.48 修立绘 N+1 时顺带发现 —— `open_story_pool` 被**复制粘贴到 13 个模块**。

#### 排查结果比预想严重

13 处定义演化出 **6 种不同实现**，而且**每种跑的迁移不一样**：

| 模块 | story_columns | branch_columns | snapshot_temp | tags | day_summary | summaries | parent |
|---|---|---|---|---|---|---|---|
| branch | | ✓(报错) | | | | | |
| cache / check / evaluate / export / state_extract | — | — | — | — | — | — | — |
| characters / relations / world | ✓ | ✓ | | | | | |
| evolution | ✓ | ✓ | ✓ | | | | |
| generate / generate_stream | ✓ | | | | | | |
| timeline | | ✓(报错) | | ✓ | ✓ | ✓ | ✓ |

**后果**：同一份数据库，从不同模块进来，表结构演化覆盖范围不同 ——
"在角色页打开过"和"在时间线页打开过"留下的库状态可能不一样。
更糟的是**没有任何缓存**：每次调用都重跑一遍全部迁移探测。

#### 修法

1. **唯一实现**：`story_db::open_story_pool(story_id)`；
   13 个模块的本地副本全部删除，改为调用它。
2. **迁移取并集**：新增 `apply_all_story_migrations`，跑齐上表所有迁移。
3. **宽容处理**：逐个 `let _ =`。理由：`ensure_*` 内部是 `PRAGMA table_info` + `ALTER TABLE`，
   **表不存在时必然失败**；若在这里向上抛错，会让"原本能跑"的路径开始失败
   （例如只建了部分表的测试库）。迁移失败不影响后续查询，真有问题会在查询时报更清楚的错。
4. **连接池缓存**：`OnceLock<tokio::sync::Mutex<HashMap<PathBuf, SqlitePool>>>`。
   - **键是解析后的绝对路径**（不是 story_id）—— 同一 id 在不同数据根下不会串
   - 命中时**校验文件还在**：不在就丢掉重建（测试清场 / 用户手工删库）
   - **不 `create_if_missing`**：与原 13 个副本一致，库不存在时由 `init_story_db` 负责创建，
     不该悄悄建出一个空库
   - `init_story_db` 也会把自己登记的池放进缓存，避免同一文件开两个池
5. 拆出 `open_story_pool_at(path)` 便于测试直接传临时路径（同 §10.48 的思路）。

#### 测试（新增 6 项，共 159）

| 测试 | 作用 |
|---|---|
| `reuses_pool_for_same_path` | 同路径两次打开**只建 1 个池** |
| `each_path_has_its_own_cache_entry` | 缓存按路径隔离，互不干扰 |
| `clear_cache_forces_rebuild` | 清缓存后确实重建 |
| **`all_migrations_run_regardless_of_entry_point`** | ⭐ 造一个"很老"的库（缺 tags/day_summary/parent_id、缺 expanded 列、缺 branches 表、缺 temporary），打开后断言**全部迁移都补上了** —— 这就是这次统一的核心价值 |
| `missing_file_is_an_error_not_an_empty_db` | 库不存在时报错、不建空文件 |
| `cache_skips_repeated_migrations` | 60 次打开实测：**每次重跑迁移 386 ms → 走缓存 98 ms（3.9×）** |

**量化洞察**：`SqlitePool::connect_with` 本身是**懒的**（`min_connections` 默认 0），
所以"建池"并不贵；**贵的是每次都要重跑一遍迁移探测**（若干 `PRAGMA table_info`）。
缓存真正省掉的是这个。

#### 测试自身的三个坑（都踩了，都记下来）

1. **全局计数器在并行测试下不稳定** —— `cargo test` 是并行的，别的测试也在建池，
   断言"第一次只建 1 个池"实测得到 4。→ 改成**按路径计数**。
2. **`pool_cache_len()` 的绝对值不可断言** —— 同样被并行测试干扰。→ 改成按路径断言。
3. **`clear_pool_cache()` 一度会 `close()` 掉别的测试正在用的池** —— 造成随机失败。
   → 改为**只从缓存移除、不主动 close**（池在最后一个克隆 drop 时自然关闭）。

最终给池测试加了**串行锁**（它们操作的是同一份全局缓存）。

#### 顺带清理

删掉 13 个文件里因此不再需要的导入（39 条）。
第一次清理时**我把整行删了**，而警告只指向组导入里的**一项**（如
`use sqlx::sqlite::{SqliteConnectOptions, SqlitePool};`）—— 把 `SqlitePool` 也删掉了，
导致 14 个编译错误。后来改成**只删那一项**（剩 1 项时简化为单项导入）才对。

### 10.54 回滚报 `UNIQUE constraint failed: characters.id` —— 快照没按分支隔离（2026-10-17）

用户点「回滚到此版本」后报错：

```
❌ error returned from database: (code: 1555) UNIQUE constraint failed: characters.id
```

#### 真实数据长什么样（这是关键）

| 表 | 主线行 | 分支行 |
|---|---|---|
| characters | 3 行（id 2/3/4） | 3 行（id **27/28/29**） |
| relations | 0 | 3 行（id 34/35/36） |
| world_settings | 0 | 7 行（id 67~73） |

而快照 `V22`（主线）的 payload 里**装了全部 6 个角色**（`2,3,4,27,28,29`）。

#### 为什么会撞

| 步骤 | 行为 |
|---|---|
| `make_snapshot` | 读**全表**（`SELECT ... FROM characters ORDER BY id`，**没有分支过滤**） |
| `rollback_snapshot` | 只删**当前分支**的行（`WHERE branch_id IS NULL`）→ 删掉 2,3,4 |
| 插入 | 把 payload 里 6 条**按原 id** 插回去 → 27/28/29 还躺在分支里 → **主键冲突** |

一句话：**快照的读取范围（全表）与回滚的删除范围（单分支）不一致。**

> 这是第五批 ③ 分支系统留下的漏洞：当时把"删除"改成按分支，
> 但**没有同步**把"快照读取"也改成按分支。

#### 修法（三层）

| 层 | 改动 |
|---|---|
| **快照** | `make_snapshot` 三条查询都按分支过滤 → 快照语义变成"**这条分支当时的设定**" |
| **预览** | `preview_snapshot` 读"当前设定"也按同一分支过滤 → 否则快照里只有本分支、当前读全表，别的分支的行会被误报成"回滚将删除" |
| **回滚（兜底）** | 老快照 payload 里混着**别的分支**的行 → 这些行 **跳过**（它们本就不该被这次回滚改动，而且 id 还占着）。同分支残留（删除没覆盖到的异常）→ 交给自增，**宁可换 id 也不让整个回滚失败** |

顺带把回滚的后半段抽成 `restore_settings_from_payload(pool, branch, payload)` ——
原来这段逻辑在 `rollback_snapshot` 里，而该函数自己按 story_id 开池，**单测进不去**。
抽出来才能把这次的主键冲突真正测住。

#### 测试（新增 3 项，共 168）

| 测试 | 断言 |
|---|---|
| `snapshot_payload_is_branch_scoped` | 主线快照只含 `[2,3,4]`；分支快照只含 `[27,28,29]` |
| **`rollback_skips_rows_belonging_to_other_branch`** | 手搓一个"老格式"快照（6 条全塞）→ 回滚**不报错**，主线恢复成 3 个、分支 3 个原样保留 |
| `rollback_falls_back_to_autoincrement_when_id_taken` | id 被占时退化为自增，不报错 |

**回归测试有效性已验证**：把修复临时关掉后，前两个测试立刻报出
`(code: 1555) UNIQUE constraint failed: characters.id` —— **与用户看到的错误一字不差**；恢复后全过。

#### 真实库副本复验

诊断测试里加了一步"回滚到最新版本（老格式，含分支行）"：

```
✅ 回滚到 V18：已回滚到快照 V18：…
角色总数 6 → 6（主线 3 + 分支 3）
```

修复前这一步必然失败；现在成功且**分支数据完好**。

#### 教训

> 当"读取范围"和"写入/删除范围"分开实现时，**两者必须同时按同一个维度过滤**。
> 第五批 ③ 只改了删除那一侧，就埋下了这个雷 —— 而且它只在"存在分支"的数据上才会炸，
> 单分支/无分支的开发环境**永远测不出来**。
### 10.55 修 Q7（补摘要跨分支）+ 回滚加事务（2026-10-17）

两件都是在核对 RAG 规划稿时顺带挖出来的，**同一类病根**：读取范围与实际作用范围不一致。

#### ① Q7：补摘要会挑到兄弟分支的节点

`timeline.rs select_nodes_needing_summary` 原来：

```rust
SELECT id, date_label, sort_order, is_flashback, COALESCE(day_summary,'')
FROM timeline_nodes ORDER BY sort_order ASC, id ASC      // 全表，没有分支过滤
```

再按**全表位置**判断"是否在当前节点之前"。在分支故事里后果：

- 挑到**兄弟分支**的节点 → 花用户的 API 钱去给不在的那条线生成摘要（并写进该分支数据）
- 漏掉当前分支上全表位置靠后的节点

修法：先用现成的 `branch_path_ids(pool, branch)`（= 本分支节点 ∪ 沿父链共享历史）限定范围，
再在该范围内按 `sort_order, id` 判断"之前"。主线行为不变。

测试（2 项，已验证有效性）：把过滤关掉后，测试立刻报
`不该选中主线独有的第 3 天（那是兄弟分支的节点）：[(1,"第1天"),(2,"第2天"),(3,"第3天"),(4,"第3天")]`。

#### ② 回滚没有事务 —— 失败会留下删了一半的库

`rollback_snapshot` 的顺序原来是：**删角色 → 删关系 → 删世界观 → 逐条插回**，
**全程没有事务**。于是：

> 用户实机点回滚 → 插角色时撞主键（1555）报错 → **关系与世界观已经被删、再也没插回来**。
> 表现就是"主线突然没有关系和世界观了"。

（这次用户的数据后来被别的操作补回来了，但**差点真丢**。）

修法：把"删三张表 + 逐条插回"包进同一个事务，全成则提交，任一步失败**整体回退**。

为了能测住这件事，把回滚拆成 `rollback_snapshot_in(pool, story_id, version, branch, backup_note)`
—— 原来它自己按 `story_id` 开池，**单测进不去**，所以"删了一半"这种事故没有任何测试拦得住。

测试（2 项，已验证有效性）：去掉事务后，`failed_rollback_keeps_previous_state` 立刻报
"**回滚失败后三张表必须原样还在**（之前会留下删了一半的库）"。

#### 教训（本项目第二次栽在同一处）

| 事故 | 读的范围 | 写/删的范围 |
|---|---|---|
| 回滚 1555（§10.54） | 快照读**全表** | 只删**当前分支** |
| Q7 补摘要（本节） | 读**全表**判断位置 | 实际只应看**本分支可见范围** |

> **凡涉及分支的表，读、写、删三处必须用同一个范围口径。**
> 而且这类 bug **在无分支的数据上永远不会暴露** —— 必须在"有兄弟分支"的测试数据上才测得出来。

#### 附带说明：用户问的"主线没有关系/世界观"

查证结论：**当前数据是好的**（主线 3 关系 + 7 世界观，分支同样 3 + 7）。
我看到"主线 0 条"是因为**恰好采集在回滚失败的中间状态**（正是上面第 ② 条那个 bug）。
不是原始数据问题，也不需要恢复操作。

### 10.57 RAG ① 修正：回顾注入**当天原始对话**，不是摘要（2026-10-17 用户实测反馈）

- 【前情提要】里**本来就全是摘要** —— 再塞一条摘要等于没回顾；

| 环节 | 用什么 |

| 注入（喂给模型） | **当天全部原始消息**（`messages` 表，`strip_director` 剥掉导演标记） |

```text
【相关旧日记忆】（根据本次提问恢复的**当时原始对话**，用于回应「那次/当时/还记得」；以此为准，不要改写）
```

### 10.61 时间线页两个真问题（用户拆分验收时发现，2026-10-17）

#### ① 树状图的两个按钮"点了没反应"

用户反馈：「全部展开」和「只留主线（收起分叉）」点击无反应。

**先查数据再改代码** —— 查真实库副本发现：

| 检查项 | 结果 |
|---|---|
| 该故事的时间线 | **10 个节点，纯单链**（每个节点只有 1 个子节点） |
| 「分叉点」（子节点 >1） | **0 个** |

于是两个按钮都在**空转**：

- 「全部展开」= 清空折叠集合，而它**本来就是空的** → 没有变化
- 「只留主线」= 只收起分叉点，而**一个分叉都没有** → 没有变化

**不是拆分拆坏的，是这两个按钮从来没有"禁用态"** —— 在无分叉的故事上看着就像坏了。

修法：

1. 新增「**全部收起**」：收起所有含子节点的行，只留根节点 —— 长线也能一屏放下
2. 「全部展开」：`collapsedCount === 0` 时禁用（title：当前已经是全部展开）
3. 「只留主线」：`forkCount === 0` 时禁用（title：这条线上没有分叉点，无需收起）
4. 无分叉时在按钮后面补一句灰字：**（线性时间线，没有分叉；可用「全部收起」折叠长列表）**

#### ② 「插入事件」不知道有两条限制（而且后端真没拦）

用户要求标注：**已经存在的天不能重复创建；只能选区间内的天**。

查后端 `create_node_at_day_with`：**只校验 `day_no > 0`** ——
也就是说**真的能造出两个「第 5 天」**。这不是"标注一下"就够的，是数据完整性缺口。

修法（三层）：

| 层 | 改动 |
|---|---|
| 弹窗说明 | 常驻一段规则：① 只能选这段空白期内的天（第 X ~ Y 天）；② 已存在的天不能重复创建 |
| 即时校验 | 边输入边判：空 / 非正整数 / 超出区间 / 该天已存在 → 红框显示具体原因；合法时显示「✅ 可以插入」 |
| 提交按钮 | 不合法时**禁用**并给 title |
| 提交函数 | 同样的校验再兜一道（防别的入口绕过） |
| **后端** | `create_node_at_day_with` 加守卫：本分支可见范围内已有该天 → 返回「第 N 天已经存在，不能重复创建」 |

#### 验证

诊断测试（真实库副本）里加了两步：

```
=== 时间线：重复创建同一天 ===
  ✅ 被拒绝：encountered unexpected or invalid data: 第 3 天已经存在，不能重复创建
  ✅ 新的一天可以创建：第 99 天
```

#### 教训

> **"按钮没反应"要分两种查：是代码坏了，还是"在当前数据上本来就无事可做"。**
> 这次是后者 —— 但**后者同样是缺陷**：可点击却无效果的按钮会让用户以为功能坏了。
> 正确做法是给出禁用态 + 一句为什么，而不是让它静静地空转。
### 10.62 树状图「收起/展开」无效的真凶：两个数据源（2026-10-17 用户实测）

#### 用户的原话

> "树状图里面的'展开和收起'按钮对于树状图没有影响，
> 影响的是时间线'列表'下的这个显示（时间维区间条）。"

#### 真凶：同一份数据被两处消费，而两个消费方要的是两种东西

App 里原本有 **两个**行构建器：

| 变量 | 是否感知折叠 | 谁在用 |
|---|---|---|
| `treeRows` | ✅ 读 `treeCollapsedRef` | 时间维区间条、列表 |
| `treeRowsAll` | ❌ 纯全量 | **树状图表格** ← 用错了 |

于是：点收起 → 折叠集合变了 → **区间条**跟着变 → **树状图表格用的那份根本不看折叠** → 一动不动。

这不是这次拆分引入的（块是整体搬过去的，原代码就写着 `treeRowsAll`），
但**拆分时把 `treeRowsAll` 一眼看成了"树状图该用的那行"**，没发现它名字的语义是"折叠无关"。

#### 修法：合成一个纯函数，用参数区分两种语义

新增 `src/lib/timelineTree.ts`：

```ts
export function buildTreeRows(
  nodes: TimelineNodeDto[],
  collapsed: ReadonlySet<number> | null,   // null = 折叠无关
): TreeNodeRow[]
```

App 里两个消费方各取所需：

| 消费方 | 用哪个 | 理由 |
|---|---|---|
| **树状图表格** | `buildTreeRows(nodes, treeCollapsedRef.current)` | 收起某节点，它的子孙不该出现 |
| **时间维区间条** | `buildTreeRows(nodes, null)` | 收起后如果日期按钮也消失，用户就没法导航了 |

顺手清掉了：`treeRowsAll`、`forkIds`、`hasFork`、`visibleNodeIds`（都已无消费方）。

#### 测试还抓到一个真 bug：数据成环时树会**完全空白**

`buildTreeRows` 的起点是"没有父节点的那些"。如果数据坏了（例如两个节点互为父），
**没有任何节点算根** → 遍历从空开始 → 返回 0 行 → 界面一片空白。

这个 bug 是写单测时发现的（断言"不死循环"时实际拿到 0 行）。
修法：找不到根但确实有节点时，**把所有节点当根**。
> 空白树比"显示得不对"更难排查 —— 宁可按脏数据画出来，也别什么都不画。

#### 新增 8 项前端测试（共 47）

单链展开 / 收起某节点藏子孙 / `null` 无视折叠 / 分叉点收起 /
父不存在的节点当根 / 成环兜底不全空白 / 同级排序 / 空输入。

#### 顺带：自检的"主窗口已创建"偶发 FAIL

紧跟 `cargo build --release` 之后跑自检时失败过一次（重跑即过）——
磁盘与杀软扫描抢资源（本机安全软件会拦 `app.exe`）。
已加**第二轮重试**（再等最多 9 秒），成功时在报告里注明"第二轮重试才出现"。
连跑 3 次均为 14/14。

#### 教训

> **"有多个消费方的同一份数据"要警惕语义漂移。**
> 这次的两个变量名（`treeRows` / `treeRowsAll`）只差后缀，
> 但一个是"折叠感知"、一个是"折叠无关" —— 名字没把语义说清，就看走眼了。
> 现在合成一个函数、用参数表达语义，并且**写进注释"两个消费方需求不同"**。
### 10.63 `App.tsx` 拆分第三步：立绘素材页（2026-10-17）

最大的一块：**491 行 / 63 个依赖**（26 state + 23 setter + 14 处理函数）。

#### 为什么分两步，而不是一次把 state 也搬走

先量了"这些 state 在块**外**被谁用"：

| state | 块外引用 | 谁在用 |
|---|---|---|
| `portraits` | 12 处 | 立绘页 + 生成参数页 + 素材选择 |
| `pDetail` / `pDraft` / `pSel` … | 2~13 处 | **主要是立绘自己的处理函数**（`doBind`/`doDelete`/`submitPModal`…） |

也就是说：state 和**处理函数**是一伙的，处理函数又住在 App 作用域。
一次性把 state + 处理函数都搬走，要同时改 App 里 40+ 处引用 —— 风险远高于收益。

所以：**这一步只搬视图**（63 个 props 确实多，是过渡态），下一步再把 state + 处理函数搬进去，
那时 props 会缩到个位数。

#### 生成器这一轮又踩了三个坑（都值得记）

| 坑 | 现象 | 修法 |
|---|---|---|
| **泛型里带 `>`** | `useState<Set<number>>` 用 `[^>]*` 捕获 → 只吃到 `Set<number`，整条 props 变 `<Set<number>` 语法错 | 改成贪婪 `useState<(.+)>\(` |
| **模块级导入被当成 props** | `convertFileSrc` / `PORTRAIT_GRADS` 是 App 的 import，不是 App 作用域变量 → 组件里报"找不到" | 解析 App 的 import 表，这类名字在组件里**直接 import**，不进 props |
| **相对路径** | `./constants` 原样抄过去 → 组件在 `views/` 下，少一层 | 统一 `./x` → `../x` |

外加一个老坑的变体：**`<input>` JSX 标签**会被 `\binput\b` 命中，误判成用了 `input` 这个 state。

#### 结果

| 文件 | 行数 |
|---|---|
| `App.tsx` | 5930 → **5504**（-426） |
| `views/PortraitPage.tsx` | **573**（含 61 个 props 类型声明） |

累计：`App.tsx` **6788 → 5504**（-1284，**-18.9%**）。

守卫同步收紧：`APP_MAX_LINES` 6050 → **5600**，并把 `PortraitPage` 纳入"非空壳"检查（≥400 行）。

#### 下一个（把 props 从 61 缩到个位数）

把 26 个 `pXxx` state + 12 个处理函数从 App 搬进 `PortraitPage`：
- `portraits` 的加载与刷新、`doPick`/`submitPModal`/`doBind`/`doDelete`/`doGroupSet`/`doTagBatch`/`doPExport`/`doRoleSave`/`doGenSave`/`regenFromPortrait`/`loadBindChars` 全部内移
- 只保留 `setMsg`（全局提示）、`setView`（跳转）、`stories`（绑定弹窗用）
- App 里其它引用点（生成参数页读 `portraits`、素材选择）改走"传入回调"或提升为共享状态

### 10.64 自检「主窗口已创建」偶发 FAIL 的治理（2026-10-17）

#### 现象

今天约 8 次自检里失败 2 次，**两次都紧跟在 `cargo build --release` 之后**，重跑即过。
报错是"没枚举到 Tauri 主窗口"，但同一轮"进程能启动并保持运行"是 PASS ——
进程活着、窗口没枚举到。本机安全软件会拦 `app.exe` 写入，冷 exe 首启较慢。

#### 我自己先制造了一个 bug

第一版"重试"加在了 FAIL 分支里，但**重试成功判 PASS 之后代码继续往下走**，
又走了一遍枚举 → 同一个检查项会**同时出现 PASS 和 FAIL** 两个结论。
而且我给"耗时统计"插的 `$winSw` 落到了**另一个循环**（等残留进程退出那个）里。

#### 现在的写法

整段重写为单一判定：

```
首轮轮询（20 × 900ms ≈ 18s）
  → 没拿到窗口 → 补一轮重试（10 × 900ms ≈ 9s）
  → 拿到 → PASS，并报出"等待 X.Xs"，超过 18s 时标注"（第二轮重试才出现）"
  → 仍没拿到 → FAIL，报出"等了 X.Xs 仍没枚举到"，附实际窗口列表 + msedgewebview2 进程数
```

#### 老实说：没证明修好了

这个偶发**无法稳定复现**（重建后立刻跑，也有一半概率是过的）。
所以现状是：机制上更合理（单一结论、有时间证据、失败信息更全），
但"再也不 FAIL"**没有被证明**。若再遇到，先看报告里的"等了 X 秒"和窗口列表。
### 10.65 立绘素材页收尾：props 61 → 10（2026-10-17）
