## 四、待细化的核心设计：摘要机制（D1 的延伸）

**目标**：让"更早的日子"以低成本进上下文，同时**不破坏前缀缓存**（上一轮刚建立的「稳定前缀 + 易变尾部」原则不能自己破坏）。

### 可选路线（三选一，待定）

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地规则摘要**（现成） | 每条消息已有 `abs` 一句话摘要，按天拼接 | 零成本、零延迟 | 机械、丢因果，只适合当"目录" |
| **B. AI 逐日摘要** | 每天剧情结束后，用一次小请求生成"这一天发生了什么"（≤N 字） | 质量好、可读 | 每天一次额外调用 |
| **C. 分层摘要**（A+B） | 每天一条日摘要（B）+ 若干天滚成"阶段摘要" | 可容纳整部长篇 | 实现最复杂 |

### 必须遵守的三条规则（无论选哪条）

1. **生成一次就固化**：摘要生成后写库，**绝不每轮重算** —— 否则前缀每轮都变，缓存全灭。
2. **只追加、不回改**：新的一天完成 → 追加一条日摘要；阶段摘要只"追加新覆盖的天"，不改写旧文字。这样历史段仍然满足"只追加"的缓存特性。
3. **存放位置**：摘要属于**稳定前缀**（进 system 的【前情提要】段，`【】` 段落便于「生成参数」预览分区），近期三天仍是 messages 里的原文（role 结构保留）。

### 建议的数据落点

- 日摘要：`timeline_nodes` 加一列（如 `day_summary`）或在 `messages` 的 `abs` 基础上聚合 —— 需要定
- 阶段摘要：新表（如 `story_summaries`，按覆盖的天数区间存）—— 需要定

### 6.2 子项 B：跨天历史装配（核心）—— ✅ 已实现（2026-10-11，待用户验收）

#### 6.2.1 动态 N 值公式（已拍板，替换原"固定 10 条"）

**核心思想**：把"每天 10 条"降级为**理想目标**，实际每天取多少条由**模型窗口 + token 预算**动态分配得出。

**用户 2026-10-11 修订：不要把 N 写死，N 必须由「历史可用预算」倒推。**

```
① 历史可用预算
   = 窗口 × 安全系数(默认 0.8；用户决定保留 —— 各项占用虽已显式扣除，仍留 20% 防止软件异常导致爆上下文)
     − 回复预留（max_tokens 4000 + 安全余量 800）
     − 固定区（实测：基础指令 + 输出排版 + 数据字典 + 世界观 + 角色 + 方向和关系）
     − 摘要区（实测：【前情提要】已生成的日摘要 —— 会随天数增长，不能当固定成本）
     − 尾部块（上下文更新块）
     − 本次输入（预估）

② 每日基准预算 = 历史可用预算 ÷ 保留天数（KEEP_DAYS = 3）

③ 实际 N = 每日基准预算 ÷ 单条消息平均 token
   （单条均 token 由近三天真实消息长度算出；N 再受「每日上限 n_recent」与「当天实际条数」约束）

④ 阶梯式降级（最终落地）
   第一阶梯 封顶    ：N = min(倒推 N, 用户每日上限（默认 10）, 当天实际条数)
   第二阶梯 强制降级：三天总量超预算时，从最老的一天开始把该天踢出原文区、转【前情提要】摘要块
   第三阶梯 继续降 N：仍超预算 → N 逐条递减（下限 1，保证当天仍有上下文）
   第四阶梯 兜底    ：摘要区本身放不下 → 从最旧的摘要开始丢弃（保证最近的记忆一定在）并提示
```

**说明**：固定区与摘要区都取「本次实际要发出去的内容」的 token 估算，而不是写死的常数 ——
写死会在加角色 / 加世界观 / 天数变多时算错（N 偏大 → 实际超窗）。

**踢出顺序（已拍板）**：`算出 N → 封顶 → 三天总量超预算则 Day-3 转摘要 → 仍超则继续降 N → 极端情况 N=0 只带摘要 + 本次输入`。
**每一步都要重新校验**：摘要区本身也占预算（摘要区 = 稳定前缀的一部分，随天数增长，因此也要纳入 ① 的"系统段占用"里一起算）。

| 序号 | 改动 | 涉及 |
|---|---|---|
| B1 | `timeline_nodes` 加列 `day_summary`（幂等补列），日摘要落在这里（**Q7 方案 1**） | `story_db.rs`（ensure 函数）、`timeline.rs` |
| B2 | 新增命令：**生成某节点的日摘要**（一天剧情收尾时调用，≤N 字；生成一次即固化；提示词只写事实：谁做了什么 / 关系变化 / 未回收伏笔，不写感想不写台词） | `lib.rs`、`timeline.rs`、提示词常量 |

实现要点（与设计一致）：

- 每日条数 = `min(理想 N, 用户上限 n_recent, 当天实际条数)`，理想 N 由 `plan_day_limits` 纯函数算出（含"每天至少 1 条"兜底）

### 8.4 一键替换的技术形态（定稿：结构化补丁 + 软件校验执行）

**不使用真正的 tool calling**（那需要额外往返，且等于让模型直接写库）。改为让 AI 输出**约定的 JSON 补丁**，软件**先校验、再二次确认、后执行**：

```json
{
  "has_issue": true,
  "problems": [
    { "where": "夏婉琴", "field": "人物小传", "kind": "歧义",
      "why": "同一段里“她/他”混用，指代不清", "suggestion": "统一为“她”" }
  ],
  "patch": [
    { "board": "characters", "target_kind": "character", "target_name": "夏婉琴",
      "field": "profile", "value": "（改好的完整文本）" }
  ]
}
```

| 环节 | 规则 |
|---|---|
| 执行范围 | **只执行 patch 列出的字段**（局部覆盖，绝不整表重写） |
| 执行前校验 | ① 板块与 `target_name` 必须存在；② `field` 必须在**白名单**内（防止 AI 改 id / created_at 等）；③ 关系条目用 `from/to` 定位 |
| 二次确认 | 弹"将要修改 N 条"的清单（含**改动前 → 改动后**对照），确认后才写库 |
| 可回滚 | 执行前自动打快照（复用演进模块的 `make_snapshot`） |
| 降级 | AI 返回的 JSON 不合法 → 只显示只读报告，**不执行任何修改** |

### 8.11 五轮加固（2026-10-11）：用数据库判定「这个名字是谁」

| 加固 | 内容 |
|---|---|
| **按库反查改判** | 新增 `resolve_target(pool, patch)`：名字带箭头 → `(characters, relation)`；名字能在 `characters.name` 找到 → `(characters, character)`；能在 `world_settings.key` 找到 → `(world, world_entry)`；都查不到才保留原样（后续给人文拒绝）。`validate_patch` 因此改为 **async + 池参数**：先反查改判、再归一化字段 |

共 **34 项单测**全过（含真实临时库端到端测试）。

### 8.12 六轮加固（2026-10-11）：以角色名定位，字段由软件反查

用户提出关键判断（并拍板）：

> 「既然我们需要的是 AI 的判断内容本身，那就**只取 AI 的判断内容 + 必需的角色名**，
> 然后由**软件**根据角色名去改对应内容 —— 先看角色名，再看角色管理里的那几个字段。」

这条判断完全正确，而且指出了前几轮一直没解决的**根本矛盾**：

| 矛盾 | 说明 |
|---|---|
| 模型**不知道**"这段文字在数据库的哪个字段里" | 给它的板块内容是各字段拼成的 JSON，它只看到内容：`"女主，身材瘦小纤细，身高154cm"` 到底属于 `one_liner` 还是 `profile`，它无从判断 |
| 于是它随口猜字段名 | 猜成 `profile` → 与库中现值对不上 → 被 before 核对拒绝。实测报错即为：「夏婉琴」的 `profile` 当前值是「」，但 AI 以为它是「女主，身材瘦小纤细，身高154cm」（**那段其实在 `one_liner` 里**） |

**修法（本轮实现）**：

| 机制 | 内容 |
|---|---|
| **`resolve_field`（按内容反查字段）** | 拿 AI 声明的 `before` 去比对该条目**各个可改字段的真实值**：完全相等优先；否则取"互为包含"的字段；多个命中取**更长更具体**的那个；都对不上则不猜（保留原字段，交给 before 核对报错） |
| 校验顺序 | ① 按库反查板块/类型（8.11）→ ② 归一化字段名 → ③ **按当前值反查真实字段** → ④ before 核对 → ⑤ 执行 |
| 提示词放宽 | 明确告诉 AI："字段名写不准没关系，软件会按你对条目的判断定位正确字段；只要**条目名准确**、`value` 是**改好后的完整文本**" |
| 结果可追溯 | 执行结果里带上"实际的板块 / 类型 / 字段"（可能已被软件改判）；二次确认框在字段名不可识别时标注"（字段名由软件按内容自动定位）" |

**新增测试** `field_is_resolved_from_current_value`：造 `one_liner` 有值、`profile` 为空的角色，
AI 声称改 `profile` 但给的当前值来自 `one_liner` → 应改判为 `one_liner`，执行后**只有 `one_liner` 被改、`profile` 仍为空**；
before 与任何字段都对不上时**不改判**。共 **35 项单测**全过。
