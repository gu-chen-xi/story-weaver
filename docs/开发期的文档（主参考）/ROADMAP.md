## 四、待细化的核心设计：摘要机制（D1 的延伸）

**目标**：让"更早的日子"以低成本进上下文，同时**不破坏前缀缓存**（上一轮刚建立的「稳定前缀 + 易变尾部」原则不能自己破坏）。

### 可选路线（三选一，待定）

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地规则摘要**（现成） | 每条消息已有 `abs` 一句话摘要，按天拼接 | 零成本、零延迟 | 机械、丢因果，只适合当"目录" |
| **B. AI 逐日摘要** | 每天剧情结束后，用一次小请求生成"这一天发生了什么"（≤N 字） | 质量好、可读 | 每天一次额外调用 |
| **C. 分层摘要**（A+B） | 每天一条日摘要（B）+ 若干天滚成"阶段摘要" | 可容纳整部长篇 | 实现最复杂 |

### 必须遵守的三条规则（无论选哪条）

1. **生成一次就固化**：摘要生成后写库，**绝不每轮重算** —— 否则前缀每轮都变，缓存全灭。
2. **只追加、不回改**：新的一天完成 → 追加一条日摘要；阶段摘要只"追加新覆盖的天"，不改写旧文字。这样历史段仍然满足"只追加"的缓存特性。
3. **存放位置**：摘要属于**稳定前缀**（进 system 的【前情提要】段，`【】` 段落便于「生成参数」预览分区），近期三天仍是 messages 里的原文（role 结构保留）。

### 建议的数据落点

- 日摘要：`timeline_nodes` 加一列（如 `day_summary`）或在 `messages` 的 `abs` 基础上聚合 —— 需要定
- 阶段摘要：新表（如 `story_summaries`，按覆盖的天数区间存）—— 需要定

### 6.2 子项 B：跨天历史装配（核心）—— ✅ 已实现（2026-10-11，待用户验收）

#### 6.2.1 动态 N 值公式（已拍板，替换原"固定 10 条"）

**核心思想**：把"每天 10 条"降级为**理想目标**，实际每天取多少条由**模型窗口 + token 预算**动态分配得出。

**用户 2026-10-11 修订：不要把 N 写死，N 必须由「历史可用预算」倒推。**

```
① 历史可用预算
   = 窗口 × 安全系数(默认 0.8；用户决定保留 —— 各项占用虽已显式扣除，仍留 20% 防止软件异常导致爆上下文)
     − 回复预留（max_tokens 4000 + 安全余量 800）
     − 固定区（实测：基础指令 + 输出排版 + 数据字典 + 世界观 + 角色 + 方向和关系）
     − 摘要区（实测：【前情提要】已生成的日摘要 —— 会随天数增长，不能当固定成本）
     − 尾部块（上下文更新块）
     − 本次输入（预估）

② 每日基准预算 = 历史可用预算 ÷ 保留天数（KEEP_DAYS = 3）

③ 实际 N = 每日基准预算 ÷ 单条消息平均 token
   （单条均 token 由近三天真实消息长度算出；N 再受「每日上限 n_recent」与「当天实际条数」约束）

④ 阶梯式降级（最终落地）
   第一阶梯 封顶    ：N = min(倒推 N, 用户每日上限（默认 10）, 当天实际条数)
   第二阶梯 强制降级：三天总量超预算时，从最老的一天开始把该天踢出原文区、转【前情提要】摘要块
   第三阶梯 继续降 N：仍超预算 → N 逐条递减（下限 1，保证当天仍有上下文）
   第四阶梯 兜底    ：摘要区本身放不下 → 从最旧的摘要开始丢弃（保证最近的记忆一定在）并提示
```

**说明**：固定区与摘要区都取「本次实际要发出去的内容」的 token 估算，而不是写死的常数 ——
写死会在加角色 / 加世界观 / 天数变多时算错（N 偏大 → 实际超窗）。

**踢出顺序（已拍板）**：`算出 N → 封顶 → 三天总量超预算则 Day-3 转摘要 → 仍超则继续降 N → 极端情况 N=0 只带摘要 + 本次输入`。
**每一步都要重新校验**：摘要区本身也占预算（摘要区 = 稳定前缀的一部分，随天数增长，因此也要纳入 ① 的"系统段占用"里一起算）。

| 序号 | 改动 | 涉及 |
|---|---|---|
| B1 | `timeline_nodes` 加列 `day_summary`（幂等补列），日摘要落在这里（**Q7 方案 1**） | `story_db.rs`（ensure 函数）、`timeline.rs` |
| B2 | 新增命令：**生成某节点的日摘要**（一天剧情收尾时调用，≤N 字；生成一次即固化；提示词只写事实：谁做了什么 / 关系变化 / 未回收伏笔，不写感想不写台词） | `lib.rs`、`timeline.rs`、提示词常量 |
| B3 | 历史装配：**当前节点 + 前 2 个 day 节点**（按节点数）取 role 原文，各自按 §6.2.1 的 N 取值；更早的 day 节点取 `day_summary` | `generate_stream.rs` |
| B4 | 摘要注入 system 的 **【前情提要】** 段：**只追加、不回改**（保证"稳定前缀"成立） | `generate_stream.rs`、`relations.rs`（如需文案） |
| B5 | 触发点：切换节点时 / 回复完成后，为"已有剧情但还没摘要"的节点补摘要（幂等） | `App.tsx` 调用、`lib.rs` |

|---|---|---|---|

| 第 4 天 | 第 2~4 天（8 / 8 / 6） | 22 | 第 1 天 |

实现要点（与设计一致）：
- `KEEP_DAYS = 3`：`当前节点 + 前 2 个天数节点`取原文（插曲/倒叙不算天数）
- 每日条数 = `min(理想 N, 用户上限 n_recent, 当天实际条数)`，理想 N 由 `plan_day_limits` 纯函数算出（含"每天至少 1 条"兜底）
- 两级降级：① 先逐条降 N（下限 1）② 仍超则从**最老的一天**开始整天移出原文区 → 改用它的日摘要
- 【前情提要】追加在 system 末尾；**关闭「记忆上下文」开关时不带历史、也不带摘要**

| 风险 | 应对 |
