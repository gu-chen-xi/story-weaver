## 四、待细化的核心设计：摘要机制（D1 的延伸）

**目标**：让"更早的日子"以低成本进上下文，同时**不破坏前缀缓存**（上一轮刚建立的「稳定前缀 + 易变尾部」原则不能自己破坏）。

### 可选路线（三选一，待定）

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本地规则摘要**（现成） | 每条消息已有 `abs` 一句话摘要，按天拼接 | 零成本、零延迟 | 机械、丢因果，只适合当"目录" |
| **B. AI 逐日摘要** | 每天剧情结束后，用一次小请求生成"这一天发生了什么"（≤N 字） | 质量好、可读 | 每天一次额外调用 |
| **C. 分层摘要**（A+B） | 每天一条日摘要（B）+ 若干天滚成"阶段摘要" | 可容纳整部长篇 | 实现最复杂 |

### 必须遵守的三条规则（无论选哪条）

1. **生成一次就固化**：摘要生成后写库，**绝不每轮重算** —— 否则前缀每轮都变，缓存全灭。
2. **只追加、不回改**：新的一天完成 → 追加一条日摘要；阶段摘要只"追加新覆盖的天"，不改写旧文字。这样历史段仍然满足"只追加"的缓存特性。
3. **存放位置**：摘要属于**稳定前缀**（进 system 的【前情提要】段，`【】` 段落便于「生成参数」预览分区），近期三天仍是 messages 里的原文（role 结构保留）。

### 建议的数据落点

- 日摘要：`timeline_nodes` 加一列（如 `day_summary`）或在 `messages` 的 `abs` 基础上聚合 —— 需要定
- 阶段摘要：新表（如 `story_summaries`，按覆盖的天数区间存）—— 需要定

### 6.2 子项 B：跨天历史装配（核心）—— ✅ 已实现（2026-10-11，待用户验收）

#### 6.2.1 动态 N 值公式（已拍板，替换原"固定 10 条"）

**核心思想**：把"每天 10 条"降级为**理想目标**，实际每天取多少条由**模型窗口 + token 预算**动态分配得出。

**用户 2026-10-11 修订：不要把 N 写死，N 必须由「历史可用预算」倒推。**

```
① 历史可用预算
   = 窗口 × 安全系数(默认 0.8；用户决定保留 —— 各项占用虽已显式扣除，仍留 20% 防止软件异常导致爆上下文)
     − 回复预留（max_tokens 4000 + 安全余量 800）
     − 固定区（实测：基础指令 + 输出排版 + 数据字典 + 世界观 + 角色 + 方向和关系）
     − 摘要区（实测：【前情提要】已生成的日摘要 —— 会随天数增长，不能当固定成本）
     − 尾部块（上下文更新块）
     − 本次输入（预估）

② 每日基准预算 = 历史可用预算 ÷ 保留天数（KEEP_DAYS = 3）

③ 实际 N = 每日基准预算 ÷ 单条消息平均 token
   （单条均 token 由近三天真实消息长度算出；N 再受「每日上限 n_recent」与「当天实际条数」约束）

④ 阶梯式降级（最终落地）
   第一阶梯 封顶    ：N = min(倒推 N, 用户每日上限（默认 10）, 当天实际条数)
   第二阶梯 强制降级：三天总量超预算时，从最老的一天开始把该天踢出原文区、转【前情提要】摘要块
   第三阶梯 继续降 N：仍超预算 → N 逐条递减（下限 1，保证当天仍有上下文）
   第四阶梯 兜底    ：摘要区本身放不下 → 从最旧的摘要开始丢弃（保证最近的记忆一定在）并提示
```

**说明**：固定区与摘要区都取「本次实际要发出去的内容」的 token 估算，而不是写死的常数 ——
写死会在加角色 / 加世界观 / 天数变多时算错（N 偏大 → 实际超窗）。

**踢出顺序（已拍板）**：`算出 N → 封顶 → 三天总量超预算则 Day-3 转摘要 → 仍超则继续降 N → 极端情况 N=0 只带摘要 + 本次输入`。
**每一步都要重新校验**：摘要区本身也占预算（摘要区 = 稳定前缀的一部分，随天数增长，因此也要纳入 ① 的"系统段占用"里一起算）。

| B1 | `timeline_nodes` 加列 `day_summary`（幂等补列），日摘要落在这里（**Q7 方案 1**） | `story_db.rs`（ensure 函数）、`timeline.rs` |

实现要点（与设计一致）：
- `KEEP_DAYS = 3`：`当前节点 + 前 2 个天数节点`取原文（插曲/倒叙不算天数）
- 每日条数 = `min(理想 N, 用户上限 n_recent, 当天实际条数)`，理想 N 由 `plan_day_limits` 纯函数算出（含"每天至少 1 条"兜底）

- 【前情提要】追加在 system 末尾；**关闭「记忆上下文」开关时不带历史、也不带摘要**
- **天数标记**：每天实际保留的首条消息前加一行 `【第 N 天】`（用户 2026-10-11 追加要求），抽成纯函数 `mark_days` 并加单测（每天恰好 1 个标记、落在实际保留的首条、被跳过的天不产生标记）
- 快照新增 `day_window` / `day_n` 两列，界面可看到"保留几天 × 每天上限几条"

**说明（用户 2026-10-11 决定）**：不再把"前缀缓存"当作设计约束 —— 摘要段每轮从库里现读现拼，
优先"简单、好算、好调"；因此本子项**没有**做"只追加不回改"的强约束测试。

### 8.4 一键替换的技术形态（定稿：结构化补丁 + 软件校验执行）

**不使用真正的 tool calling**（那需要额外往返，且等于让模型直接写库）。改为让 AI 输出**约定的 JSON 补丁**，软件**先校验、再二次确认、后执行**：

```json
{
  "has_issue": true,
  "problems": [
    { "where": "夏婉琴", "field": "人物小传", "kind": "歧义",
      "why": "同一段里“她/他”混用，指代不清", "suggestion": "统一为“她”" }
  ],
  "patch": [
    { "board": "characters", "target_kind": "character", "target_name": "夏婉琴",
      "field": "profile", "value": "（改好的完整文本）" }
  ]
}
```

| 环节 | 规则 |
|---|---|
| 执行范围 | **只执行 patch 列出的字段**（局部覆盖，绝不整表重写） |
| 执行前校验 | ① 板块与 `target_name` 必须存在；② `field` 必须在**白名单**内（防止 AI 改 id / created_at 等）；③ 关系条目用 `from/to` 定位 |
| 二次确认 | 弹"将要修改 N 条"的清单（含**改动前 → 改动后**对照），确认后才写库 |
| 可回滚 | 执行前自动打快照（复用演进模块的 `make_snapshot`） |
| 降级 | AI 返回的 JSON 不合法 → 只显示只读报告，**不执行任何修改** |

但模型**仍会**把关系数值写成世界字段 `scale`、把类型写成 `faction_relation`。结论：**不能只靠提示词约束模型**，
软件侧必须硬拦。本轮三处加固：

| 加固 | 内容 |
|---|---|
| **一板一提示词** | `check_system_prompt` 拆成两套完全独立的模板：角色板块模板里**只出现角色/关系字段名的白名单**，世界板块模板里只出现世界字段名 —— 从提示词层面消除"串字段"的可能（原实现是把两套字段拼在一个示例里） |
| **字段硬闸门** | `field_allowed` 明确为**数据库真实列白名单**；命中不了就由 `field_reject_reason` 给出人话原因（并列出该板块允许的字段），**绝不放行到 SQL** —— 从根上消灭 `no such column`；同时把世界板块的 `key`（名称）移出可改范围 |
| **逐条勾选** | 「可一键替换」清单每行加勾选框（默认全选）+ 全选 / 全不选 + 计数；二次确认与执行**只针对勾选项**；补丁里若出现未知字段，弹窗内提前红字警告（这批不会被放行） |

新增 1 项单测（错字段被拒且原因可读），`fieldLabel` 改为**以 patch 自带的 `board` 为准**（不再靠 `target_kind` 猜），

### 8.10 四轮加固（2026-10-11）：字段名归一化 + SQL 类型安全

用户继续验收，暴露两个新问题（报错已能自解释，说明前面的闸门生效了）：

| 问题 | 报错 | 根因 | 修法 |
|---|---|---|---|
| ① 板次/字段名不对 | `第 1 条补丁看起来是角色关系（宸熙→院长 · value），却标成了世界板块条目` | 模型把"关系数值"写成**泛化词** `value`，还把板块标成 `world` | ① **板块自动改判**：名字带箭头或字段是关系字段 → 自动从 world 改判为 characters；② **字段名归一化**（`normalize_field`，上下文感知）：泛化词 `value`/`内容`/`值` 在**关系语境 → strength**、角色语境 → profile、世界语境 → value；中文别名 `数值`/`强度`/`关系数值` → strength、`人物小传` → profile、`说话方式` → speech_style…；③ 只对**泛化词**兜底，`scale` 这类"明确属于别的板块"的字段仍然拒绝（不猜） |

### 8.11 五轮加固（2026-10-11）：用数据库判定「这个名字是谁」

用户反馈数值已能替换成功，但**文本改动**仍失败：`找不到条目「宸熙」（world_entry）` ——
模型把**角色**的小传改动标成了「世界板块条目」（此前的改判只覆盖「关系」，没覆盖「角色名」）。

| 加固 | 内容 |
|---|---|
| **按库反查改判** | 新增 `resolve_target(pool, patch)`：名字带箭头 → `(characters, relation)`；名字能在 `characters.name` 找到 → `(characters, character)`；能在 `world_settings.key` 找到 → `(world, world_entry)`；都查不到才保留原样（后续给人文拒绝）。`validate_patch` 因此改为 **async + 池参数**：先反查改判、再归一化字段 |
| 理由 | 名字是**唯一可靠的线索**（模型对板块/类型的判断经常出错），而「数据库里有没有这个名字」是确定事实 |

应改判为角色补丁、字段「内容」落地为 `profile`，执行后**小传确实写入 characters 表**；真正的世界条目仍走世界板块。
共 **34 项单测**全过（含真实临时库端到端测试）。

### 8.12 六轮加固（2026-10-11）：以角色名定位，字段由软件反查

用户提出关键判断（并拍板）：

> 「既然我们需要的是 AI 的判断内容本身，那就**只取 AI 的判断内容 + 必需的角色名**，
> 然后由**软件**根据角色名去改对应内容 —— 先看角色名，再看角色管理里的那几个字段。」

这条判断完全正确，而且指出了前几轮一直没解决的**根本矛盾**：

| 矛盾 | 说明 |
|---|---|
| 模型**不知道**"这段文字在数据库的哪个字段里" | 给它的板块内容是各字段拼成的 JSON，它只看到内容：`"女主，身材瘦小纤细，身高154cm"` 到底属于 `one_liner` 还是 `profile`，它无从判断 |
| 于是它随口猜字段名 | 猜成 `profile` → 与库中现值对不上 → 被 before 核对拒绝。实测报错即为：「夏婉琴」的 `profile` 当前值是「」，但 AI 以为它是「女主，身材瘦小纤细，身高154cm」（**那段其实在 `one_liner` 里**） |

**修法（本轮实现）**：

| 机制 | 内容 |
|---|---|
| **`resolve_field`（按内容反查字段）** | 拿 AI 声明的 `before` 去比对该条目**各个可改字段的真实值**：完全相等优先；否则取"互为包含"的字段；多个命中取**更长更具体**的那个；都对不上则不猜（保留原字段，交给 before 核对报错） |
| 校验顺序 | ① 按库反查板块/类型（8.11）→ ② 归一化字段名 → ③ **按当前值反查真实字段** → ④ before 核对 → ⑤ 执行 |
| 提示词放宽 | 明确告诉 AI："字段名写不准没关系，软件会按你对条目的判断定位正确字段；只要**条目名准确**、`value` 是**改好后的完整文本**" |
| 结果可追溯 | 执行结果里带上"实际的板块 / 类型 / 字段"（可能已被软件改判）；二次确认框在字段名不可识别时标注"（字段名由软件按内容自动定位）" |

**新增测试** `field_is_resolved_from_current_value`：造 `one_liner` 有值、`profile` 为空的角色，
AI 声称改 `profile` 但给的当前值来自 `one_liner` → 应改判为 `one_liner`，执行后**只有 `one_liner` 被改、`profile` 仍为空**；
before 与任何字段都对不上时**不改判**。共 **35 项单测**全过。

## 一、依赖链（为什么是这个顺序）

```
① 时间线扩展：节点关系由「线性顺序」改为「树」（parent_id）
        ↓  同一套数据结构
② 快照与回滚增强：按分支隔离的状态快照，可对比、可回滚
        ↓
③ 分支系统（软件原生，只做手动）：节点可分叉，各分支状态互不干扰，可切换回去
        ↓
④ 树状图管理平行故事：①的树长成分叉形态，可视化 + 跳转
```

**关键判断**：`①` 不只是"顺手做个可视化"。**"一个节点可以有多条后继"正是树的数据结构**，
所以 ① 直接按树来做（用 `parent_id`，线性顺序退化为"只有一个子节点"的特例），
到 ③ 时只需加"分叉 + 状态隔离"，**不必再改一遍数据模型**。这是本批最重要的一条技术决策。

## 二、① 时间线扩展：可展开树状图

| 项 | 内容 |
|---|---|
| **数据模型** | `timeline_nodes` 增加 `parent_id`（幂等补列）。现有线性链按 `sort_order` 顺序回填 `parent_id`，老库无感迁移；`sort_order` 保留用于同层排序与向后兼容 |
| **纯函数 + 单测** | `build_tree(nodes)`（线性 → 树）、`flatten_tree(tree)`（树 → 带层级的列表）、`path_to_root(node)`、`branches_of(node)` —— 全部纯函数，配单测（这是分支系统的地基） |
| **UI：树状图** | 时间线页新增「树状」视图：可展开/收起、显示层级缩进与连线、点击节点跳转；**保留现有线性视图**（默认仍是线性，树视图为可切换） |
| **跨天装配兼容** | `KEEP_DAYS` 取"当前节点 → 父链 → 各自的兄弟"这条路径上的近 3 天（现在是"按 sort_order 前 3 个"），改完必须回归：**不分支的故事行为与现在完全一致** |
| **验收** | ① 老库迁移后线性故事行为零变化；② 树视图能正确显示层级与连线；③ 纯函数单测覆盖（含"多子节点""深链""孤立节点"） |

| 项 | 内容 |
|---|---|

## 四、③ 分支系统（软件原生，**只做手动**）

用户定的形态：**按节点来分支；分支之后仍是原来的运行逻辑；两个分支互不干扰各自的独立状态、
角色关系与后续时间线；而且可切换回去。**

| 项 | 内容 |
|---|---|
| **分叉方式** | 在任意节点上「从此处分叉」→ 新建一个子节点作为新分支起点（`parent_id` 指向该节点） |
| **状态隔离** | 每分支独立维护：角色卡与关系数值 / 状态、世界观与术语、演进提案、快照链。实现上沿用 ② 的"快照归属分支" |
| **切换** | 顶部或时间线树可切换"当前所在分支"；切换后对话区/角色管理/世界观/演进提案都跟着切 |
| **不干扰** | 分支 B 的生成**不得**读到分支 A 的后续内容（跨天装配按"路径"取，见 ①） |
| **明确不做** | **不做自动分支**（那属于插件，见第六节）；不做分支合并（先不做，避免数据冲突语义复杂） |
| **验收** | ① 同一节点分出 A/B 后，各写剧情互不影响（可用真实库验证）；② 切回 A 后看到的角色状态与离开时一致；③ 不分支的故事零变化 |

## 八、⑥ RAG：历史回顾与检索（方案已与用户讨论，采用"本地判定优先"）

用户的原始设想：**在提示词里加一句"当用户想回顾某段历史时请回复某某某"，软件接关键字，
把用户输入与找到的历史传回去再输出一次。**

**讨论结论**：流程保留，但**"关键字"不交给 AI 输出** —— 让模型在小说正文里插暗号不可靠
（检查功能六轮加固已证明该模型的结构化输出不稳；暗号会被揉进句子、可能改写或漏掉）。
改为**软件本地判定**：

| 层 | 做法 |
|---|---|
| **第一层：本地规则判定意图** | 输入命中"还记得 / 之前 / 那次 / 第一次 / 上次 / 回顾 / 第 X 天 / 当时"等模式 → 判定为回顾意图（纯规则、可单测、零成本） |
| **第二层：本地检索** | 用输入里的角色名 / 关键词 / 天数去检索：该分支**路径上**的日摘要 + 阶段摘要 + 原文片段，按相关度取 1~2 天摘要 + 3~5 条原文（**预算受控**，不整段塞） |
| **第三层：再跑一次生成** | 组装【历史回顾材料】+ 用户原话，再走一次正常生成；结果照常入时间线，但**标记为"回顾轮"**（不计入日摘要的天数累计） |
| **兜底** | 输入台加「🔍 回顾」按钮：用户自己指哪段就检索哪段（最可靠，不依赖意图识别） |
| **可选增强** | 允许 AI 用**方括号独立行**（如 `【回顾：第 5 天】`）提议回顾 —— 方括号比裸暗号可靠得多（模型已习惯 `[角色名]` 语法）；软件扫到则用它做检索锚点 |
| **验收** | ① 命中规则时能检索出正确片段并组装；② 回顾轮不污染日摘要与天数；③ 不命中时行为与现在完全一致；④ 检索为纯本地函数，可单测 |

### 10.9 第五批 ① 时间线树：数据模型 + 树状视图（2026-10-12 完成）

| 项 | 落地 |
|---|---|
| **数据模型** | `timeline_nodes` 增 `parent_id`（幂等补列）；老库按 `(sort_order, id)` 回填；**每次打开库跑一次幂等补链**（`ensure_parent_links`）—— 关键：新建节点 `parent_id` 为 NULL，只在"首次补列"时回填会让新节点永远没父节点、树碎成孤点 |
| **纯函数** | `children_index` / `path_to_root`（= `ancestor_ids`）/ `flatten_tree` / `branches_of` / `is_fork`，全部无副作用、可单测；另有 `load_tree_nodes` 读树 |
| **跨天装配改为按父链** | `keep_nodes`（近 KEEP_DAYS 天）与 recap（更早的天）都改为"**当前节点的父链上的天数节点**"，不再用"全表位置"。数据异常时**退回原位置算法**，保证不因迁移问题改变生成内容 |
| **界面（形态 A′）** | 并入现有时间线条：有子节点的节点左侧出现 `▸/▾` 展开钮（**默认全部收起**）；展开后子节点带缩进显示；分叉点的节点边框用强调色；`dayNodesSorted()` 同步过滤，日历轨道与"共 N 天"不会与时间线条对不上 |
| **不改的地方** | 保留线性视图作为默认；不新增页面、不新增下拉框 |

**风险与守住的方式（本批最重要的一条）**：跨天装配改按父链，**不分支的故事行为必须与改动前逐项一致**。
用等价性单测钉住：`linear_story_path_equals_positional` 对每个节点分别算"父链法"与"位置法"，
比较 近 KEEP 天 与 recap 两部分结果必须相同（含插曲混排的真实形态）。
另加 `forked_story_path_excludes_other_branch` 证明分支后两条线互不可见。

**实施中发现并修掉的问题**
1. 新建节点无父节点（见上，改为幂等补链）
2. **坐标系混用**：recap 项的排序键一度改成"链上相对下标"，而下游算降级天数时用的是"全表下标"（`earliest_kept`）→ 会算错哪些天的摘要进【前情提要】；已统一为全表下标
3. `earliest_kept` 一度被放进 `if` 分支内部导致作用域错误，已提到分支外

**真机验证**：对真实库（story 7，9 个节点、sort_order 有跳号 5→9→12→15）跑迁移，
父链完整串起（`1→2→3→6→7→12→15→21→29`），`path_to_root` 长度 = 节点数。

**用户实测后修正（同日）**：第一版按"**有子节点就显示 ▸**"实现，结果线性故事里**每个节点都长出一个 ▸**
（线性链上每个节点恰好有 1 个子节点），满屏折叠按钮、还带缩进，横向空间被挤占 —— 纯噪音。
改为按"**这棵树有没有分叉**"（存在任何节点子节点数 > 1）判定：**没有分叉时树控件一律不显示**
（不显示 ▸、不缩进、不留占位、圆角保持原样、日历也不过过滤），外观与改动前完全一致。
**教训：树控件的触发条件应当是"分叉"，而不是"有子节点"** —— 线性链上"有子节点"是常态。
### 10.10 第五批 ② 快照增强（第一项：回滚前的差异预览，2026-10-12 完成）

用户选择"先做 ② 再做 ③"，本轮先做其中最要紧的一项 —— **回滚不再盲操作**。

| 项 | 落地 |
|---|---|
| **问题** | 回滚是**破坏性操作**（现存角色 / 关系 / 世界观被整表替换），原实现只有一句 `confirm("确定回滚吗")`，用户根本不知道会失去什么 |
| **新增命令** | `preview_snapshot(storyId, version) -> SnapshotDiff` |
| **差异结构** | `SnapshotDiff { characters, relations, world_settings }`，每项为 `ItemChange { kind: added/removed/modified, label, fields }`，`modified` 带字段级 `before → after` |
| **纯函数** | `diff_items(before, after, fields, label_of, match_on)` —— 不碰数据库，可单测 |
| **比对字段** | 角色 15 项（**刻意不含 version** —— 内部计数，对用户无意义）、关系 6 项、世界观 4 项 |
| **界面** | 点「回滚到此版本」→ 先弹**差异预览**（分角色卡 / 关系 / 世界观三区，`新增 → 修改 → 删除` 着色，字段显示"当前 → 回滚后"）→ 确认按钮写明"（N 处变更）"；**0 差异时按钮禁用**并提示"完全一致，回滚不会产生任何变化" |

**实施中真机测出并修掉的两个 bug**（都是"看起来像整批设定被换掉"的假象）

1. **快照生成端漏了 `world_settings.id`**：`SELECT key, value, ...` 没选 id → 预览的按 id 对齐全部落空，
   7 条世界观**全被报成"将删除"**。已补 id（并同步调整索引，否则列会读错位）。
   注意：**历史快照的 payload 里仍没有 id**（无法追溯），所以世界观对齐改为按 `key`。
2. **对齐键两边不一致**：当前库的世界观条目有 id、老快照没有 → 一边按 `i:5`、一边按 `k:背景介绍`，
   配不上 → 同一条目**同时出现在"新增"与"删除"里**（新增 7 + 删除 7）。
   根治：对齐键**由调用方显式指定**（`match_on`），不允许函数"聪明地自己挑"。
   角色/关系按 `id`，世界观按 `key`。加 2 项单测锁住这个坑。

**真机验证**（真实库 story 7，15 个快照）
- 修复前：`V15：新增 7 · 修改 4 · 删除 7`（其中 14 处是假象）
- 修复后：`V15：新增 0 · 修改 4 · 删除 0` —— 剩下的 4 处**全是真实差异**
  （用户编辑过角色卡：`说话方式`、`当前状态`、`小传` 各改了内容），正是这个功能要展示的东西

**② 还剩的项**（后续做）：快照归属分支（`branch_id`/`node_id`，为 ③ 的状态隔离铺路）、快照清理策略（保留最近 N 个 + 手动标记保留）。

### 10.12 回滚安全垫：会话内临时版本（2026-10-12 完成，用户定"退出即失效"）

**背景**：回滚是破坏性的（整表替换设定）。用户确认要加"回滚前先自动备份"，但要求
**做成临时的 —— 一旦退出程序就失效**，避免版本列表被自动备份越堆越长。

| 项 | 落地 |
|---|---|
| **表结构** | `setting_snapshots` 加 `temporary`（默认 0）+ `note`（说明文案）两列，幂等迁移；**老库已有版本一律视为永久**（默认 0，不会被清理误删） |
| **回滚前自动备份** | `rollback_snapshot` 入口先调 `make_rollback_backup` 存一个临时版本，note 写明"回滚到 V{n} 前的自动备份（临时，退出程序即清除）"；**备份失败不阻断回滚**（否则"备份不了就永远回滚不了"），但会把情况写进返回文案 |
| **"退出即失效"的实现** | 程序**启动时**遍历 `library/*/projects/*/story.db` 调用 `purge_all_temporary_snapshots`，删掉上一次运行遗留的临时版本（`temporary = 1`）；失败只记日志，绝不阻断启动 |
| **版本号序列** | 临时版本与永久版本**共用同一条 version 序列**（否则回滚时会撞号） |
| **界面** | 列表里临时版本带「⏳ 临时」徽标（橙色边框 + 加粗版本号）+ note 说明；标题行新增「🧹 清理临时版本」按钮；说明文字写明"点错回滚可以用它退回来，但要在关掉软件之前退" |

**测试**（`temporary_snapshot_tests` 4 项，临时文件库）
1. `purge_removes_only_temporary` —— 清理只删临时版本，**永久版本必须原样保留**（最要紧的一条）
2. `migration_marks_existing_snapshots_permanent` —— 老库补列后已有版本视为永久；迁移可重复执行
3. `temporary_versions_share_the_same_sequence` —— 临时版本也占版本号
4. 另在 `rollback_sql_tests` 里覆盖"缺失 id 不许退回 0"

**用户可见的完整流程**
```
点「回滚到此版本」→ 差异预览（会改什么/删什么）
   → 确认回滚 → 自动存一份临时版本（⏳ 临时）→ 整表替换
   → 提示"已回滚…已自动备份当前状态为临时版本 V16（退出程序即清除）"
   → 若发现点错了：在列表里找到那条 ⏳ 临时，再回滚回它
   → 关掉软件后再打开：临时版本已被自动清除，只剩永久版本
```
### 10.13 直接编辑设定也有退路（2026-10-12 完成，第五批 ② B 项）

**问题**：设定版本**只有"应用提案"时才会产生**。直接在角色管理 / 世界观 / 关系里手改，
既不留版本也留不下备份 —— 手滑改错就没有退路（这一点在写 §10.11 的界面说明时才暴露出来）。

| 项 | 落地 |
|---|---|
| **触发时机** | **首次直接编辑设定之前**自动存一个临时版本。覆盖 10 处写入点：角色（存/删）、关系（存/删）、世界观设定（存/删）、势力关系（存/删） |
| **只存一次** | 用 `backupTakenRef` 记住"本次会话已备份"→ 连续改十几个字段只留 1 个版本，不会把列表刷满；**切换故事时重置**（新故事要重新备份） |
| **失败不阻断** | 备份存不上也要让用户能改设定（与回滚前的自动备份同一原则） |
| **note 写明原因** | 界面传入如"修改角色「夏婉琴」"→ 列表里能看到"编辑前自动备份：修改角色「夏婉琴」（临时，退出程序即清除）" |
| **仍是临时版本** | 复用 §10.12 的机制（`temporary = 1`）→ 退出程序即清除，不污染版本历史 |

**设计取舍（写在代码注释里）**
- 为什么不是"每次保存都存"：那会为每个字段改动产生一个版本，列表被冲垮，真正的历史版本反而找不到
- 为什么不做"内容未变则不存"的校验：备份应当廉价且无害，多存一份好过漏存；用户随时可用「🧹 清理临时版本」

**用户可见流程**
```
在角色管理里改夏婉琴的小传 → 点保存
  → 提示"🛟 已在编辑前自动备份为临时版本 V16（退出程序即清除）"
  → 改错了：去「演进提案」页找到那条 ⏳ 临时，回滚回它
  → 关掉软件：临时版本自动清除
```

| **uuid 依赖** | `uuid = { version = "1", features = ["v4"] }`（**已在 Tauri 依赖树里**，加为直接依赖不新增下载） |

**实施中踩到并修掉的一个隐蔽 bug（值得记）**

复制语句最初写成：

```sql
INSERT INTO characters (…, branch_id)
SELECT …, ?1 FROM characters       -- ?1 = 新分支 id
WHERE branch_id = ?                -- 匿名 ? 被 SQLite 当成 ?1！
```

**SQLite 里匿名 `?` 等价于 `?1`**，于是 WHERE 也绑上了"新分支 id"——而此时新分支还没有行
→ **静默复制出 0 行**（不报错、不抛异常，纯粹数据丢失）。

- 为什么差点溜过去：**主线场景的 WHERE 是 `branch_id IS NULL`（没有占位符）**，所以
  `create_branch_copies_world_state` 当时是**通过的**；只有"源分支非 NULL"（嵌套）时才暴露。
- 修法：`branch_clause` 增加**参数编号**（`?N`），复制语句固定 `?1` = 新分支 id、`?2` = 源分支 id，
  两个参数总是都绑，避免条件绑定带来的错位。
- 补测试 `nested_copy_copies_full_world_state`：**嵌套时也逐表断言行数**，专门为这个坑守门。

**测试（7 项）**：创建/列表/详情、**复制世界状态（逐表断言 + 临时版本不复制 + id 必须是新的）**、
主线不被触碰、**嵌套分支从源分支复制**、**嵌套时逐表行数正确**、错误处理、颜色轮替。

**顺带修掉的测试卫生问题**：测试原本会在用户的 `library/default/projects/` 里留下临时故事目录
（实测留下 7 个）。现在每个测试结束时关池并删目录，跑完 `library/` 只剩真实故事。

**验收**：114 项单测通过（107 + 新增 7）；`cargo build` / `tsc` 通过。
