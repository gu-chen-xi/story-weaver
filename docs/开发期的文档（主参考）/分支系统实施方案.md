# 分支系统实施方案（第五批 ③）

> 用户 2026-10-12 定的形态：**按节点来分支；分支之后还是原来的运行逻辑；两个分支互不干扰各自的独立状态、
> 角色关系和后续的时间线；而且可切换回去**。只做**手动**分叉（自动分叉属"分支插件"，插件默认不启动）。

## 一、现状盘点（地基已就位）

| 已有 | 位置 | 对本项的意义 |
|---|---|---|
| `timeline_nodes.parent_id` + 幂等补链 | 第五批 ① | **"一个节点可以有多条后继"就是分叉** —— 分叉本身不需要改数据结构 |
| `children_index` / `path_to_root` / `flatten_tree` / `branches_of` / `is_fork` | `timeline.rs` | 树运算已具备且**有单测**（含"分支隔离""线性等价性"） |
| 跨天装配已改为**按父链**取历史 | `generate_stream.rs` | 分支后"读不到别的分支内容"这一条**已经成立** |
| 快照 / 回滚 / 差异预览 / 临时版本 | `evolution.rs` | 状态变化的"安全网"与"时间点记录"都已具备 |

**还缺的三样**：① 分支的**身份**（谁是谁）② 状态的**隔离**（各分支独立）③ 切换分支的**入口**。

## 二、核心设计决策

### 决策 1：分支的"身份"用什么标识？

**方案 A（采用）：用"分支根节点 id"作为分支标识。**
- 分叉 = 在某节点下新建一个子节点；这个子节点就是新分支的**根**，`branch_root_id` 即它的 id
- 主干分支的标识 = 时间线根节点（通常"第 1 天"）的 id
- 优点：**不新增"分支表"**，分支与节点天然绑定，删节点时不会留下孤儿分支
- 代价：需要一个"当前节点 → 所属分支根"的解析函数（就是已有的 `path_to_root` 取第一个元素）

**方案 B（不采用）：新建 `branches` 表。**
- 要维护 parent_branch、分支名、创建时间等，且与节点树形成**两套并行的层级**，容易出现不同步

### 决策 2：状态隔离怎么做？（本项最关键的取舍）

**方案 A（采用）：行级 `branch_root_id` 标记 + 按当前分支过滤读取。**
- 给三张**设定表**加 `branch_root_id`（默认 0 = 主干）：
  `characters` / `relations` / `world_settings`
  （已核对真实库的表清单，故事库里**没有** `story_terms` —— 术语是并进 `world_settings` 的）
- 分叉时**复制**父分支的全部状态行给新分支（带上新 `branch_root_id`）
- 之后每张表的读/写都按"当前分支"过滤 → 两个分支天然互不干扰
- 迁移：现有全部行 `branch_root_id = 0`（主干），老库行为不变

**方案 B（不采用）：用快照驱动**（分支 + 快照 = 当前状态）。
- 改动最小，但每次切换分支都要"整表替换"（就是回滚），**慢且有破坏性**（切换本身会改库、
  并发/中断时不安全），而且"切分支"与"回滚"语义会混在一起

**方案 C（不采用）：一个分支一个 story.db。**
- 隔离最彻底，但跨分支统计/切换/迁移成本都高，且与"同一故事的不同可能"这一语义不符

### 决策 3：快照与提案是否也隔离？

| 对象 | 处理 |
|---|---|
| `setting_snapshots` | 加 `branch_root_id`；列表**默认只显示当前分支**（可切换"显示全部分支"） |
| `change_proposals` | 加 `branch_root_id`；**只分析当前分支的节点** → 天然只产当前分支的提案 |
| `event_logs` / `audit_logs` | 加 `branch_root_id`（便于过滤），但**默认不过滤**（日志是流水，全看更有用） |
| 立绘 / 素材库 | **不隔离**（素材是共享资源；用户的设定里没提，且隔离会让"同一个角色的立绘"变得难以管理） |
| 日摘要 / 阶段摘要 | 属于节点（`node_id`）→ **天然随分支走**，无需改 |

## 三、分步实施（每步一个提交、每步可独立验收）

### 第 1 步：分支的创建与识别（纯数据 + 纯函数）
- 新增 `timeline::create_branch_from(story_id, node_id) -> TimelineNode`：
  在该节点下新建一个 day 节点作为新分支的根（`parent_id = node_id`，`sort_order` 取同层最大值 +1）
- 新增纯函数 `branch_root_of(nodes, node_id) -> i64`（= `path_to_root(...).first()`）
- 新增 `list_branches(story_id) -> Vec<BranchInfo>`：每个分支根 + 它的节点数 + 是否当前分支所在
- 单测：分叉后 `is_fork(parent) == true`；`branch_root_of` 对两个分支分别返回各自的根；主干仍为时间线根
- **验收**：暂无界面；测试证明"分叉能建出来、归属判断正确"

### 第 2 步：状态隔离（数据层）
- 四张状态表加 `branch_root_id`（幂等迁移，默认 0）
- 所有读取按"当前分支"过滤；所有写入带上当前分支
- **当前分支**存在哪里：`stories.current_branch_root_id`（library.db）—— 记住"上次在哪条分支"
- 分叉时复制父分支状态行
- 单测：临时库上分叉 → 改 A 分支的角色 → B 分支读到的是旧值；主干不受影响
- **验收**：后端行为正确（前端还没接）

### 第 3 步：界面（分叉 + 切换）
- 时间维的每个节点右侧加「⚑ 分叉」（或只在节点菜单里），点击 → 确认 → 创建分支并切过去
- 时间维上：分支节点用**缩进 + 连线**显示（① 的树控件此时才真正出现 —— 有分叉才显示）
- 顶部加"当前分支"指示 + 下拉切换（列出所有分支：主干 / 分支 2 …）
- 切换分支 = 切换当前节点到该分支的**最后写入节点** + 重新加载角色/关系/世界观/提案/版本列表
- **验收**：手动走一遍用户描述的场景（分叉 → 各写剧情 → 切回来状态独立）

### 第 4 步：配套（按需）
- 分支命名与备注（默认"分支 2"，可改名）
- 快照列表加"按分支过滤"
- 版本列表的差异预览：跨分支回滚时给出**额外警告**（"这会用其它分支的状态覆盖当前分支"）

## 四、明确不做（写清楚避免误解）

- ❌ **自动分叉**（属"分支插件"，默认不启动，另做）
- ❌ **分支合并**（数据冲突语义复杂；本期不做，留待以后评估）
- ❌ 立绘 / 素材库隔离（素材是共享资源）
- ❌ 分支删除（第 1~3 步先不做；删分支涉及"它的节点与状态行怎么处理"，需要单独设计）

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| **改动面大**：状态表加列会影响所有读写路径 | 分两步走（先数据层、后界面），每步跑全量测试；`branch_root_id = 0` 时行为与现在完全一致 |
| **老库迁移** | 幂等补列 + 默认 0（主干）→ 老故事零感知；真机库上先验证再继续 |
| **跨天装配** | 已按父链取（① 完成），**这是分支隔离最容易出错的一环，已提前解决** |
| **切分支时状态没跟上** | 切换后**强制重新加载**全部相关状态（角色/关系/世界观/提案/版本），并在界面提示"已切到分支 X" |
| **用户误以为主干也被隔离** | 界面明确标注每条分支的名字与节点数；主干标为「主干」 |
