# 立绘系统设计（ROADMAP 第四批 ⑥）

> 本文档定稿于 2026-10-11，与用户确认「两者都留」+「即使没有绘图系统也不影响立绘素材与角色管理立绘展示」之后。
> 状态：**设计已定，待动工**。

---

## 一、核心原则：一条单向依赖线

```
        ┌──────────────────────────────┐
        │   绘图系统（插件，可缺席）      │   ← 依赖下方；缺席不影响下方
        │   云端适配器 / 本地适配器      │
        └──────────────┬───────────────┘
                       │ 产出的图片
                       ▼  必须走同一条入口
        ┌──────────────────────────────┐
        │   立绘素材库（核心功能）        │   ← 零依赖，永远可用
        │   portraits 表 + 文件 + 版本    │
        └──────────────┬───────────────┘
                       │ 按 character_id 绑定
                       ▼
        ┌──────────────────────────────┐
        │   角色管理的立绘展示            │   ← 只读素材库，不关心图片来源
        └──────────────────────────────┘
```

**三条硬规则（架构约束，写进代码注释）**

| # | 规则 | 违反的后果 |
|---|---|---|
| **R1** | 绘图系统**不得绕过 `portrait_import`** 直接写文件或插表 | 版本记录、宽高、绑定、分组全乱 |
| **R2** | 立绘素材库**不得 import 绘图模块**（反向依赖） | 没有绘图服务时素材库直接崩 |
| **R3** | 绘图失败/未配置**不得产生错误态阻塞**素材库与角色管理 | 用户会被"没配绘图"挡住正常功能 |

**判断"是否解耦成功"的验收标准**：把绘图插件整块删掉（注册表去掉那条 + 后端生成模块不编译），
`cargo test` / `tsc` 全过，且素材库的导入、绑定、分组、标签、版本、导出、角色卡展示**全部照常工作**。

## 二、现状盘点（已经具备的）

| 层 | 已有 | 说明 |
|---|---|---|
| 存储 | `library/default/shared/portraits/` 目录 + `portraits` 表 + `portrait_versions` 表 | 全局共享素材库 |
| 入库 | `portrait_import`（导入图片）/ `portrait_create`（占位素材） | **生成结果复用这两条** |
| 组织 | `portrait_bind`（绑定角色）/ `portrait_group_set` / `portrait_tag_batch` | 四视图 / 分组 / 批量 |
| 版本 | `portrait_versions` + `add_version` | 已有版本链 |
| 其他 | `portrait_update` / `portrait_update_params` / `portrait_export` / `portrait_delete` | |
| 生成参数列 | `prompt / negative / seed / steps / cfg / model`（**可空默认空**） | 手工图不需要它们，天然兼容 |
| 展示 | 角色管理按 `p.character_id === id && p.story_id === current` 取图 | 只认绑定关系 |

**结论**：素材库这层**不需要为绘图做任何改造**，只需加两个"来源标注"列（可空，不影响老数据）。

## 三、生成层设计（插件）

### 3.1 通道适配器（两者都留）

`GeneratorProvider` 抽象：一个适配器 = 一个通道实现。

| 适配器 | 目标服务 | 说明 |
|---|---|---|
| `cloud_openai_image` | 兼容 OpenAI Images API 的云服务 | 覆盖面最广的一种通用形态 |
| `cloud_custom` | 可配 URL + 请求模板 | 应对各家不兼容 API（即梦 / 通义万相 / 火山…） |
| `local_sdwebui` | SD WebUI（`/sdapi/v1/txt2img`） | 本机跑 |
| `local_comfyui` | ComfyUI（`/prompt` + 轮询 `/history`） | 工作流式，能力最强 |

每个适配器声明自己的元信息（**能力也做成数据，沿用插件基础设施那套**）：

```rust
struct GeneratorDescriptor {
    id: &'static str,            // "local_sdwebui"
    name: &'static str,          // "本地 SD WebUI"
    channel: &'static str,       // "local" | "cloud"
    needs_base_url: bool,
    needs_api_key: bool,
    supports: GenSupports,       // negative / size / steps / cfg / seed / batch
}
```

前端据此**动态决定显示哪些参数控件** —— 不支持负向提示词的通道就不显示那一栏，而不是显示了再报错。

### 3.2 统一请求与结果

```rust
struct GenRequest {
    prompt: String, negative: String,
    width: u32, height: u32,        // 预设：立绘 3:4（768×1024）/ 方图 1:1 / 半身 2:3
    steps: Option<u32>, cfg: Option<f32>, seed: Option<i64>, batch: u32,
    base_portrait_id: Option<i64>,  // 有值 = "重出这张" → 走版本链
}

struct GenResult {
    files: Vec<PathBuf>,            // 落到临时目录
    meta: Value,                    // 通道原始返回（便于排错与复现）
    seed_used: Vec<i64>,            // 实际种子（随机时回填，便于"同种子微调"）
}
```

### 3.3 落库流程（严守 R1）

```
生成 → 图片写入临时目录
     → 逐张调用既有 portrait_import（带来源标注与参数）
     → 自动 add_version（"AI 生成：<通道名>"）
     → 若带 base_portrait_id：作为该素材的新版本，而不是新建一条
     → 若从角色卡发起：按 character_id 自动绑定
     → 失败/取消：临时文件清理，库内不留半成品
```

### 5.1 插件卡（注册表加一条，复用 `PluginCard`）

```

│ 🎨 立绘生成   [已开启 · 本地 SD WebUI]                [打开面板] │

```

### 5.2 生成面板

- 通道选择 + 连接状态（**未配置/连不上时，面板内黄字说明 + 「如何使用手工导入」的指引，绝不弹错误阻塞**）
- 提示词 / 负向提示词（**从角色卡一键填充**：姓名 + 定位 + 年龄 + 性格 + 说话方式 + 别名，拼成基础提示词）
- 尺寸预设 / 步数 / CFG / 种子（随机或固定）/ 张数
- 「开始生成」→ 进度 → 结果缩略图预览 → 「入库（可勾选）」

### 5.3 两个既有入口的关系

| 入口 | 处理 |
|---|---|
| 立绘素材页的「✨ AI 生成立绘」 | 改为**唤起同一个面板**（不再是一句"依赖插件系统（后置）"的提示） |
| 角色卡的「✨ AI 生成立绘」 | 带 `character_id` 唤起，提示词用该角色资料预填，入库后**自动绑定该角色** |

两个入口共用一套面板与后端通道 —— 不为每个入口各写一套。

### 5.4 素材库里的来源角标

素材卡上加来源标记（`AI` / `手工` / `占位`），并可**按来源筛选**。这样"AI 产了多少张"一目了然，
也方便把不满意的 AI 产出批量删掉（`portrait_delete` 已具备）。

## 六、分期（每期都可独立提交、独立验收）

| 期 | 内容 | 依赖 |
|---|---|---|
| **P1 骨架与边界** | 后端 `generator` 模块（trait + 适配器表 + 临时目录 + 清理）、`portrait_import` 的来源标注与版本描述联动、`base_portrait_id` 重出链；前端注册表加插件卡 + 面板骨架（通道选择 + 连接测试 + 未配置时的友好提示） | **无外部服务即可完成并验收**（通道测试允许失败） |
| **P2 本地通道** | SD WebUI 适配器（最省事：一个 POST + base64 返回）+ 参数联动 + 结果入库 + 自动绑定 | 需要本机 SD WebUI（可选，没装也能验收 P1） |
| **P3 云端通道** | 通用 Images API 适配器 + 自定义 URL/请求模板（应对各家差异）+ API Key 走既有 keychain | 需要一家云服务（保持可选） |
| **P4 体验收口** | 从角色卡一键填充提示词、重出（同种子微调）、批量入库勾选、来源角标与筛选、失败清理与错误文案 | 无 |

**P1 是"铺路"阶段的延续**，且**不依赖任何外部服务**就能完整验收 —— 这样即使你暂时没有可用的绘图服务，
边界也先立住了；等以后接上服务，P2/P3 只是加适配器。

  素材库与角色管理完全不受影响
- 这样 P1 的成果**不是空壳**：骨架可用、边界可验收；以后加适配器是"往表里加一条"，不动界面结构

## 八、P1 实施记录（2026-10-11）

### 8.1 实际落地的列名（比设计稿更中立）

设计稿里写的是 `generator_id / base_portrait_id`，实施时发现这两个名字**本身就让素材库"知道"了生成**（R2 的精神）。
最终改为**业务中立**的列名 —— 素材库只知道"有这么三个普通列"，不知道谁写、写什么：

| 列 | 含义（由调用方定义，素材库不解释） |
|---|---|
| `source` | 来源标记（当前取值 `manual` / `placeholder` / `ai-local` / `ai-cloud`） |
| `origin_tool` | 产生它的工具 id（当前取值 = 通道 id，如 `local_sdwebui`） |
| `derived_from` | 派生来源：指向被它重做/替换的那一条（可空） |

写入走素材库的通用入口 `portraits::portrait_set_columns(id, &[(列名, 值)])` ——
**只做白名单校验 + 绑定写入，不理解任何列的业务语义**。生成侧的桥接模块负责解释这些值。

### 8.2 模块分层（实际）

| 模块 | 职责 | 依赖 |
|---|---|---|
| `portraits.rs` | 立绘素材库（表 / 文件 / 版本 / 分组 / 绑定 / 导入导出） | **无**（最底层） |
| `generator.rs` | 各通道适配器：产图到 `target/gen-tmp` | 只依赖临时目录，**不碰数据库** |
| `generator_ingest.rs` | **唯一的桥接**：生成结果 → 走 `portrait_import` 入库 + 写来源/参数快照 | 依赖 `portraits` |
| `lib.rs` | 命令注册（宿主） | 依赖以上三者 |

### 8.3 边界已钉成可执行断言

`generator_ingest::tests::architecture_boundaries_hold` 会**读源码文件**做静态检查（非注释行）：

- **R2**：`portraits.rs` 里不得出现 `generator` / `GenRequest` / `ai-local` / `gen-tmp` / `SD WebUI` 等生成相关标识符
- **R1**：`generator.rs` 的非注释代码里不得出现 `INSERT INTO portraits` / `UPDATE portraits` / `portraits_dir` / `sqlx::query`
- **桥接唯一性**：`generator_ingest.rs` 必须调用 `portrait_import`

以后谁不小心破坏边界，这个测试会直接变红。

### 8.4 解耦验收（按设计文档 §一 的验收标准）

| 验收点 | 结果 |
|---|---|
| 素材库是否反向依赖生成 | ✅ 零感知（测试断言） |
| 生成是否绕过入库入口 | ✅ 只产临时文件（测试断言） |
| 删掉绘图功能要动几个文件 | **3 个**：`generator.rs`、`generator_ingest.rs`、注册表一条（外加 `lib.rs` 的 6 行命令注册） |
| 素材库 / 角色管理是否要改 | ✅ **一行都不用改** |

### 8.5 P1 已实现能力

## 九、P3 云端通道实施记录（2026-10-11）

用户定「云端两个都做」，本轮完成。

### 9.1 两个适配器

| 适配器 | 请求 | 响应解析 | 说明 |
|---|---|---|---|
| `cloud_openai_image` | `POST {base_url}/images/generations` | `data[].b64_json`（也兼容 `data[].url`，会去下载） | 负向提示词按该 API 惯例**并入 prompt**（`\n\nNegative prompt: …`）；没填 model 就不带该字段 |
| `cloud_custom` | `POST {请求地址}` + **用户填的请求体模板** | 用户填的**响应字段路径** | 占位符 `{{prompt}} {{negative}} {{negative_prompt}} {{width}} {{height}} {{batch}} {{seed}} {{steps}} {{cfg}} {{model}} {{api_key}}`，在 URL / 请求头 / 请求体里都能用 |

**响应字段路径**支持三种写法：

| 写法 | 含义 |
|---|---|
| `b64:data.0.b64_json` | 该路径的字符串是 base64 |
| `url:output.0` | 该路径是图片 URL（软件下载后入库） |
| `auto:images` | 自动识别：`http(s)://` 当 URL，`data:` 前缀剥掉，其余当 base64；元素也可以是含 `b64_json` / `url` / `b64` 的对象 |

**鉴权**三选一：`bearer`（`Authorization: Bearer`）/ `api-key`（`api-key` 头）/ `none`；另可填**额外请求头**（`X-Org=abc;X-Foo=bar`）。

### 9.2 配置项（键名见 db.rs）

| 键 | 用途 |
|---|---|
| `portrait.cloud_url` | OpenAI 形态：服务地址（填到 `/v1` 为止） |
| `portrait.cloud_model` | OpenAI 形态：模型名（可空） |
| `portrait.cloud_api_key` | 云端 API Key（**同时**会写入系统凭据库 `portrait_api_key`，配置表留空也能用） |
| `portrait.cloud_request_url` | 自定义形态：完整请求地址（可含占位符） |
| `portrait.cloud_body_template` | 自定义形态：请求体模板（JSON 文本） |
| `portrait.cloud_response_path` | 自定义形态：响应字段路径 |
| `portrait.cloud_auth_style` | `bearer` / `api-key` / `none` |
| `portrait.cloud_extra_headers` | 额外请求头 |
| `portrait.cloud_ok_status` | 成功状态码（少数服务用 201 等） |
| `portrait.cloud_response_raw_b64` | 响应整体就是 base64 文本（极少数服务） |

### 9.3 探测策略（不浪费额度）

| 通道 | 探测方式 |
|---|---|
| `cloud_openai_image` | 先 `GET /models`（最省）：成功 → 报出可选模型名；401/403 → 明确说鉴权失败；没有该端点 → 如实说明"这在很多服务上正常，建议直接小尺寸生成一张验证" |
| `cloud_custom` | **只做配置完整性检查**（地址 / 模板 / 响应路径 / 模板是否合法 JSON），**不替用户发请求**，避免误触计费 |

### 9.4 界面

- 「插件 / 扩展 › 立绘生成」：选中云端通道时才出现**云端配置区**（本地通道完全不出现，避免干扰）
- 字段按通道裁剪：OpenAI 形态只显示地址/模型；自定义形态显示请求地址/模板/响应路径
- 「保存到配置」按钮；API Key 输入框不回显明文，只显示「已保存 / 尚未设置」
- 提示词参数按 `supports` 动态裁剪（OpenAI 形态不显示负向/步数/CFG，因为它确实没有）

### 9.5 并发加固（实施中发现）

`cleanup_temp` 原本会删掉临时目录里**所有**文件 —— 并发生成时会删掉另一个请求刚产出的图（测试里并行跑两个通道时确实踩到了）。
现在：**最近 5 分钟内改动过的文件一律保护**；另提供 `remove_files` 供精确删除。新增单测 `cleanup_protects_fresh_files` 锁住该行为。

## 十、来源标识与合规导出（2026-10-11，P4 的一部分）

用户要求「给 AI 生成的图加角标，导出时也能带上」，本轮完成。

### 10.1 素材库里的来源标注

| 项 | 实现 |
|---|---|
| **来源字段** | `portraits.source`（业务中立列）由入库方写入：手工导入写 `manual`、占位写 `placeholder`、AI 生成写 `ai-local` / `ai-cloud`（取值定义在 `generator_ingest.rs`，**素材库只原样存取**） |
| **卡片角标** | 四种卡片布局（网格 / 列表 / 瀑布 / 详情）均显示 `AI` 角标；鼠标悬停提示"对外发布时须标注 AI 生成字样" |
| **按来源筛选** | 素材页新增三个 chip：`来源：全部` / `手工` / `AI 生成` |
| **概览行** | 「共 N 张 … 」后追加「AI 生成 M 张」（M > 0 时显示，警示色） |

**注意**：`generator.rs` 与 `generator_ingest.rs` 中的来源常量**只在生成侧定义**；
素材库侧不出现任何 `ai-*` 字样 —— 这是架构边界测试（R2）强制的，实施时就抓到过一次（我在注释里写了 `ai-local` 被判红）。

### 10.2 导出时带上标识（不修改图片内容）

导出仍是 `std::fs::copy` 纯字节拷贝（**不动像素、不重编码，水印与元数据原样保留**），在此之上：

| 措施 | 说明 |
|---|---|
| **文件名加 `_AI`** | AI 生成的文件导出为 `角色名_12_AI.png`，标识跟着文件走，即使被单独转发也在 |
| **附「导出清单.json」** | 记录每个导出文件的 `name` / `source` / `ai_generated` / `origin_tool` / `prompt` / `negative` / `seed`，并写明"ai_generated=true 的图片对外发布时须标注 AI 生成" |
| **返回文案** | 「已导出 N/M 个素材 → 路径（其中 AI 生成 K 个，文件名带 _AI；已附「导出清单.json」）」 |

清单里的提示词与参数同时具备**创作过程证据**的作用（著作权争议时可用）。

### 10.3 一处顺手修的隐患

`portrait_get` 原用 `SELECT *`，而 `row_to_item` 是**按下标读列**的 —— 表结构一变（本轮就加了三个列）就会错位。
已统一改用 `COLS` 常量取列，与其它查询保持一致。
